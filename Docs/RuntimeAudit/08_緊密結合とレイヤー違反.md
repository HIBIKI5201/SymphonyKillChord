# 08. 緊密結合とレイヤー違反

## 前提: レイヤー分離は概ね守られている

`ServiceLocator` の参照は全229箇所のうち、**227箇所が `6.Composition` 内**に収まっている。
`asmdef` による参照制約（`KillChord.Domain` は `Utility` のみを参照、など）も機能しており、
Clean Architecture の依存方向は保たれている。LINQも `6.Composition` の3ファイルのみ。

以下は、その原則から外れている箇所と、明示的な依存に置き換えたい箇所。

---

## 【要検証】Adaptor層からのServiceLocator直接参照（2箇所）

**場所1**: [SkillCrosshairProgressController.cs:55-57](../../Assets/Scripts/Runtime/3.Adaptor/InGame/Skill/SkillUI/SkillCrosshairProgressController.cs)

```csharp
private static bool IsLockedOn()
{
    return ServiceLocator.TryGetInstance<TargetSystemController>(out var targetSystemController)
        && ...;
}
```

`static` メソッド内でサービスを取得しているため、**コンストラクタ注入に置き換えられない形**に
なっている。このクラスは Adaptor 層であり、本来は `TargetSystemController` を
コンストラクタで受け取るべき。同じ層の
[HUDEnemyHealthPresenter.cs:18-29](../../Assets/Scripts/Runtime/3.Adaptor/InGame/UI/HUDEnemyHealthPresenter.cs) は
`TargetSystemController` を正しくコンストラクタ注入している。

**場所2**: [BattleSortieSelectionService.cs:43-67](../../Assets/Scripts/Runtime/3.Adaptor/OutGame/StageSelect/BattleSortieSelectionService.cs)

```csharp
private static SelectedBattleStageState ResolveSelectedBattleStageState()
{
    if (ServiceLocator.TryGetInstance(out SelectedBattleStageState selectedBattleStageState))
    {
        return selectedBattleStageState;
    }
    selectedBattleStageState = new SelectedBattleStageState();
    ServiceLocator.RegisterInstance(selectedBattleStageState);   // ← 取得だけでなく登録もしている
    ...
}
```

こちらはより深刻で、**Adaptor層がServiceLocatorへの登録まで行っている**。
「無ければ作って登録する」という遅延初期化をAdaptorが担うと、
Composition層が把握していないインスタンスがコンテナに入る。

**修正方針**: 両方とも `6.Composition` 側で解決してコンストラクタ注入する。
`BattleSortieSelectionService` の遅延生成は Composition の初期化フェーズへ移す。

## 【設計指摘】ServiceLocator取得の定型ブロックが79箇所に重複

`ServiceLocator.TryGetInstance` の呼び出しは 25ファイル・79箇所に及び、
その多くが同一の定型パターンになっている。

```csharp
// 6.Composition/OutGame/StageSelect/StageSelectInitializer.cs:262-315 — 6回連続
if (!ServiceLocator.TryGetInstance(out SomeService x))
{
    Debug.LogError("...");
    return false;
}
```

同様のブロックは [IngameComposition.cs:174-202](../../Assets/Scripts/Runtime/6.Composition/InGame/Bootstrap/IngameComposition.cs)
`TryResolveBootDependencies` にもある。

**修正方針**: ヘルパーメソッドに集約する。

```csharp
private static bool TryResolve<T>(out T value, string context) where T : class
{
    if (ServiceLocator.TryGetInstance(out value)) { return true; }
    Debug.LogError($"[{context}] {typeof(T).Name} の解決に失敗しました。");
    return false;
}
```

これだけで20行以上の削減になり、同時に [02. Null参照リスク](02_Null参照リスクとアサート漏れ.md) で
指摘したCompositionのガード不足も一箇所で改善できる。

## 【設計指摘】FindObjectsByType系によるシーン走査での結合（29箇所）

シーン内オブジェクトの参照解決を実行時走査で行っている箇所が29ある。
大半は `6.Composition` に集中しており、Composition Root の役割としては許容範囲。

ただし、**1つのメソッドで8回連続で走査している箇所**は改善余地が大きい。

```csharp
// 6.Composition/InGame/Sequence/SequenceInitializationModule.cs:41-48
_stageSequenceView        = FindFirstObjectByType<StageSequenceView>();
_stageSequenceMessageView = FindFirstObjectByType<StageSequenceMessageView>();
_stageStartFadeView       = FindFirstObjectByType<StageStartFadeView>();
_stageStartCameraView     = FindFirstObjectByType<CameraSystemView>();
_cameraSystemView         = FindFirstObjectByType<CameraSystemView>();
_stageResultView          = FindFirstObjectByType<StageResultView>();
_inGamePlayDirector       = FindFirstObjectByType<InGamePlayDirector>();
_stageSequenceVoiceView   = FindFirstObjectByType<StageSequenceVoiceView>();
```

`FindFirstObjectByType` は毎回シーン全体を走査する。8回の走査に加え、
**どれか1つでもシーンに存在しなければ静かにnullが入り**、
後段でNullReferenceExceptionになる（ログなし）。

**修正方針**: `[SerializeField]` でInspector参照に置き換えるのが最も確実。
シーン構成上それが難しい場合は、少なくとも取得失敗時のログを追加する。

より問題なのはView層での使用。

```csharp
// 4.View/InGame/Enemy/EnemySpawnPositionSearcher.cs:19
_positionPairs = GameObject.FindObjectsByType<SpawnPositionPair>(FindObjectsSortMode.None);

// 4.View/Persistent/Voice/VoiceSource.cs:65
_volumeRegistryView ??= FindAnyObjectByType<PersistentAudioVolumeRegistryView>();

// 4.View/Persistent/Music/SoundEffectSource.cs:72
_volumeRegistryView ??= FindAnyObjectByType<PersistentAudioVolumeRegistryView>();
```

View層が自力で依存を探しに行くのは、Composition Root の存在意義を損なう。
音源2件は `??=` の問題（[02](02_Null参照リスクとアサート漏れ.md) 参照）も併発している。

## 【設計指摘】Camera.mainへの直接依存（6箇所）

```
4.View/InGame/UI/HUDEnemyHealthViewModel.cs:22
4.View/InGame/Enemy/EnemyHealthBillboardView.cs:14
4.View/InGame/Camera/CameraSystemView.cs:78,79,396
6.Composition/InGame/Reticle/ReticleHudInitializer.cs:43
6.Composition/InGame/Bootstrap/SceneDependencyInitializationModule.cs:74
```

`Camera.main` は `MainCamera` タグでの検索であり、Unity 2020以降キャッシュされるものの、
**カメラが差し替わる演出（`StageStartCameraView` 等）と組み合わさると危険**。
本プロジェクトには `CameraSystemView` という明確なカメラ所有者がいるので、
そこから参照を配るのが自然。

特に [CameraSystemView.cs:394-397](../../Assets/Scripts/Runtime/4.View/InGame/Camera/CameraSystemView.cs) は
`Tick` 内（毎フレーム）で `_camera == null` を判定して `Camera.main` を再取得しており、
カメラ喪失時に毎フレーム検索が走る。

## 【設計指摘】静的シングルトンが1クラスだけ存在する

**場所**: [RhythmJustService.cs:11](../../Assets/Scripts/Runtime/2.Application/InGame/Music/RhythmJustService.cs)

```csharp
public static RhythmJustService Instance
```

周辺の Application 層クラスはすべてコンストラクタ注入で構成されているのに、
このクラスだけが `_instance ??= new(...)` 形式の静的シングルトン。
`IDisposable` で自己解除する独自ライフサイクルも持つ。

静的状態はシーンをまたいで残るため、テスト・シーン遷移の両面でリスクになる。

**修正方針**: 他のサービスと同様、Composition層で生成して `ServiceLocator` へ登録するか、
必要な箇所へ注入する。

## 【設計指摘】Composition層に業務ロジックとUIレイアウトが混入

**場所**: [StageSelectInitializer.cs](../../Assets/Scripts/Runtime/6.Composition/OutGame/StageSelect/StageSelectInitializer.cs)（945行）

`6.Composition` 内で最大のファイル。`Initialize()`（260-393行）がDIの組み立てに加えて
以下のUIレイアウト計算を抱えている。

| メソッド | 行 | 内容 |
| --- | --- | --- |
| `BuildNodeCenterMap` | 618-660 | ノード中心座標の算出 |
| `BuildConnectionElements` | 668-718 | 接続線要素の生成 |
| `BuildNodeElements` | 726-761 | ノード要素の生成 |
| `UpdateStageMapVerticalAlignment` | 532-548 | 垂直位置の調整 |

これらは View または Adaptor の責務であり、Composition Root は
「依存を繋ぐ」ことに専念すべき。

**修正方針**: レイアウト構築を `StageMapLayoutBuilder`（View層）として切り出し、
Initializer からは生成済みのビルダーを呼ぶだけにする。
