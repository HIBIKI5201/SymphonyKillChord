## 【確定】文字列補間226箇所がリリースビルドでも常に評価される

Unityの `Debug.Log` は**既定ではリリースビルドから除去されない**
（Player Settings で明示的に無効化しない限り、`UnityEngine.Debug` の呼び出しは残る）。

さらに重要なのは、**文字列補間は `Debug.Log` を呼ぶ前に評価される**という点。
ログ出力自体が無効化されていても、引数の文字列生成は実行される。

```csharp
// 6.Composition/OutGame/SkillTree/SkillTreeController.cs:100
Debug.LogError($"[SkillTreeController] 解放対象ノードの取得に失敗しました。");
```

この例は補間対象の変数が1つもないのに `$` が付いており、
**単なる文字列リテラルにすべきところで補間構文が使われている**。
コンパイラが最適化する場合もあるが、意図としては誤り。

より問題なのは変数を含むもの。

```csharp
// 4.View/InGame/Reticle/ReticleHudView.cs:31
Debug.LogError($"[{nameof(ReticleHudView)}] {nameof(_markerPrefab)} が未設定です。", this);
```

`nameof` はコンパイル時定数なのでこれは実質的にリテラルだが、
実行時の値を埋め込むログは毎回 `string.Format` 相当の処理とヒープ確保を伴う。

**幸い、毎フレーム実行されるパスにログは見つからなかった**。
`EnemyWaveTimerView.FixedUpdate` 内の `Debug.Log`（[line 68](../../Assets/Scripts/Runtime/4.View/InGame/Enemy/EnemyWaveTimerView.cs)）も
Waveタイムアウト時のみで、毎フレームではない。したがって
現時点でのGC影響は限定的である。

**修正方針**: 独自ログラッパーを用意し、`[Conditional("UNITY_EDITOR")]` または
`[Conditional("ENABLE_LOG")]` を付ける。`Conditional` 属性は**呼び出し側ごと除去される**ため、
引数の文字列補間も実行されなくなる。これが `#if` で囲むより優れている点。

```csharp
public static class KillChordLog
{
    [System.Diagnostics.Conditional("UNITY_EDITOR")]
    [System.Diagnostics.Conditional("KILLCHORD_ENABLE_LOG")]
    public static void Info(string message, UnityEngine.Object context = null)
        => UnityEngine.Debug.Log(message, context);

    // Warning / Error も同様。ただし Error はリリースでも残すか要検討。
}
```

なお `ZString`（導入済み・未使用、[07. ライブラリ未活用](07_ライブラリ未活用.md) 参照）を
組み合わせれば、残すログのアロケーションも削減できる。

## 【設計指摘】ログのプレフィックス表記が不統一

現在、以下の表記が混在している。

```csharp
Debug.LogError("[EnemyRaycastDetectView] Target transform is null.");            // 英語・角括弧
Debug.LogWarning($"[{nameof(ACLikeRhythmGuideView)}] ジャストタイミング演出設定が未設定です。", this);  // 日本語・nameof
Debug.LogError("_beatColor の長さが判定ゾーン数より少ないです。", this);            // プレフィックスなし
Debug.Log("[EnemyWaveTimerView] Wave Timeout.");                                  // 英語
Debug.Log(skipped ? "シナリオ再生完了: スキップ終了。" : ...);                     // プレフィックスなし・日本語
```

言語（日本語/英語）、プレフィックスの有無、`nameof` 使用の有無がバラバラ。

`[EnemyRaycastDetectView] Target transform is null.` のように
**メッセージ本文が英語**のものと日本語のものが同一ファイル内に混在している例もある
（[EnemyRaycastDetectView.cs:24,30,208,214](../../Assets/Scripts/Runtime/4.View/InGame/Enemy/EnemyRaycastDetectView.cs)）。

**修正方針**: 上記のログラッパー導入時に規約を固定する。
`nameof` によるクラス名プレフィックスは自動付与できるため、
呼び出し側はメッセージ本文だけを書く形にできる。

## 【設計指摘】第2引数 context の指定漏れ

`Debug.Log(message, context)` の第2引数に `this` を渡すと、
Consoleでログをクリックした際に**該当オブジェクトがHierarchyでハイライトされる**。
デバッグ効率に大きく影響する。

指定されている例:
```csharp
// 4.View/InGame/Reticle/ReticleHudView.cs:31,36
Debug.LogError($"[{nameof(ReticleHudView)}] {nameof(_markerPrefab)} が未設定です。", this);

// 4.View/InGame/Enemy/EnemyRaycastDetectView.cs:208,214
Debug.LogWarning("[EnemyRaycastDetectView] Attack warning decal is not assigned. ...", this);
```

指定されていない例:
```csharp
// 4.View/InGame/Enemy/EnemyRaycastDetectView.cs:24,30 — 同じファイル内なのに未指定
Debug.LogError("[EnemyRaycastDetectView] Target transform is null.");
Debug.LogError("[EnemyRaycastDetectView] Target collider is missing.");

// 4.View/InGame/Enemy/EnemyWaveTimerView.cs:68
Debug.Log("[EnemyWaveTimerView] Wave Timeout.");
```

MonoBehaviour内のログでは原則 `this` を渡すべき。
特に敵など**同じPrefabが多数存在するオブジェクト**では、
どの個体のログか特定できないと調査が困難になる。

## 【設計指摘】エラーを検知しているのに処理を継続している箇所

ログの運用として最も重大な問題は、**`LogError` を出しながら処理を止めていない**こと。

| 場所 | 状況 |
| --- | --- |
| [SkillTreeController.cs:98-102](../../Assets/Scripts/Runtime/3.Adaptor/OutGame/SkillTree/SkillTreeController.cs) | `return` がなく直後の `foreach` でNullReferenceException（[02](02_Null参照リスクとアサート漏れ.md) 参照） |
| [ACLikeRhythmGuideView.cs:222-225](../../Assets/Scripts/Runtime/4.View/InGame/Music/ACLikeRhythmGuideView.cs) | `_effectConfig` 未設定を警告するが、以降 `_effectConfig != null` チェックが各所に散在 |
| [ReticleHudView.cs:27-38](../../Assets/Scripts/Runtime/4.View/InGame/Reticle/ReticleHudView.cs) | `Awake` でエラーを出し、`LateUpdate` で毎回nullチェックして黙ってreturn |

`ReticleHudView` のパターンは「起動時に1回エラーを出し、以降は静かに無効化」という
妥当な設計だが、`_presenter == null` によるreturnは毎フレーム評価される。
`enabled = false` にすればUnityメッセージ自体が止まる。

**修正方針**: 「回復不能なエラーを検知したら、ログを出した上で
コンポーネントを `enabled = false` にする」を規約にする。
毎フレームの無駄なチェックが消え、問題も明確になる。
