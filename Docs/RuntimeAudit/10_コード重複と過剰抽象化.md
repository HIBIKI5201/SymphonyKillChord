# 10. コード重複と過剰抽象化

前回の調査（レイヤー別の簡略化余地の洗い出し）の結果を統合したもの。
「動作は正しいが、より少ないコードで同じことができる」箇所を扱う。

## 最大の重複塊: Enemy系とBoss系の全面コピペ（約1,300行）

Boss実装がEnemy実装のファイル単位コピーになっており、クラス名以外がほぼ同一。

| 層 | 対象 | 規模 |
| --- | --- | --- |
| 2.Application | `EnemyAttackReservationUsecase` / `BossAttackReservationUsecase` / `ShellReservationUsecase` | 402行 |
| 4.View | `BehaviorGraphNode/Action` × 4 + `Condition` × 4（Enemy/Boss各々） | 約440行 |
| 4.View | `AIFacade` 系 × 4（Enemy/Boss各々） | 約440行 |

特筆すべきは、[BossAttackReservationUsecase.cs:10](../../Assets/Scripts/Runtime/2.Application/InGame/Enemy/Boss/BossAttackReservationUsecase.cs) の
コメントに「`EnemyAttackReservationUsecase` には手を入れず」と、
**意図的なコピペであることが明記されている**点。既存実装への影響を避けるための
判断であり、当時の選択としては妥当だが、負債として顕在化している。

3クラスとも `HasReservation` / `OnReservedTimingReached` / `On2BeatBefore` /
`On1BeatBefore` / `Cancel` / `Dispose` / `Deactivate` を同一構造で持つ。

**修正方針**: 共通の予約スケジューラを基底クラスまたは合成用ヘルパーとして抽出する。
`BehaviorGraphNode` 側は `BlackboardVariable<TBattle>` / `<TState>` を型引数にした
ジェネリック基底クラスで吸収できる。

## シナリオ出力パイプラインが4層構造で種類ごとに複製（約24ファイル）

**場所**: `3.Adaptor/OutGame/Scenario/`

`AnimationEventHandler` / `BackgroundEventHandler` / `FadeEventHandler` /
`LayerEventHandler` / `PortraitEventHandler`（各30〜45行）が
`IXxxOutputPort` 経由で `XxxPresenter` に1行転送し、それがさらに `IXxxViewSink` へ1行転送する。

```
EventHandler → Facade → Presenter → ViewSink
```

「値を1つ渡すだけ」の処理に対して、種類ごとに interface × 3 + class × 2 が複製されている。
[ScenarioPresenterFacade.cs](../../Assets/Scripts/Runtime/3.Adaptor/OutGame/Scenario/ScenarioPresenterFacade.cs) も
6つのOutputPortへの単純委譲のみ。

**修正方針**: 汎用の `ScenarioEventHandler<TEvent, TId, TDefinition>` 基底クラスを導入するか、
Presenter層とViewSink層を統合する。

### 訂正

初版では `IStageEffectDefinition` をデッドコードとして挙げていたが、これは誤りだった。
実装は `StageEffectDefinition`（sealed）1件のみだが、
**型として11箇所で使われている**（`IReadOnlyDictionary<int, IStageEffectDefinition>` の形で
`3.Adaptor` / `5.InfraStructure` / `6.Composition` を横断）。

```
3.Adaptor/InGame/Stage/StageEffectPresenter.cs:25       Present(IStageEffectDefinition)
5.InfraStructure/InGame/Enemy/EnemyWaveDefinitionAsset.cs:67
5.InfraStructure/InGame/Enemy/EnemyWaveDefinitionRepository.cs:48
6.Composition/InGame/Enemy/EnemyInitializer.cs:325
6.Composition/InGame/Enemy/EnemyModuleContainer.cs:28
6.Composition/InGame/Stage/StageEffectInitializer.cs:111,129,153,161,164
```

削除は「単純な削除」ではなく11箇所の型置換を伴う。
なお、インターフェースと実装が**どちらも `1.Domain` にある**ため
依存の逆転には寄与しておらず、抽象として必須ではない。
優先度の低い整理対象、という位置づけが正しい。

`ApplyFailed` / `ApplyChallenging` / `ApplySucceeded` は checkBox の isOn/interactable と

[ShowScreenUseCase.cs:28-83](../../Assets/Scripts/Runtime/2.Application/OutGame/Screen/ShowScreenUseCase.cs) は
`Execute()` と `Execute(CancellationToken)` の結果構築ロジックがPresent呼び出し以外ほぼ同一。

**ScreenControllerの1行委譲** — [ScreenController.cs:29-56](../../Assets/Scripts/Runtime/3.Adaptor/OutGame/Screen/ScreenController.cs) の
`ShowTitle` / `ShowMenu` / `ShowOptions` / `ShowCredit` は
`_showScreenUseCase.Execute(new ShowScreenCommand(ScreenId.X))` の複製。
`Show(ScreenId id)` 1つで足りる。

**ModuleContainer系10クラス** — `SkillModuleContainer` / `StageResultModuleContainer` /
`MusicSyncModuleContainer` / `TargetSystemModuleContainer` / `EnemyModuleContainer` /
`SceneDependencyModuleContainer` 等が「コンストラクタ + プロパティのみ」の同一パターン。

## 逆に、統合すべきでないもの（調査で確認済み）

過剰な共通化を避けるため、以下は現状維持が妥当と判断した。

- [CatalogRepositoryBase.cs](../../Assets/Scripts/Runtime/5.InfraStructure/OutGame/Scenario/CatalogRepositoryBase.cs) —
  既に良い抽象化として3リポジトリで共有されている
- `IEnemyBattleAIFacade` 等の4分割インターフェース — Enemy/Boss双方に実装があり単一実装ではない
- Mission系 `ConditionAsset` 群 — `SerializeReference` によるポリモーフィズムで、
  Unityエディタ上のデータ駆動設計として妥当
- `IOneShotVisualEffect` の6実装（Particle/Sound/VFXGraph/Animator等） — 正当なStrategyパターン
- `ScreenViewBase` / `IScreenView` — レジストリ経由でポリモーフィックに使用されている
- `ParticleSystemPoolView` — 既に `UnityEngine.Pool.ObjectPool<T>` を活用済み
