## 【最優先】UniTaskが導入済みなのに1ファイルでしか使われていない

`com.cysharp.unitask 2.5.10` が導入されているが、`using Cysharp.Threading.Tasks` を
持つファイルは [AttackIntervalEvaluator.cs](../../Assets/Scripts/Runtime/2.Application/InGame/Battle/AttackIntervalEvaluator.cs) の**1つだけ**。

一方 `using System.Threading.Tasks` を持つファイルは **100以上**ある。

### なぜ問題か

1. **アロケーション**: `Task` は参照型のため `async Task` メソッドは呼び出しごとに
   Taskオブジェクト + ステートマシンのボックス化を伴う。`UniTask` は構造体ベースで
   ゼロアロケーションを実現している。ゲームプレイ中に走る非同期処理では差が大きい。

2. **`Task.Delay` が `Time.timeScale` を無視する**。システムタイマーによる実時間待機のため、
   ポーズ中（`timeScale = 0`）でもシナリオが進行してしまう。

   ```csharp
   // 2.Application/OutGame/Scenario/ScenarioUsecase.cs:178,188
   await Task.Delay(_settingsRepository.PausePollInterval, ct);
   await Task.Delay(delay, ct);

   // 3.Adaptor/OutGame/Scenario/TextEventHandler.cs:44,57
   await Task.Delay(pauseDelay, ct);
   await Task.Delay(delay, ct);
   ```

3. **`Task.Yield()` の復帰タイミングが制御できない**。UniTaskなら
   `UniTask.Yield(PlayerLoopTiming.LastPostLateUpdate)` のようにフレーム内の位置を指定できる。

   ```csharp
   // 4.View/InGame/Player/PlayerView.cs:606 — 毎フレームのロックオン追従回転ループ内
   await Task.Yield();

   // 5.InfraStructure/OutGame/Scenario/ScenarioRepository.cs:454
   await Task.Yield();
   ```

### 特に問題のある箇所

**キャンセル不能なタイムアウト**

```csharp
// 4.View/OutGame/Screen/ScreenViewBase.cs:125
Task.Delay(TimeSpan.FromSeconds(TRANSITION_TIMEOUT_SEC), CancellationToken.None));

// 4.View/OutGame/StageSelect/StageNodeConnectionView.cs:69
Task.Delay(TimeSpan.FromSeconds(ANIMATION_TIMEOUT_SEC), CancellationToken.None));
```

`CancellationToken.None` を明示的に渡しているため、**画面遷移が先に完了しても
タイマーは満了まで生き続ける**。`UniTask.Delay(..., cancellationToken: destroyCancellationToken)` にすれば
オブジェクト破棄で確実に片付く。

**CancellationToken未指定**

```csharp
// 4.View/InGame/Enemy/EnemySpawnPositionSearcher.cs:45
await Task.Delay(_searchDelay);   // トークンなし
```

**修正方針**: 一括置換ではなく、影響の大きい順に移行する。
1. ゲームプレイ中に走るもの（`PlayerView`、`EnemySpawnPositionSearcher`）
2. `timeScale` の影響を受けるべきもの（`ScenarioUsecase`、`TextEventHandler`）
3. `CancellationToken.None` を渡している2箇所
4. 残りのOutGame系

## 【設計指摘】ReactivePropertyが使える場面でC# eventを使っている

R3の `ReactiveProperty` は以下で適切に使われている。

```csharp
// 3.Adaptor/InGame/Music/MusicSyncState.cs:90-102
// ReactivePropertyは同値を弾くため、拍が変わったフレームだけ購読者へ通知される。
private readonly ReactiveProperty<int> _currentBeat = new(0);
```

```csharp
// 4.View/InGame/UI/HUDEnemyHealthViewModel.cs:65-68
private readonly ReactiveProperty<Vector2> _uiPosition = new();
private readonly ReactiveProperty<float> _maxHealth = new();
private readonly ReactiveProperty<float> _currentHealth = new();
private readonly ReactiveProperty<LockOnDisplayState> _displayState = new();
```

購読側も `.Subscribe(...).RegisterTo(destroyCancellationToken)` で自動解除しており模範的。

一方、**同じ「値が変わったら通知」という用途で素のC# `event` を使っている箇所**が多数ある。
これらは [01. イベント購読解除漏れ](01_イベント購読解除漏れ.md) で挙げた解除漏れの温床でもある。

| 場所 | 現状 | ReactiveProperty化の利点 |
| --- | --- | --- |
| [PlayerInitializer.cs:264-277](../../Assets/Scripts/Runtime/6.Composition/InGame/Player/PlayerInitializer.cs) | `OnDodgeStarted` / `OnDodgeEnded` イベント | `RegisterTo` で解除漏れが構造的に消える |
| [EnemyLifeCycle.cs:176-179](../../Assets/Scripts/Runtime/6.Composition/InGame/Enemy/EnemyLifeCycle.cs) | `On1BeatBefore` / `On2BeatBefore` / `OnAttack` | 同上 |
| [HUDEnemyHealthInitializer.cs:59](../../Assets/Scripts/Runtime/6.Composition/InGame/UI/HUDEnemyHealthInitializer.cs) | `OnUpdate` イベント | 同上 |

**判断基準**: 「状態の変化」は `ReactiveProperty`、「一度きりの出来事（発火）」は
`Observable` / `Subject` または素のeventでよい。拍タイミング通知（`On1BeatBefore` 等）は
後者に近いが、`RegisterTo` による自動解除の恩恵は同じく得られる。

## 【設計指摘】LitMotionが使える手書きトゥイーンが残っている

LitMotionは `ACLikeRhythmGuideView` や `HUDEnemyHealthView` で高度に活用されている
（`LSequence` による複合モーション、`MotionScheduler.UpdateIgnoreTimeScale` の指定など）。

一方、以下は手書きのトゥイーン状態機械になっている。

**場所**: [ScenarioView.cs:225-247](../../Assets/Scripts/Runtime/4.View/OutGame/Scenario/ScenarioView.cs)

```csharp
_time += Time.deltaTime;
...
if (_duration <= 0f) { _canvasGroup.alpha = _end; _onFade = false; return; }

float t = Mathf.Clamp01(_time / _duration);
_canvasGroup.alpha = Mathf.Lerp(_start, _end, t);
if (t >= 1f) { _onFade = false; }
```

`_onFade` / `_time` / `_duration` / `_start` / `_end` という5つの状態フィールドと
毎フレームの `Update` 分岐で、LitMotionなら1行で書けることを再実装している。

```csharp
LMotion.Create(_start, _end, _duration).BindToAlpha(_canvasGroup);
```

**修正方針**: `MotionHandle` を保持して `TryCancel` すればフェード中断も表現できる。
既に `ACLikeRhythmGuideView` がこのパターンを実践しているので、そのまま横展開できる。

## 【設計指摘】ZString / ObservableCollections が完全未使用

**ZString** (`com.cysharp.zstring 2.6.0`) — 導入済みだが利用ゼロ。
文字列補間付き `Debug.Log` が226箇所ある（[12. ログ運用](12_ログ運用とビルド影響.md) 参照）ほか、
UI向けの数値→文字列変換が `StageResultViewModel` などにある。
毎フレーム更新するテキスト（タイマー、コンボ数など）があれば `ZString.Format` の効果が大きい。

**ObservableCollections** (`com.cysharp.observablecollections 1.1.3`) — 導入済みだが利用ゼロ。
[SkillBuildScreenView.cs:87](../../Assets/Scripts/Runtime/4.View/OutGame/Screen/SkillBuildScreenView.cs) の
`OnSkillListChanged` イベントや、[SkillListView.cs](../../Assets/Scripts/Runtime/4.View/OutGame/SkillBuild/SkillListView.cs) の
リスト再構築がこのライブラリの想定用途に合致する。

**判断**: 使わないなら `manifest.json` から外すべき。導入済みライブラリが未使用のまま残ると、
ビルドサイズと「何が標準手段なのか」の判断コストを増やす。

## 【要検証】フレームレート依存の補間が1箇所だけ混在

補間の書き方が本プロジェクトでは2種類ある。

**フレームレート非依存（正しい）** — 3箇所

```csharp
// 4.View/InGame/Camera/Calculation/CameraLockOnRotationCalculator.cs:39
cameraBoneRotation = Quaternion.Slerp(cameraBoneRotation, target, 1f - Mathf.Exp(-effectiveSpeed * context.DeltaTime));

// 4.View/InGame/Camera/Calculation/CameraLookAtRotationCalculator.cs:56-58
float interpolationRatio = 1f - Mathf.Exp(-Mathf.Max(0f, _parameter.LockOnRotationSpeed) * Mathf.Max(0f, context.DeltaTime));
rotation = Quaternion.Slerp(rotation, target, interpolationRatio);

// 4.View/InGame/Player/PlayerView.cs:597
float t = 1f - Mathf.Exp(-Mathf.Max(0f, speed) * Time.deltaTime);
```

**フレームレート依存（要修正）** — 1箇所

```csharp
// 4.View/InGame/Camera/Calculation/CameraFollowCalculator.cs:36
cameraCenterPosition = Vector3.Lerp(cameraCenterPosition, targetFollowCenterOffset, _parameter.FollowLerpSpeed * context.DeltaTime);
```

`Lerp(a, b, speed * deltaTime)` は指数減衰の近似だが、**フレームレートによって
収束速度が変わる**。60fpsと144fpsでカメラの追従感が変わり、
さらに `speed * deltaTime > 1` になるフレーム落ち時にはオーバーシュートする。

同じ `Calculation/` ディレクトリ内で他3箇所は正しく書かれているため、
このファイルだけ書き換えれば揃う。

```csharp
float t = 1f - Mathf.Exp(-_parameter.FollowLerpSpeed * context.DeltaTime);
cameraCenterPosition = Vector3.Lerp(cameraCenterPosition, targetFollowCenterOffset, t);
```
