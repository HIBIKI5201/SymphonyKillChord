**修正方針**: `CatalogRepositoryBase<TId, TDefinition, TEntry>` が既に良い抽象化として
存在するので、SkillTree系3リポジトリもこれに寄せる。難しければ最低限
`Array.Find` に置き換えるだけでも各15行 → 1行に圧縮できる。

## 【確定】値オブジェクト12種がIEquatable<T>を宣言しておらず比較のたびにボクシングする

**場所**: `1.Domain/InGame/Character/` の値オブジェクト群

`DodgeCooldown` を例に見ると、**型付きの `Equals` は実装されているのに
インターフェース宣言だけが抜けている**。

```csharp
// 1.Domain/InGame/Character/DodgeCooldown.cs:8
public readonly struct DodgeCooldown          // ← : IEquatable<DodgeCooldown> がない
{
    ...
    public override bool Equals(object obj)   // line 52
        => obj is DodgeCooldown dodgeCooldown && dodgeCooldown.Value == Value;

    public bool Equals(DodgeCooldown other)   // line 60 ← 実装済み。だが誰からも使われない
        => other.Value == Value;

    public override int GetHashCode() => Value.GetHashCode();   // line 68
}
```

`IEquatable<T>` を宣言していないと、`EqualityComparer<T>.Default` は型付きの
`Equals(T)` を発見できず `ObjectEqualityComparer<T>` にフォールバックする。
その結果、`Dictionary` / `HashSet` / `List.Contains` / `Array.IndexOf` / LINQ の
**比較1回ごとに `Equals(object)` が呼ばれ、引数がボクシングされる**。

型付き `Equals` を書いた作者の意図は明らかに「ボクシングを避ける」ことであり、
宣言漏れによってその意図が実現していない状態。

### 実装状況（`1.Domain/InGame/Character/`）

| 状態 | 型 |
| --- | --- |
| **宣言済み** | `Health`、`CharacterDefinitionId` |
| **未宣言** | `AttackCooldown`、`AttackPower`、`AttackRangeMax`、`AttackRangeMin`、`AttackRotationSpeed`、`CharacterName`、`CriticalChance`、`CriticalMultiplier`、`DodgeCooldown`、`DodgeDuration`、`DodgeSpeed`、`MoveSpeed` |

`1.Domain` 全体では struct を含む64ファイル中、`IEquatable` の記載があるのは24ファイル。

**修正方針**: 各構造体の宣言に `: IEquatable<T>` を追加するだけでよい。
`using System;` は既にインポートされており、`Equals(T)` も実装済みのため、
**追記は1行のみで挙動は一切変わらない**（正しく速くなるだけ）。

```csharp
public readonly struct DodgeCooldown : IEquatable<DodgeCooldown>
```

なお `Dictionary` のキーとして使われている型は優先度が高い。

- [StageTree.cs:271](../../Assets/Scripts/Runtime/1.Domain/OutGame/StageSelect/StageTree.cs) — `Dictionary<StageId, ...>`
- [ReticleHudView.cs:127](../../Assets/Scripts/Runtime/4.View/InGame/Reticle/ReticleHudView.cs) — `Dictionary<Guid, ReticleMarkerView>`（`Guid` は BCL 実装のため問題なし）

`SkillNodeId` / `StageId` についても同様の確認が必要。

```bash
grep -rLn "IEquatable" --include=*.cs Assets/Scripts/Runtime/1.Domain | xargs grep -ln "readonly struct"
```

## 【設計指摘】配列とListの使い分け方針が不明確

`ACLikeRhythmGuideView` は `RectTransform[]` / `Image[]` / `MotionHandle[]` / `int[]` を
`Array.Empty<T>()` で初期化しつつ、`CacheZones` で毎回 `new float[zones.Count]` を確保している
（[ACLikeRhythmGuideView.cs:558-560](../../Assets/Scripts/Runtime/4.View/InGame/Music/ACLikeRhythmGuideView.cs)）。

ゾーン数が変わらないなら再確保は不要であり、`List<T>` にして `Clear` + `Add` するか、
容量が同じなら既存配列を再利用すべき。現状はゾーン定義が変わったときのみ
呼ばれる想定だが、[05](05_不必要な繰り返し処理.md) の指摘のとおり
実際には毎フレーム `ConfigureZones` が呼ばれている（`NeedsRebuild` でほぼ弾かれるが）。

## 【設計指摘】ジャストタイミング判定が線形探索

**場所**: [ACLikeRhythmGuideView.cs:81-89](../../Assets/Scripts/Runtime/4.View/InGame/Music/ACLikeRhythmGuideView.cs)

```csharp
bool isJustTiming = false;
for (int i = 0; i < _justTimingBeatBoxIndex.Length; i++)
{
    if (activeIndex == _justTimingBeatBoxIndex[i]) { isJustTiming = true; break; }
}
```

`_justTimingBeatBoxIndex` の要素数はゾーン数（数個程度）なので線形探索で十分だが、
ブロック単位の `bool[] _isJustTimingBlock` を `InitBeatGUI` で事前構築すれば
配列1回引きになる。[05](05_不必要な繰り返し処理.md) の
`GetBeatSectionIndex` 事前計算と同時に対応するのが効率的。

## 【設計指摘】値オブジェクト13種の構造重複

`1.Domain/InGame/Character/` に `DodgeCooldown` / `DodgeDuration` / `AttackPower` /
`AttackRangeMax` / `AttackRangeMin` / `AttackRotationSpeed` / `CriticalChance` /
`CriticalMultiplier` / `DodgeSpeed` / `Health` / `MoveSpeed` / `AttackCooldown` など
**float1個をラップした構造体が13種**存在する。

`DodgeCooldown.cs` と `DodgeDuration.cs`（各73行）は型名以外が完全に同一。
データ構造としては正しい設計（プリミティブ型の混同を型で防ぐ）だが、
定型コードの量が問題。詳細は [10. コード重複と過剰抽象化](10_コード重複と過剰抽象化.md) を参照。
