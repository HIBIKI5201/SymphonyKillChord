# 18. 命名一貫性と可読性

**最小驚きの原則**（Principle of Least Astonishment）に関わる指摘。
動作には影響しないが、**新規メンバーの学習コストと誤読のリスク**に直結する。

---

## 【確定】ディレクトリ名の綴り誤り

**場所**: `3.Adaptor/InGame/Animaiton/`

正しくは `Animation`。他の3レイヤーは正しく綴られている。

```
3.Adaptor/InGame/Animaiton      ← 誤り
4.View/InGame/Animation         ← 正しい
5.InfraStructure/InGame/Animation
6.Composition/InGame/Animation
```

**修正が容易な理由**: このディレクトリ内3ファイルの `namespace` は
すでに正しく `KillChord.Runtime.Adaptor.InGame.Animation` と書かれている。

```
3.Adaptor/InGame/Animaiton/ICharacterAnimationSignal.cs      → namespace ...InGame.Animation
3.Adaptor/InGame/Animaiton/ICharacterAnimationViewContext.cs → namespace ...InGame.Animation
3.Adaptor/InGame/Animaiton/ICharacterAnimationViewModel.cs   → namespace ...InGame.Animation
```

つまり**フォルダ名を変えるだけでコード修正はゼロ**。
Unityエディタ上でリネームすれば `.meta` のGUIDも保持される。

放置すると、`Animation` で検索したときにこのフォルダが引っかからず、
インターフェース定義を見落とす原因になる。

## 【確定】ファイル名の綴り誤り

**場所**: [AttackPilpelineAsset.cs](../../Assets/Scripts/Runtime/5.InfraStructure/InGame/Battle/AttackPilpelineAsset.cs)

正しくは `AttackPipelineAsset`。`Pipeline` が `Pilpeline` になっている。

関連する型は正しく綴られている。

```
1.Domain/InGame/Battle/IAttackPipeline.cs        ← 正しい
2.Application/InGame/Battle/AttackPipeline.cs    ← 正しい
5.InfraStructure/InGame/Battle/AttackPilpelineAsset.cs  ← 誤り
```

`AttackPipeline` で検索した際にこのアセットクラスだけ漏れるため、
攻撃パイプラインの設定箇所を追う際に見落とす。クラス名のリネームが必要なため
`Animaiton` フォルダより修正コストは高いが、影響範囲は限定的（このファイルと
それを参照する Composition 側のみ）。

## 【確定】Usecase と UseCase の混在

| 表記 | 件数 | 例 |

**新規追加分から `UseCase` に統一し、既存は機械的リネームを一度に行う**のが現実的。

## 【設計指摘】Controller という名前の濫用

`3.Adaptor` のサフィックス分布。

| サフィックス | 件数 |
| --- | --- |
| **Controller** | **41** |
| Presenter | 25 |
| State | 13 |
| Facade | 5 |
| Service | 1 |
| Applicator / Sequencer / Gate | 各1 |

`Controller` が全体の半分近くを占め、実際の役割は多岐にわたる。

| クラス | 実際にしていること | 適した名前 |
| --- | --- | --- |
| `ScreenController` | UseCaseへの委譲 | Controller（適切） |
| `EnemyAIController` | AI状態機械の駆動 | `EnemyAICoordinator` |
| `PlayerAttackController` | 攻撃判定・ダメージ算出 | `AttackPipeline` |
| `SkillExecutionController` | 失敗ポリシーの適用 | `SkillExecutionPolicy` |
| `MissionProgressRecorderController` | 7イベントを購読して記録 | `MissionProgressRecorder` |

`Applicator` / `Sequencer` / `Gate` が各1件しかないのは、
**それらが役割を正確に表す名前として孤立している**ことを示す。
つまり命名の語彙は存在するのに、多くが `Controller` に吸収されてしまっている。

**修正方針**: プロジェクト用語集（`Docs/用語集_追加候補.md` が既に存在）に
サフィックスの定義を追加する。既存クラスの改名は影響範囲が大きいため、
まず新規クラスから適用する。

## 【設計指摘】ログメッセージの言語・書式が不統一

同一ファイル内で日本語と英語が混在している。

```csharp
// 4.View/InGame/Enemy/EnemyRaycastDetectView.cs
Debug.LogError("[EnemyRaycastDetectView] Target transform is null.");           // 英語・context無し
Debug.LogWarning("[EnemyRaycastDetectView] Attack warning decal is not assigned. ...", this); // 英語・context有り
Debug.LogError("_beatColor の長さが判定ゾーン数より少ないです。", this);          // 日本語・プレフィックス無し
```

書式のバリエーション:
- プレフィックス: `[ClassName]` / `[{nameof(ClassName)}]` / なし
- 言語: 日本語 / 英語
- 第2引数 `context`: あり / なし

詳細は [12. ログ運用とビルド影響](12_ログ運用とビルド影響.md) 参照。

## 良い命名として維持すべき点

  [TargetingSystem.cs:251-258](../../Assets/Scripts/Runtime/4.View/InGame/Target/TargetingSystem.cs) が模範

- **`readonly` の徹底** — 依存フィールドはほぼ全て `readonly` になっている
- **XMLドキュメントコメント** — `<summary>` / `<param>` の記述率が非常に高い
- **値オブジェクトの命名** — `DodgeCooldown` / `AttackRangeMax` など、
  単位や役割が名前から読み取れる
- **レイヤー番号プレフィックス**（`0.Utility` 〜 `6.Composition`）—
  依存方向がディレクトリ順で一目で分かる優れた工夫
