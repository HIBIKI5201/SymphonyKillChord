# 05. 不必要な繰り返し処理

同じ結果を何度も計算している箇所、毎フレーム実行する必要のない処理、
ループの入れ子で計算量が跳ね上がっている箇所を対象とする。

---

## 【確定】毎フレーム判定ゾーンを再構築し、受け手側で「変わっていない」と判定している

**場所**: [RhythmGuidePresenter.cs:41-52](../../Assets/Scripts/Runtime/3.Adaptor/InGame/Music/RhythmGuidePresenter.cs)
と [ACLikeRhythmGuideView.cs:42-51, 519-568](../../Assets/Scripts/Runtime/4.View/InGame/Music/ACLikeRhythmGuideView.cs)

Presenter側は毎フレーム、判定ゾーンのリストを作り直している。

```csharp
_zones.Clear();
foreach (RhythmJudgmentRange range in ...JudgmentRanges)
{
    _zones.Add(new RhythmGuideZoneDto((int)range.BeatType, range.StartNormalized, range.EndNormalized));
}
```

View側は受け取ったそれを毎フレーム、既存キャッシュと全要素比較して
「変わっていない」と判定して捨てている。

```csharp
public void ConfigureZones(IReadOnlyList<RhythmGuideZoneDto> zones)
{
    if (!NeedsRebuild(zones)) { return; }   // ほぼ常にここでreturn
    CacheZones(zones);
    RebuildBeatRectTransforms();
}
```

`NeedsRebuild` は全ゾーンに対し `Mathf.Approximately` を2回 + `int` 比較を行う。

`RhythmJudgmentDefinition` は楽曲データであり、**通常はステージ中に変化しない**。
つまり「変化しないデータを毎フレーム作り直し、毎フレーム変化していないことを確認する」
という二重の無駄が生じている。

**修正方針**: ゾーン定義の変更を明示的なイベント（楽曲切り替え時など）で通知する。
`RhythmGuideDto` からは `Zones` を外し、`SetBeatsOffset` / `SetAlpha` のみ毎フレーム更新する。
これだけで [04](04_GCAllocとメモリリーク.md) の列挙子ボクシングも同時に解消する。

## 【確定】ビート色の区間判定を毎回線形探索している

**場所**: [ACLikeRhythmGuideView.cs:666-684](../../Assets/Scripts/Runtime/4.View/InGame/Music/ACLikeRhythmGuideView.cs)

```csharp
private int GetBeatSectionIndex(int blockIndex, float scale, float beatWidth)
{
    float position = (blockIndex * beatWidth) / scale;

    for (int i = 0; i < _zoneStarts.Length; i++)
    {
        float start = (_zoneStarts[i] / GUIDE_LENGTH_IN_BARS) * _displayLength;   // 毎回除算+乗算
        float end   = (_zoneEnds[i]   / GUIDE_LENGTH_IN_BARS) * _displayLength;
        if (position >= start && position < end) { return i; }
    }
    return _zoneStarts.Length - 1;
}
```

問題は2点。

1. **`start` / `end` の変換計算がループのたびに再実行される**。
   `_zoneStarts` / `_zoneEnds` / `GUIDE_LENGTH_IN_BARS` / `_displayLength` は
   すべて `CacheZones` の時点で確定するため、変換済み配列をキャッシュすべき。

2. **呼び出し箇所が2つあり、片方はループ内**。
   - [line 142](../../Assets/Scripts/Runtime/4.View/InGame/Music/ACLikeRhythmGuideView.cs) `SetBeatAnimation` — ビート切り替わりのたび
   - [line 620](../../Assets/Scripts/Runtime/4.View/InGame/Music/ACLikeRhythmGuideView.cs) `InitBeatGUI` — 全ブロック生成ループ内（O(ブロック数 × ゾーン数)）

**修正方針**: `CacheZones` で変換済みの `_zoneStartsInGauge[]` / `_zoneEndsInGauge[]` を作る。
さらにブロックごとの色インデックスは `InitBeatGUI` で `_blockSectionIndex[]` として
事前計算しておけば、`SetBeatAnimation` は配列引きだけで済む。

## 【要検証】NavMesh探索が候補数ぶんのパス計算とRaycastを行う

**場所**: [NearestAttackPositionSearchView.cs:43-88](../../Assets/Scripts/Runtime/4.View/InGame/Enemy/NearestAttackPositionSearchView.cs)

1回の探索で、`_samplingCount` 個の候補それぞれに対して以下を実行する。

| 処理 | コスト |
| --- | --- |
| `NavMesh.SamplePosition` | NavMesh空間探索 |
| `_agent.CalculatePath` | フルパス計算 |
| コーナー距離の合計ループ | パス長に比例（+ GC Alloc、[04](04_GCAllocとメモリリーク.md) 参照） |
| `_raycastView.CheckCanRaycastHitTarget` | `Physics.RaycastNonAlloc` |

これが `_searchInterval` 秒ごと、**敵1体ごとに**走る。敵が同時に多数存在する場合、
`_samplingCount × 敵数` 回のパス計算が同一フレームに集中しうる。

改善余地として、`_raycastView.CheckCanRaycastHitTarget` の判定順序がある。
現在はパス長が最短を更新した候補についてのみRaycastしているため
（line 75-82のネスト）、この点は既に最適化されている。良い実装。

一方、**全候補について無条件に `CalculatePath` を実行している**点は削減できる。
候補位置と敵位置の直線距離が現在の最短パス長を超えている場合、
パスがそれより短くなることはないため、事前に枝刈りできる。

**修正方針**:
1. `Vector3.Distance` による事前枝刈りを入れる（安価な下界による除外）
2. 敵ごとの探索タイミングをずらす（`_timer` の初期値に個体差を持たせる）ことで
   同一フレームへの集中を避ける

なお `_timer` の管理のためだけに `Update()` を定義している（line 91-94）が、
`FindNearestAttackPosition` の呼び出し側で経過時間を渡すか `Time.time` との差分で
判定すれば `Update` 自体が不要になる。敵の数だけUnityメッセージが減る。

## 【設計指摘】UpdateがイベントをInvokeするだけの中継になっている

以下のViewは `Update` / `LateUpdate` の中身がイベント発火のみである。

```csharp
// 4.View/InGame/Music/ACLikeRhythmGuideView.cs:231-234
private void Update() { OnUpdate?.Invoke(); }

// 4.View/InGame/UI/HUDEnemyHealthView.cs:99-102
private void LateUpdate() { OnUpdate?.Invoke(); }
```

これはMonoBehaviourでないViewModel/Presenterを毎フレーム駆動するための
意図的な設計であり、**方針としては妥当**。ただしコストとして
「Unityメッセージのディスパッチ + デリゲート呼び出し」が二段になる。

同じ役割を果たす仕組みが3種類混在している点が指摘事項。

| 方式 | 例 |
| --- | --- |
| Viewが `OnUpdate` イベントを公開し外部が購読 | `ACLikeRhythmGuideView`、`HUDEnemyHealthView` |
| View自身が `Update` 内でPresenterを呼ぶ | [RhythmGuideUpdateView.cs:47-62](../../Assets/Scripts/Runtime/4.View/InGame/Music/RhythmGuideUpdateView.cs)、[ReticleHudView.cs:40-49](../../Assets/Scripts/Runtime/4.View/InGame/Reticle/ReticleHudView.cs) |
| `IGameplayControllable` + `Tick(deltaTime)` | [MissionLoopView.cs:30-38](../../Assets/Scripts/Runtime/4.View/InGame/Mission/MissionLoopView.cs) |

**修正方針**: 毎フレーム駆動を一箇所に集約する（`InGamePlayDirector` が
`IGameplayControllable` を保持しているので、そこに `ITickable` 相当を追加する）。
Unityメッセージの総数が減り、実行順序も制御しやすくなる。

## 【設計指摘】ループ内でのContains（O(n²)）

**場所**: [SkillTreeController.cs:102-116](../../Assets/Scripts/Runtime/3.Adaptor/OutGame/SkillTree/SkillTreeController.cs)

```csharp
foreach (SkillNodeEntity entity in _nodesOnPath)
{
    ...
    if (!_skillTreeStatusEntity.UnlockedNodes.Contains(entity.SkillNodeIdVO))   // O(n)
    {
        _skillTreeStatusEntity.AddUnlockedNode(entity.SkillNodeIdVO);
    }
```

`UnlockedNodes` がリストであれば全体で O(パス長 × 解放済みノード数) になる。
スキル解放は頻繁な操作ではないため実害は小さいが、解放済みノードが増えるほど劣化する。

同様のパターン: [SkillTreeInitializer.cs:376](../../Assets/Scripts/Runtime/6.Composition/OutGame/SkillTree/SkillTreeInitializer.cs)、
[StageTreeAsset.cs:272-273](../../Assets/Scripts/Runtime/5.InfraStructure/OutGame/StageSelect/StageTreeAsset.cs)。
