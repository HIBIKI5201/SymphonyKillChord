## 【確定】async void が25箇所あり例外が握り潰される

`async void` は `async Task` と違い、**内部で発生した例外が呼び出し元へ伝播しない**。
UnityではUnobservedな例外としてログに出る場合もあるが、
呼び出し元での `try/catch` は機能せず、処理が途中で止まったことも検知できない。

### 一覧

レイヤー別の内訳。**全25件の完全な一覧は [付録A](#付録a-async-void-全25件) を参照**。

| レイヤー | 件数 |
| --- | --- |
| 4.View | 6 |
| 6.Composition | 19 |

### 特に危険な箇所

**`async void Start()`（4箇所）** — シーン起動の初期化そのものが `async void`。
初期化中に例外が出ると、**シーンが半分初期化された状態で静かに停止する**。
`IngameComposition.cs:28` は try/catch/finally を持っているため被害は限定的だが、
その catch が握った例外を上位へ伝える手段がない。

**UI操作ハンドラ（`OnCompleteButtonClicked` 等）** — ボタン連打で
多重実行される可能性がある。`async void` は実行中かどうかを呼び出し側が
知る術がないため、多重実行ガードは自前フラグに頼ることになる。

**修正方針**: `async UniTaskVoid` + `.Forget()` へ移行する。
UniTaskVoid は例外を `UniTaskScheduler.UnobservedTaskException` に確実に流すため、
グローバルハンドラで一括捕捉できる。

```csharp
private void Start()
{
    InitializeAsync(destroyCancellationToken).Forget();
}

private async UniTaskVoid InitializeAsync(CancellationToken ct) { ... }
```

現状 `.Forget()` はプロジェクト全体で
[AttackIntervalEvaluator.cs:39](../../Assets/Scripts/Runtime/2.Application/InGame/Battle/AttackIntervalEvaluator.cs) の1箇所のみ。

## 【確定】CancellationToken未指定の待機

| 場所 | コード | 影響 |
| --- | --- | --- |
| [AttackIntervalEvaluator.cs:53](../../Assets/Scripts/Runtime/2.Application/InGame/Battle/AttackIntervalEvaluator.cs) | `await UniTask.Delay((int)(duration * 1000f));` | シーン破棄後もEntityを書き換える |
| [EnemySpawnPositionSearcher.cs:45](../../Assets/Scripts/Runtime/4.View/InGame/Enemy/EnemySpawnPositionSearcher.cs) | `await Task.Delay(_searchDelay);` | 敵破棄後も継続 |
| [ScreenViewBase.cs:125](../../Assets/Scripts/Runtime/4.View/OutGame/Screen/ScreenViewBase.cs) | `Task.Delay(..., CancellationToken.None)` | **明示的に**キャンセル不能 |
| [StageNodeConnectionView.cs:69](../../Assets/Scripts/Runtime/4.View/OutGame/StageSelect/StageNodeConnectionView.cs) | `Task.Delay(..., CancellationToken.None)` | 同上 |

後者2つは `Task.WhenAny` によるタイムアウト実装と思われるが、
`CancellationToken.None` を渡しているため**本処理が先に完了してもタイマーは満了まで生存する**。
`ANIMATION_TIMEOUT_SEC` / `TRANSITION_TIMEOUT_SEC` の長さぶん、
使われないタイマーが積み上がる。

**修正方針**: `CancellationTokenSource` を作り、本処理完了時に `Cancel()` する。
UniTaskなら `UniTask.WhenAny` + `token` で自然に書ける。

なお、CancellationTokenを正しく使っている箇所も多数ある。

```csharp
// 2.Application/OutGame/Scenario/ScenarioUsecase.cs:178,188
await Task.Delay(_settingsRepository.PausePollInterval, ct);

// 3.Adaptor/OutGame/Scenario/TextEventHandler.cs:44,57
await Task.Delay(pauseDelay, ct);
```

R3側も `.Subscribe(...).RegisterTo(destroyCancellationToken)` で統一されており、
**トークンを流す文化自体は根付いている**。上記4箇所が例外的に漏れている状態。

## 【要検証】ContinueWithによるTPL的な例外処理

**場所**: [SkillTreeController.cs:119-123](../../Assets/Scripts/Runtime/3.Adaptor/OutGame/SkillTree/SkillTreeController.cs)

```csharp
_skillTreeService
    .SaveSkillUnlockData(...)
    .ContinueWith(
        t => Debug.LogError($"[SkillTreeController] スキル解放データ保存失敗: {t.Exception}"),
        TaskContinuationOptions.OnlyOnFaulted);
```

問題点が3つある。

1. **`ContinueWith` は既定でThreadPool上で実行される**。
   `TaskScheduler.FromCurrentSynchronizationContext()` を指定していないため、
   `Debug.LogError` がメインスレッド外から呼ばれる可能性がある。

2. **保存の完了を誰も待っていない**。失敗時にログは出るが、
   ユーザーには成功したように見え、スキルポイントは既に消費済み
   （[02. Null参照リスク](02_Null参照リスクとアサート漏れ.md) の指摘と複合すると被害が大きい）。

3. **プロジェクト全体で `ContinueWith` はここ1箇所のみ**。他は `await` を使っており、
   この箇所だけTPLスタイルになっている。

**修正方針**: `async` メソッドに切り出して `try/catch` で書き直す。

## 【設計指摘】UniTaskへの移行が中断されている

`com.cysharp.unitask` が導入済みにもかかわらず利用が1ファイルに留まっている件は
[07. ライブラリ未活用](07_ライブラリ未活用.md) に詳述した。

非同期処理の観点から重要なのは、**`Task` と `UniTask` が混在すると
`timeScale` の扱いが不統一になる**点。

| API | timeScaleの影響 |
| --- | --- |
| `Task.Delay` | 受けない（実時間） |
| `UniTask.Delay`（既定 `DelayType.DeltaTime`） | 受ける |
| `UniTask.Delay(..., DelayType.UnscaledDeltaTime)` | 受けない |

現在、シナリオ再生は `Task.Delay`、攻撃硬直は `UniTask.Delay` を使っている。
ポーズ機能を実装した際、**シナリオは進行し続け、攻撃硬直は止まる**という
一貫性のない挙動になる。

**修正方針**: UniTaskへ統一した上で、`DelayType` をシステムごとに明示的に決める。
リズムゲームである本作では、音楽同期系は `Realtime`、
ゲームプレイ系は `DeltaTime` という切り分けが自然と思われる。

---

## 【設計指摘】コルーチン不使用は良い判断

`StartCoroutine` / `IEnumerator` による非同期は
[PriorityQueue.cs:622](../../Assets/Scripts/Runtime/0.Utility/Collections/PriorityQueue.cs) の
`IEnumerable` 実装（列挙のための正当な用途）以外に存在しない。

コルーチンは例外処理・戻り値・キャンセルのいずれも扱いにくいため、
async/awaitに統一されているのは適切な判断である。この方針は維持すべき。
