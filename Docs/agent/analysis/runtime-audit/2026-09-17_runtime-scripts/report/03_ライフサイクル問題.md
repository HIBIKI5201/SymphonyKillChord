# 03. ライフサイクル問題

MonoBehaviourの生成・破棄、非同期処理と破棄タイミングの競合、プール再利用時の
状態リセットなど、オブジェクト寿命に関わる指摘。

---

## 【確定】シーン破棄後も非同期処理が継続する

**場所**: [AttackIntervalEvaluator.cs:50-60](../../Assets/Scripts/Runtime/2.Application/InGame/Battle/AttackIntervalEvaluator.cs)

```csharp
private async UniTaskVoid EvaluateAttackIntervalAsync(AttackInterval duration, int attackId)
{
    _attackIntervalEntity.UpdateAttackState(true);
    await UniTask.Delay((int)(duration * 1000f));   // CancellationToken 未指定

    if (attackId == _currentIntervalId)
    {
        _attackIntervalEntity.UpdateAttackState(false);
    }
}
```

`CancellationToken` を渡していないため、**シーンアンロードやゲーム終了後も
PlayerLoopに残り続け、待機完了後に `_attackIntervalEntity` を書き換える**。

`_currentIntervalId` によるID照合で古い呼び出しの上書きは防いでいる
（この設計自体は良い）が、これは「同一インスタンス内での競合」への対策であって
「インスタンス自体の寿命超過」は防げない。

副次的な問題として、`UniTask.Delay` の既定は `DelayType.DeltaTime`（`Time.timeScale` 依存）である。
ポーズメニューで `timeScale = 0` にした場合、攻撃硬直が永久に解けない。
リズムゲームである本作では意図的かもしれないが、明示されていない。

**修正方針**: 呼び出し側から `CancellationToken` を受け取り、`UniTask.Delay(ms, cancellationToken: token)` とする。
`2.Application` 層はMonoBehaviourではないため、`EnemyLifeCycle` / `PlayerInitializer` 側の
`destroyCancellationToken` を初期化時に渡す形が素直。

## 【確定】1つのMonoBehaviourがUpdate/FixedUpdate/LateUpdateを全て定義している

**場所**: [CameraSystemView.cs:223-253](../../Assets/Scripts/Runtime/4.View/InGame/Camera/CameraSystemView.cs)

```csharp
private void FixedUpdate() { ...; if (_updateMode != UpdateModeEnum.FixedUpdate) { return; } Tick(...); }
private void Update()      { ...; if (_updateMode != UpdateModeEnum.Update)      { return; } Tick(...); }
private void LateUpdate()  { ...; if (_updateMode != UpdateModeEnum.LateUpdate)  { return; } Tick(...); }
```

`_updateMode` はSerializeFieldで**実行中に切り替わらない**にもかかわらず、
3つのUnityメッセージすべてが定義されているため、Unityは毎フレーム3回の
マネージド↔ネイティブ境界越えを行う。実際に処理するのは常に1つだけ。

Unityは「メソッドが存在するかどうか」でメッセージ登録を決めるため、
中身が即returnでもディスパッチのコストは発生する。

**修正方針**: 3つのタイミングを別コンポーネントに分離し、`Initialize` 時に
`_updateMode` に応じて不要なものを `enabled = false` にする。
あるいは、そもそも `UpdateModeEnum` が実運用で1つの値しか使われていないなら
選択肢自体を削除するのが最も単純。

## 【要検証】FixedUpdate内でTime.deltaTimeを使用

**場所**: [EnemyWaveTimerView.cs:62-81](../../Assets/Scripts/Runtime/4.View/InGame/Enemy/EnemyWaveTimerView.cs)

```csharp
private void FixedUpdate()
{
    if (_timerActive)
    {
        if (_waveTimer <= 0f) { ... }
        _waveTimer -= Time.deltaTime;   // FixedUpdate内なので fixedDeltaTime を使うべき
    }
}
```

Unityの仕様上、`FixedUpdate` 内の `Time.deltaTime` は `Time.fixedDeltaTime` を返すため
**動作は正しい**。ただし読み手に「フレーム時間で減算している」と誤読させるため、
意図を明示する意味で `Time.fixedDeltaTime` と書くべき。

より本質的には、**Waveタイマーに物理タイムステップを使う理由がない**。
`Update` + `Time.deltaTime` の方が自然で、`Time.fixedDeltaTime` の設定変更にも影響されない。

## 【設計指摘】破棄順序に暗黙依存したイベントクリア規約

複数のViewが `OnDestroy` でイベントをnull代入して購読者を一括切断している。

```csharp
// 4.View/InGame/Music/ACLikeRhythmGuideView.cs:238-242
private void OnDestroy()
{
    OnUpdate = null;
    OnStartGameplay = null;
    OnStopGameplay = null;
    ...
}
```

```csharp
// 4.View/InGame/UI/HUDEnemyHealthView.cs:103-107
private void OnDestroy()
{
    OnUpdate = null;
    _handle.TryCancel();
}
```

この規約自体は有効だが、**購読側（ViewModel / Initializer）が自力で解除しない前提**を
生んでいる（[01. イベント購読解除漏れ](01_イベント購読解除漏れ.md) 参照）。
Viewが先に破棄されなかったケースでは購読が残る。

**修正方針**: 「Viewは `OnDestroy` で公開eventをnullクリアする」を明文化した規約とするか、
購読側を `IDisposable` に統一するか、どちらかに寄せる。現状は両者が混在している。

## 【設計指摘】async voidが破棄タイミングと競合する

`async void` は25箇所ある（[11. 非同期処理の不純点](11_非同期処理の不純点.md) に詳述）。
うちMonoBehaviour上のものは破棄との競合リスクが高い。

代表例: [EnemyLifeCycle.cs:456-474](../../Assets/Scripts/Runtime/6.Composition/InGame/Enemy/EnemyLifeCycle.cs)

```csharp
private async void DieAsync()
{
    ...
    try
    {
        await PlayDeathAnimationAsync();
        Deactivate();                        // 破棄済みでも実行されうる
        _waveSpawnerState.OnEnemyDeath();
    }
    catch (OperationCanceledException) { }
}
```

`OperationCanceledException` を捕捉している点は良い（キャンセルが機能する設計を
意図している）。ただし `async void` のため、それ以外の例外は
呼び出し元に伝播せず `UnobservedTaskException` 相当として消える。

## 【設計指摘】プール返却時の線形探索と状態リセット

**場所**: [ParticleSystemPoolView.cs:24-32](../../Assets/Scripts/Runtime/4.View/InGame/Character/ParticleSystemPoolView.cs)

```csharp
ParticleSystem particleSystem = _particleSystemPool.Get();
PrepareInstanceForPlayback(particleSystem);
particleSystem.Play();

if (!_activeParticleSystems.Contains(particleSystem))   // 常に false のはず
{
    _activeParticleSystems.Add(particleSystem);
}
```

`_particleSystemPool.Get()` が返すインスタンスは定義上 `_activeParticleSystems` に
含まれていない（`ReleaseInstance` で必ず `Remove` してから `Release` している）。
したがって `Contains`（O(n)の線形探索）は**常に false を返す無駄な防御**である。

`UnityEngine.Pool.ObjectPool` を `collectionCheck: true`（line 95の第5引数）で
生成しているため、二重Releaseはプール側が例外で検出する。二重の防御になっている。

**修正方針**: `Contains` チェックを削除して無条件 `Add` にする。
なお、このクラスは `ObjectPool<T>` を正しく使っており全体としては良い実装。
