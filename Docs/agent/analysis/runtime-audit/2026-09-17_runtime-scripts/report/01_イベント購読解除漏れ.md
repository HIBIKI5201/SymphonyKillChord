# 01. イベント購読解除漏れ

`+=` と `-=` をファイル単位で機械的に突き合わせ、差分のあるファイルを個別に精査した。

## 調査サマリ

| 分類 | ファイル数 |
| --- | --- |
| 購読(`+=`)があり解除(`-=`)が一切ない | 3 |
| `+=` が `-=` より多い（部分的解除漏れ） | 2 |
| 購読・解除が完全に対応 | 約30 |

R3の `.Subscribe(...).RegisterTo(destroyCancellationToken)` を使っている箇所は
すべて自動解除されており問題ない。以下は素の C# `event` に関する指摘。

---

## 【確定・最優先】OnDestroyの早期returnで静的EventBusの解除がスキップされる

**場所**: [CameraSystemView.cs:258-274](../../Assets/Scripts/Runtime/4.View/InGame/Camera/CameraSystemView.cs)

```csharp
private void OnDestroy()
{
    if (_inputView == null) { return; }   // ← ここで抜けると以下が全て実行されない

    // ... 入力イベントの解除 ...
    EventBus<EOnTakeDamage>.Unregister(OnTakeDamage);   // 到達しないケースがある
}
```

`_inputView` は `PlayerInputView`（MonoBehaviour）であり、`==` はUnityのオーバーロードが効く。
つまり **`PlayerInputView` が `CameraSystemView` より先に破棄された時点で `_inputView == null` が true になり、
早期returnによって `EventBus.Unregister` に到達しない**。

`EventBus<T>` は静的クラスであるため、シーン遷移をまたいで破棄済みの `CameraSystemView`
インスタンスへの参照が残り続ける。次に `EOnTakeDamage` が発火した際、
`OnTakeDamage` 内の `_viewSettings.AutoLockOnViewportGraceDuration`（line 376）等で
`MissingReferenceException` を誘発しうる。シーンを往復するほど購読が積み上がる。

**修正方針**: 静的EventBusの解除を早期returnより前に移す。

```csharp
private void OnDestroy()
{
    EventBus<EOnTakeDamage>.Unregister(OnTakeDamage);   // 先に実行

    if (_inputView == null) { return; }
    // ... 入力イベントの解除 ...
}
```

なお同じ `EventBus<EOnTakeDamage>` を使う
[EnemyAIController.cs:41,55,152](../../Assets/Scripts/Runtime/3.Adaptor/InGame/Enemy/EnemyAIController.cs) と
[BossAIController.cs:73,88](../../Assets/Scripts/Runtime/3.Adaptor/InGame/Enemy/Boss/BossAIController.cs)
は正しく解除されている。**このファイルだけが例外**。

## 【確定】ラムダ購読のため構造的に解除不可能

**場所**: [PlayerInitializer.cs:264-275](../../Assets/Scripts/Runtime/6.Composition/InGame/Player/PlayerInitializer.cs)

```csharp
dodge.OnDodgeStarted += (duration, direction) => { ... };   // 解除不能
dodge.OnDodgeEnded   += () => { ... };                      // 解除不能

_characterAnimationSignal.OnDodgeEnded += _onDodgeEndedHandler;  // ← こちらは正しい
```

無名ラムダは参照を保持していないため `-=` が書けない。実際 `OnDestroy`（line 385-411）でも
この2つだけ解除されていない（`+=` 6件に対し `-=` 4件）。

注目すべきは**すぐ下の line 277 では `_onDodgeEndedHandler` というフィールドに
デリゲートを保持して正しく解除している**点。実装者はパターンを理解しているので、
264/269にも同じ手法を適用すればよい。

**修正方針**: ラムダをフィールドに退避してから購読する。

```csharp
_onDodgeStartedHandler = (duration, direction) => { ... };
dodge.OnDodgeStarted += _onDodgeStartedHandler;
// OnDestroy 側
dodge.OnDodgeStarted -= _onDodgeStartedHandler;
```

## 【要検証】View側のOnDestroy任せになっている購読

**場所**: [HUDEnemyHealthInitializer.cs:59](../../Assets/Scripts/Runtime/6.Composition/InGame/UI/HUDEnemyHealthInitializer.cs)

```csharp
_view.OnUpdate += _presenter.Update;   // 対応する -= がない
```

`OnDestroy`（line 68）では `_viewModel?.Dispose()` のみを呼んでおり、`OnUpdate` の解除がない。

現状リークしていないのは、[HUDEnemyHealthView.cs:103-107](../../Assets/Scripts/Runtime/4.View/InGame/UI/HUDEnemyHealthView.cs)
の `OnDestroy` が `OnUpdate = null` でイベント自体をクリアしているため。
つまり **View側の後始末に暗黙依存している**状態で、破棄順序が変わると壊れる。

同様の構造が [ACLikeRhythmGuideViewModel.cs:13-15](../../Assets/Scripts/Runtime/4.View/InGame/Music/ACLikeRhythmGuideViewModel.cs)
にもある（3件購読・解除ゼロ、`IDisposable` 未実装）。こちらも
[ACLikeRhythmGuideView.cs:238-242](../../Assets/Scripts/Runtime/4.View/InGame/Music/ACLikeRhythmGuideView.cs)
の `OnDestroy` がイベントをnull代入することで救われている。

**修正方針**: ViewModel／Initializer側を `IDisposable` にして自分で解除するか、
View側の「`OnDestroy` でイベントをnullクリアする」を明示的な規約としてドキュメント化する。
現状は規約が暗黙なため、新規Viewで容易に破られる。

## 【設計指摘】Initializeで購読するが解除経路を持たない

**場所**: [EnemyLifeCycle.cs:176-179](../../Assets/Scripts/Runtime/6.Composition/InGame/Enemy/EnemyLifeCycle.cs)

```csharp
_aiController.On1BeatBefore += _raycastView.LockWarningDirection;
_aiController.On2BeatBefore += _raycastView.StartTrackingWarning;
_aiController.OnAttack      += _raycastView.HideWarning;
_aiController.OnAttack      += HandleEnemyAttackExecuted;
```

この4件に対応する `-=` は存在しない。

ただし `_aiController` は同じ `Initialize` 内（line 157）で `new EnemyAIController(...)` として
生成される**このインスタンス専有のオブジェクト**であり、`EnemyLifeCycle` と寿命を共にする。
そのため現状で実害のあるリークにはなっていない。

一方、`Activate()`（line 197〜）で行う `_enemyEntity.OnDied += HandleEnemyDied`（line 207）は
プール再利用のたびに購読されるため、`BeginDying`(483) / `Deactivate`(294) / `OnDestroy`(691) の
3箇所で丁寧に解除されている。**同じファイル内で購読解除の厳密さに差がある**のが指摘点。

**修正方針**: `Initialize` が二重に呼ばれた場合の安全性が保証されていないため、
`Initialize` 冒頭で既存購読を解除するか、二重初期化を防ぐガードを入れる。

## 【設計指摘】UI Toolkit の clicked 購読

**場所**: [SettingBase.cs:25](../../Assets/Scripts/Runtime/4.View/OutGame/Setting/SettingBase.cs)
