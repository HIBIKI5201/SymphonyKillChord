## 結論と網羅性判定

現状の仕様概要はゲーム動作を網羅していない。トップページ `Docs/NotionSpecifications/Symphony Kill Chord/仕様概要.md` はデータベースへのリンクだけで、仕様本文は仕様リストの個別ページに分散している。既存ページも、例として攻撃アクションやリズム判定のように詳細を記述したものがある一方、実装上の全条件・遷移・例外が網羅されているかは別途確認が必要である。

「全て」を満たすには、C#の型名の羅列ではなく、プレイヤーから見えるゲーム状態・入力・遷移・結果を機能ごとに列挙し、各々を仕様ページへ割り当てる必要がある。開発ツール、エディター専用処理、デバッグ機能、マスターデータの全数値はゲーム動作仕様の本文へ混ぜず、必要な関連仕様を参照させる。

**現行仕様リスト47ページの本文・適用範囲・実装状態の一次点検と、主要なゲーム進行経路のコード突合を実施した。** ページ別の具体的な差分とコード経路を本書の後半に記録した。全てのページについて「ページがあるか」だけでなく本文と関連する実装状態を読み、ゲーム内の主要な入力・イベント経路はApplicationからView/Compositionまで追跡した。

この結果は「全ページの記述と全コード分岐に漏れがない」という保証ではない。プラットフォーム実機、ストア管理画面、外部フォーム設定、全マスターデータ全件、および全プレイヤー可視分岐の組合せQAはこの環境から確証できない。コードだけで意図を確定できない項目は未決・要実機と明記し、確認済みと混同しない。

### 実装レイヤー別の取りこぼし防止

機能マップだけでは「何の実装を見たか」が曖昧になる。Claude は各領域で Domain のルールだけでなく、以下の実行経路をたどり、プレイヤーに影響する処理の有無と仕様ページを記録する。

| レイヤー/起点 | 確認する挙動 |
|---|---|
| `2.Application` | ユースケースの開始・完了・中止、イベント購読、複数条件の評価順、状態更新と保存の順序 |
| `3.Adaptor` | 入力からUseCaseへの振り分け、画面遷移命令、ViewModel変換、通知・エラーの表示、他モジュールとの橋渡し |
| `4.View` | 実入力（Input System/UI）、アニメーション・カメラ・表示・物理挙動、時間停止/ポーズ、シーン内オブジェクトの可視条件 |
| `5.Infrastructure` | マスターデータ欠損/初期値、リソースロード失敗、セーブの再試行・破損復旧、プラットフォーム依存の実動作 |
| `6.Composition` | シーン/画面で有効化される機能、必須/任意機能の有無による挙動差、初期化順がゲーム進行に及ぼす影響 |
| `Assets` の設定データ | 各ステージ/敵/スキル/ミッション/画面設定が利用する項目、未設定・重複・参照切れ時の挙動。全数値の転載ではなく、ルールへの参照を記録 |

モジュール名やクラス名だけを一覧にして終わらず、入力/イベント→アプリ処理→状態変化→表示/音/保存まで1本の流れとして追跡する。

## 変数・パラメーターの書き方

### 調査した現行ルール

- 仕様概要ガイドは「全職種が読むため、専門知識がなくても読めるように書く」としている。
- 仕様書ライティング規則 W-20 は、数値パラメーターが3つ以上並ぶ場合に「名前 / 値 / 単位 / 正本のアセットまたはコード」の表を求める。
- W-21と仕様概要ガイドは、マスターデータにある値については正本を分けないため、値とアセットパスを示す方針である。
- 現行の「ミッション」ページには「敵を n 体」「n 秒間」「n 回」「n 分以内」等の表記があり、`n` が何を表し、ステージごとにどこで決まるかは本文だけでは追いにくい。

### 推奨

**`n` のままにせず、意味のある名前を本文に書く。必要なときだけ、対応するコード上の識別子をコード書式で添える。** 仕様概要は全職種向けなので、C#の変数名だけで文章を置き換えると可読性が下がる。一方、コード識別子が追跡に役立つ場面では、日本語名と識別子を並記する。

例:

- 「敵を **目標討伐数** 体討伐する。目標討伐数はステージごとに設定する（実装参照: `EnemyKillCountClearConditionAsset._requiredKillCount`）。」このフィールド名は `Assets/Scripts/Runtime/5.InfraStructure/InGame/Mission/EnemyKillCountClearConditionAsset.cs` で確認した。
- 「**生存時間** が設定秒数に達したとき成功とする。設定秒数の正本はステージのミッションデータである。」
- 閾値そのものではなくルールの説明が必要なら、「**判定猶予時間** 内の入力を Just とする。判定猶予時間は判定データを参照する。」と書き、値の正本へのリンクを付ける。

注意点:

1. 仕様上の概念名と実装名を区別する。実装リファクタで変わり得るフィールド名を、プレイヤー向けルールの唯一の説明にしない。
2. 同じ `n` でも「個数」「秒」「回数」「倍率」では意味が異なる。単位と決定主体（固定値、ステージ設定、マスターデータ、プレイヤー設定）を明示する。

## 変数名を仕様に併記する基準

ユーザー指摘の通り、`n`/`m`/`x`だけの説明は意味が曖昧になりやすい。既存の「変数・パラメーターの書き方」節をClaude向けの判断基準とし、本文には「対象数」「経過時間（秒）」など意味の分かる概念名を使う。追跡に役立つときは実在を確認したコード識別子をコード書式で併記する（例: 目標討伐数 `EnemyKillCountClearConditionAsset._requiredKillCount`）。識別子は概念の説明に添える参照名であり、読者向けの語を置き換えない。計算式に記号が必要なら記号表で意味・単位・取得元を定義する。コードに存在しない識別子を仕様書用に発明したり、仕様文をC#名だけで埋めたりしない。
