# 開発運用・情報フロー設計（横断） 設計レビュー（2026-10-01, Codex）

## 要約

全体評価は **C（運用の骨格は成立しているが、担当交代時の再現性と情報更新の保証が不足）**。
二段階PR、リリース再試行、仕様の定期ミラー、設定台帳は整備され、個人作業を共有成果へ変える仕組みがある。
一方、ブランチ生成の条件判定に実装不備があり、正本の運用説明が現行自動化と逆になっている。
ビルドはDriveの可変な最新版と自己ホスト環境に依存し、検索Botの索引更新は仕様ミラー更新と接続していない。
今週は認証更新の完了確認、ブランチ生成修正、旧手順の訂正、復旧担当の引継ぎを優先する。
GitHub Issueの実時間集計は通信制約で取得できず、件数・放置率を評価根拠として捏造していない。

## 良い点

- **PRの経路が明文化されている。** `AGENTS.md`と`ValidatePRTarget.yml`は、作業master・develop・mainの役割を区別する。
- **二段階PRの転記負担を減らしている。** `BuildDevelopPullRequest.js:196`以降は全元PRのチェックを集約し、Issue実在確認も行う。
- **自動本文を手編集した場合の逃げ道がある。** 同スクリプトのmarkerを外すと全面上書きを避け、不足するクローズ参照だけ追記する。
- **Releases公開失敗への対応が具体的。** `BuildAndRelease.yml:1890`以降は3回試行、ファイル名・サイズ確認、未公開ZIPのArtifact保存を備える。
- **重いビルドを抑制する工夫がある。** 同:202以降は最後のReleaseとの差分を見て、前回見送ったUnity変更も拾う。
- **長期個人PATへの依存を減らした。** `.github/apps/README.md`には版更新Appの作成・移管・鍵更新手順がある。
- **仕様同期で公開ログを意識している。** `NotionSpecificationsSync.yml:49`以降は通常出力を退避し、件数中心に表示する。
- **Bot配備にはrollbackがある。** `S/deploy/deploy-release.sh`は稼働リンクを切り替え、登録確認失敗で前版へ戻す。
- **検索の出典選別がある。** `S/SinfoniaOperator.SpecSearch/README.md`は草案・履歴を通常検索から区別し、未分類資料を無条件採用しない。
- **受入の実作業を重視する記録がある。** Discord「プログラマーリーダー認識共有」170–195行は実機・PC確認を明示する。
- **引継ぎ一覧の対象が広い。** 9月27日の権利確認・引継ぎ資料は元データ、再書き出し、アカウント、知識まで対象とする。

### 問題の解釈と優先順位

OPS-01は命名規約の好みではなく、条件不成立でも後続処理が走る制御の問題である。
ただしmaster生成Workflow全体には`feature/`限定があるため、任意の非featureブランチにも生成するという指摘ではない。
422を一律に「存在済み」と表示する処理もあるため、修正時は同名確認とそれ以外の検証エラーを分ける必要がある。

OPS-04は保存設定と文章規則の差である。GitHub上の保護が存在しないと断定するには実設定照合が必要になる。
master側をセルフマージ可能にする方針自体は妥当であり、必要なのはPRを経由したという事実を保つことである。
develop側の保存設定は1承認・最終push承認・古い承認の失効を要求しており、レビュー制度がないわけではない。

OPS-05は大量の自動テスト導入を前提としない。既存の人手確認を守るなら、対象SHA・場面・方法を明記するだけでも追跡性が上がる。
元PRの確認をすべて集約する実装は良いが、その後developと統合した状態の確認を代替するものではない。
ドキュメント変更時の「不要」記載はPRテンプレで許されており、不必要なUnity実行を強いる必要はない。

OPS-07とOPS-08は連動する。最新版取得の対象が意図せず変わると、ビルドは成功しても以前と同じ成果物とは限らない。
Drive整理自体は進んでおり、Source / Exportへの再編をやり直す提案ではない。
必要なのは採用パッケージの固定と、後任が同じ入力を取り出せることの確認である。

OPS-10は検索ランキングの品質とは別問題である。出典分類が正しくても、入力キャッシュが古ければ現行情報を回答できない。
サーバーはLibrary側が存在するとDocs側へ切り替わらないため、新旧が併存する場合に特に注意が必要である。
VM上の定期処理を読めていないため、索引が現に古いという断定はしない。

## 改善提案

工数感はS＝半日〜1人日、M＝2〜5人日、L＝1週間以上の実作業の目安。回答待ち・学校側の確認待ちは別とする。
以下は提案であり、この調査では修正・権限変更・通知・Issue作成を実行していない。

### すぐやる（今週）

#### P1. 認証更新と引継ぎの完了を証拠で確定する

- **何を**：D2141に残る認証再発行、編集権限是正、CI・CSV確認を担当者付きの完了項目にする。
- **なぜ**：Drive移動完了と、外部供給経路が安全に動くことは別だから。
- **手順**：秘密管理担当が失効・交換を確認し、CI担当とシナリオ担当が各1回確認、結果だけをIssueへ記録する。
- **手順**：公開記録には担当役割、確認日、成功・失敗、非公開証跡の有無を記載し、認証値や識別子を転載しない。
- **完了条件**：旧認証の無効化、後任認証での取得、必要な編集者だけの更新が確認される。
- **工数感**：M。**関連問題ID**：OPS-08、OPS-13。

#### P2. master生成の分岐と生成基点を修正する

- **何を**：条件不成立時の後続処理を確実にskipし、生成基点を明示する。
- **なぜ**：正常な空push手順だけでは、待機後の最新SHA取得という競合をなくせない。
- **手順**：生成関連stepへ条件を付けるか単一処理へまとめ、短い名前・master自身・既存masterを区別する。
- **手順**：createイベントの利用可能なSHA情報を検証し、作成時基点を固定する。固定できない場合は生成完了後に編集開始と明記する。
- **完了条件**：不正名でbranch生成なし、初回変更を急いでpushしても意図した基点、既存masterを上書きしないことを確認する。
- **工数感**：S〜M。**関連問題ID**：OPS-01、OPS-02。

#### P3. 正本の運用ページと引継ぎ案内を現行決定へ合わせる

- **何を**：Notionのキャッシュ運用・ビルド説明と9月27日引継ぎ一覧の矛盾を修正する。
- **なぜ**：新担当が最初に読む手順で逆方向へ誘導されている。
- **手順**：3時間同期、非公開サブモジュール、agent記録のコミット、Drive個人所有方針を現行として記す。
- **手順**：ビルドタグの`master-<種別>-<版>`、既存Draftの本文更新、現在の検証Workflow名も現行コードと照合する。
- **完了条件**：同じ作業をAGENTS・Notion・READMEのどこから始めても同じ手順になる。
- **工数感**：S〜M。**関連問題ID**：OPS-11、OPS-14、OPS-18。

#### P4. 自動化の「成功」と「何もしなかった」を区別する

- **何を**：Draft権限不足、通知設定失敗、意図したskipを別結果として記録する。
- **なぜ**：緑色の実行結果だけではPR欠落や通知停止が分からない。
- **手順**：Draftの403は要対応として失敗または明示的な運用アラートにし、差分なしと分ける。
- **手順**：日次Botの設定失敗に非0終了を設定し、有効・無効、日曜除外、再開判断者を運用ページへ記す。
- **完了条件**：担当者がAPIログ全文を読まずに、停止・対象なし・成功を識別できる。
- **工数感**：S。**関連問題ID**：OPS-03、OPS-15。

#### P5. 公開ログから不要な識別情報を除く

- **何を**：Drive取得結果の識別子と、外部API例外の無加工表示を見直す。
- **なぜ**：取得内容の確認に公開ログ上の識別子そのものは必要ない。
- **手順**：パッケージの論理名・版・hash・成功件数を表示し、例外はHTTP状態と処理段階へ要約する。
- **完了条件**：失敗時にも認証値・Drive識別子・共有リンクを公開出力しないことを確認する。
- **工数感**：S。**関連問題ID**：OPS-09。

#### P6. Issue棚卸しを再取得して週次の受入へ結ぶ

- **何を**：今回取得できなかったOpen一覧を、通信可能な環境で集計する。
- **なぜ**：古い監査件数や声の大きさだけでは優先順位を決められない。
- **手順**：前掲の集計定義でラベル・未担当・30/90日未更新・タイトル接頭辞を数え、取得時刻と母数を残す。
- **手順**：未担当の高影響Issueから主担当役割と次回確認日を決め、Notionタスクには同じIssue番号を持たせる。

### 次に（1か月）

#### P7. 仕様同期から検索索引までの版をつなぐ

- **何を**：仕様repo更新、VMキャッシュ更新、索引生成、Bot読込の版を追跡可能にする。
- **なぜ**：ミラーの新しさがBot回答の新しさを保証していない。
- **手順**：更新元を一本にし、キャッシュのcommit・取得時刻・索引時刻を記録。Library/Docsの優先ルールを廃止または明示する。
- **手順**：新索引を生成・検証後に切替え、失敗時は前版を維持する。既存の配備rollbackを活用する。
- **完了条件**：Notionのテスト用変更が、どの同期・索引版で回答に反映されたか分かる。

#### P8. ビルド入力を固定し、代替環境で再現する

- **何を**：外部パッケージ版・hash・Unity版・プロファイル・コードSHAをビルド単位で記録する。
- **なぜ**：同じコードの再試行で違う最新版を使う状況では障害を切り分けにくい。
- **手順**：非公開の配布台帳でパッケージを固定し、公開記録は論理版とhashだけにする。利用条件のある内容は公開しない。
- **手順**：後任が別の許可済みWindows環境で1プロファイルを再現し、ライセンス・SDK・取得権限の不足を埋める。
- **完了条件**：主担当不在でも同じ入力でビルドを開始でき、前回との差を説明できる。
- **工数感**：M〜L。**関連問題ID**：OPS-07、OPS-08、OPS-13。

#### P9. 受入条件と配布条件を分けて保証する

- **何を**：PR時の軽量検証とRelease時の実機確認を、それぞれ証跡へ接続する。
- **なぜ**：チェック文字列と、公開ZIPが遊べるという事実は異なる。
- **手順**：運用スクリプトの分岐検証、対象変更に限定したコンパイル・既存テストを選び、不要な変更は理由付きで免除する。
- **手順**：ゲーム変更は対象SHA・場面・端末を記録。Releaseには成功プロファイルと未確認環境を明記する。
- **手順**：skip済み変更の回収を定期チェックか週次担当確認へ組み込み、72時間後の自動実行を誤期待させない。
- **完了条件**：マージ済み、ビルド済み、配布可をそれぞれ判別できる。
- **工数感**：M。**関連問題ID**：OPS-05、OPS-06。

#### P10. 旧文書を残したまま現行の入口を一本化する

- **何を**：Docs/agentの索引に旧資料との対応、現行・履歴・廃止の区分を加える。
- **なぜ**：ファイルを一括移動するだけでは古い提案と確定事項の混同を解消できない。
- **手順**：3件の旧引継ぎと2組の完全重複から、現行参照先・後継資料・未完了事項を確認する。
- **手順**：新しい引継ぎはhandoffsへ、確定した仕様はNotionへ置き、旧資料には後継への案内を残す。
- **完了条件**：新担当がDocs全体を検索しなくても現行手順と残作業へ到達できる。
- **工数感**：M。**関連問題ID**：OPS-11、OPS-12、OPS-14、OPS-16。

#### P11. 二段階PRの適用対象を絞り、設定と規則を照合する

- **何を**：共同機能開発は二段階、小規模な独立修正は明示した直接develop経路とする案を検証する。
- **なぜ**：統合masterの便益が少ない変更にも同じ手続き費用が掛かっている。
- **手順**：既存hotfix・非feature経路の用途を整理し、どこまで直接経路を認めるかチームで決める。
- **手順**：変更するならAGENTS・Notion・検証・Rulesetを同時更新。masterのPR必須、main保護、bypassも実設定と照合する。
- **完了条件**：適用例と例外が一枚に収まり、少数の実PRで待ち時間・手戻りを測れる。
- **工数感**：M。**関連問題ID**：OPS-04、OPS-17。
