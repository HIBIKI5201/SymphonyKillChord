## 3. 決まった書き方（設定画面で採用したもの）

ガイドにはまだ反映していない。ほかのページに展開するときも、この形に合わせる。

### 本文と子ページの分け方

- **本文には、あるべき仕様だけを書く**。「現状: 〜」「未実装（#…）」「現在は使っていない」などの実装状況は本文に書かない
- **実装状況は子ページ「<ページ名> 実装状況」に書く**。本文の「詳細説明」の冒頭に「実装の状況（実装済み・未実装）は、子ページ「<ページ名> 実装状況」に記載する。」と1行だけ置く
- 子ページの構成は「説明 / 項目ごとの状況（表: 項目・状態・実装の現状・Issue）/ 設定できる場所（体験版時点）/ 確認の記録」

### 詳細説明に足した節

- **対象のプラットフォーム**: 各項目を設定できるプラットフォームを表にする。列は「項目 / Windows / Android / iOS / 補足」。記号は ○（できる）・×（できない）・△（条件付き）
  - 「対象の版」ではなく「対象のプラットフォーム」と呼ぶ（ユーザーの指示）
  - 現在の実装ではなく、**製品として必要な将来の仕様**を書く
- **条件・例外**: 「〜したとき」「〜の間は」「〜の場合は」の形で、失敗時・範囲外の値・二重操作などの挙動を書く

### 仕様意図・経緯・却下・保留

- **最終的な仕様の意図は「仕様意図」の本文に書く**。経緯の表の行ではなく、本文に「〇〇の意図は次のとおりである。」として箇条書きにする
- **経緯の表は「提案」と「変更」の行だけ残す**。「決定」「検討」の行は消す
- **経緯の表に「出典」の列は置かない**。列は「日付 / 種別 / 内容 / 判断・理由」
- **出典は本文のどこにも書かない**（PR番号・Issue番号・Discordのチャンネル名・議事録の決定番号・フォーラムのIDなど）。子ページの「Issue」列は実装の追跡用なので残す
- **理由が実際に書かれていない「判断・理由」の欄は「ー」にする**。「理由の記録なし」「仕様意図に記載する」などの文言は使わない
- **却下・保留した案からも「記録は無い」「理由の記録なし」の文言を消す**
- 本文に【要確認】を残さない

## 4. 設定画面で決まった仕様（2026-09-24〜25 にユーザーが回答）

### 対象のプラットフォーム

- iOS は Android と同じ扱い
- スマホ（Android・iOS）は、画面モード・解像度を設定できない（常に全画面・端末の解像度）
- スマホは、オートロックオンの有効/無効を設定できない（常に有効）
- 振動: Windows はゲームパッドをつないでいるときだけ（強い / 弱い / オフ）。スマホは端末本体を振動させ、オン / オフだけ。スマホの既定はオフ
- 決定・キャンセルのボタン: スマホはゲームパッドをつないでいるときだけ設定できる
- 開き方: スマホは Start の代わりに、画面内のボタンをタップして開く
- そのほかの項目（画質・明るさ・言語・リズム判定タイミング・カメラ感度・カメラ操作反転・マニュアルロックオンの追従速度・音量）は全プラットフォームで設定できる

### 保存したときの表示

- 3回とも保存に失敗したら「保存に失敗しました」と表示し、「やり直す」「キャンセル」を出す
- 「キャンセル」では「変更は保存されませんでした。保存されている設定に戻します」（「OK」ボタン）と警告してから、最後に保存した値へ戻す
- 保存に成功したら「保存しました」と表示する。オーディオ設定（スライダーを動かすたびに保存する）では表示しない

### コードで確認した事実（子ページの「確認の記録」に記載済み）

- 作戦・改造・研究の画面にある設定のショートカットボタンからも設定を開ける（作戦画面は強制出撃中を除く）。`ScreenInitializer.cs`、`StageSelectInitializer.cs`
- 範囲外の保存値はクランプする。リズム判定タイミングは 0.05 秒刻みに丸め、読めない値は 0 秒。`EnvironmentSettingsData.cs`、`AudioSettingsData.cs`
- 保存失敗は 1 秒・2 秒の間隔で最大 3 回再試行し、保存中の追加変更は最後の値だけ保存する。`AudioSettingsService.cs`、`EnvironmentSettingsService.cs`
- 失敗通知 `OnSaveFailed` を受け取る処理が無く、今は成功・失敗とも何も表示しない
- 振動はゲームパッドのモーター（`GamepadHapticsView.cs`）だけで、端末本体を振動させる処理は無い
- 実機（PlayMode）では確認していない

## 6. 作業の進め方（このセッションで分かった注意点）

- 書き込みは `skc-notion-spec-write` スキルの手順に従う（pull → 編集 → dry-run → ユーザーの承認 → `--confirm`）。**dry-runの結果を見せて承認を得るまで送信しない**
- `push --whole` は、本文のどこか1か所でもNotion側の書式の正規化で一致しないと 400 になる。部分置換（`--whole` なし）なら通った。部分置換も1回のリクエストでまとめて送るので、途中まで反映されることはない
- 送信前にほかの人がページを編集していると、ツールが「pull以降にNotion側が更新されています」で止まる。2026-09-25 にこれが起き、ユーザーがページをリセットしたうえで送り直した。止まったら取り直して差分を見せ、上書きせずにマージする
- 下書きはスクラッチパッドに置くと消えることがある。`SinfoniaOperator/.notion-work/drafts/`（Git の管理対象外）に置く。ただしこのフォルダは別のPCには引き継がれない
- ローカルで見た目を確認するときは、Notion独自の要素（メンション・H1の背景色・目次）をHTMLに置き換えて表示した。変換スクリプトは `SinfoniaOperator/.notion-work/drafts/preview.js`（このPCのみ）
- Notionコネクタ（MCP）はこのワークスペースにつながっておらず、DBの選択肢などは読めなかった
- 仕様の判断（プラットフォームごとの可否、文言、理由など）は推測で確定させず、案を示してユーザーに答えてもらう
