## ページの構成
### W-07 既存の構成に合わせる【変更】
既存ページの節構成・見出し名・順番・絵文字・表の列構成・口調はそのまま使い、情報は既存の節の中に足す。同じ種類のページは、同じ種類の既存ページのテンプレートに揃える。

既存ページを直すときは、誤りや古い記述と、足りない情報だけを直す。言い回しを整えるだけの書き換えはしない。

仕様リストのページは「仕様概要（関連ページ・関連用語）→ 詳細説明 → 仕様意図」の順にする。仕様意図はページの末尾に置く。
仕様意図には「経緯」（日付・提案・検討・決定・変更・却下と、判断の理由・出典）と「却下・保留した案」を網羅する。仕様を変えたり、提案を却下したりしたときは、ここに追記する。同じ提案が再び出たときに、過去の検討を参照できるようにするためである。
### W-11 本文と背景を分ける【変更】
規則・仕様の本文と、背景・経緯・議論を分ける。経緯が本文に混ざると、過去の案を現行の規則と読み違えるためである。本文に経緯が混ざって誤読のおそれがあるときに限って、末尾の「背景」トグルに入れる。
### W-12 体験版の値【変更】
体験版だけの値やイベント限定の設定には「体験版（TGS 2026）設定」のように明記し、通常の値と並べる。
### W-13 必ず入る情報はDBのプロパティにする【変更】
ページの本文に「このページについて」の節を作らない。対象読者は書かない。最終確認日はNotionの最終更新日で分かるので書かない。どのページにも必ず入れる情報（何の正本か、状態など）は、本文ではなくDBのプロパティにする。

### W-15 使うブロック【変更】

## 識別子と数値
### W-19 変えないID
AIやツールが読むページ（コード規定・設計思想・QA対応表など）では、規則や項目に番号（ID）を付け、後から変えない（例: QAの`CBT:4-3`）。ツールは見出しの名前ではなく番号で項目を指すため、番号が変わると別の項目を指してしまう。
### W-20 IDの位置
IDは、表なら1列目、見出しなら先頭に置く（例: `W-04 H1の背景色`）。
### W-21 数値
数値が3つ以上並ぶときは表で書く。列は「名前 / 値 / 単位 / 正本（値が実際に入っているアセットやコード）」とする。
### W-22 マスターデータの値
値の正本がマスターデータ（Unityのデータ）にある場合は、Notionには「現在値」として写しを書き、正本のアセットのパスを添える。Notionと Unity の両方に値の正本があると、食い違ったときにどちらが正しいか分からなくなるためである。

4. マネジメント以降を第4節の「足りない点」に沿って1ページずつ進める。【要確認】・「未実装」の目印は、使うページ（例: 仕様概要、仕様検討フォーラム）を扱うときにそのガイドへ追記する
5. 最後に第3節の「別ページで直すもの」を反映し、TEMPページの削除をユーザーに依頼する

## 8. ユーザーの作業上の好み（この作業で分かったこと）

- やり取りは日本語で行う
- 要約は「ページに貼るもの」ではなく「ユーザーが各ページの中身を把握するためのもの」。置き場所の説明は要らない
- 規則の追加は、全ページに当てはまるかを先に考える。当てはまらないものは、該当ページのガイドへ個別に書く
- 分かりにくい用語は例を交えて説明する
