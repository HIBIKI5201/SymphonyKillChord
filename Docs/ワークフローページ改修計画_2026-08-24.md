# ワークフローページ 改修計画

作成日: 2026-08-24
対象: Notion「ワークフロー」ページ（`2ef7c2c6-cc02-8001-b4f0-d69b499c64f0`）とその配下 68ページ
根拠: `Docs/NotionSpecifications`（2026-08-19 取得）の全文調査。「該当なし」はワークフロー配下を全文検索した結果である

## 0. 現状の構造

ワークフロー直下は3ブロックに分かれている。

| ブロック | ページ |
| --- | --- |
| 運営 | スプリント / メンバーハンドブック / 組織図 / 休暇申請 |
| 環境構築 | Unity導入方法 |
| 役職 | ディレクター / プランナー / プログラマー / デザイナー / サウンドクリエイター / シナリオライター / 声優 |

配下ページの中身の量には大きな偏りがある。

| 役職 | 子ページ数 | 状態 |
| --- | --- | --- |
| プログラマー | 16 | 充実。ただし現役と旧方式が同じ階層に並ぶ |
| デザイナー | 14 | 職種別に納品規定まで整備済み |
| プランナー | 4 | 企画・マネジメント・リードは記載あり |
| サウンドクリエイター | 2 | 納品規定あり |
| シナリオライター | 1 | メンバー表のみ。作業・納品の規定が無い |
| ディレクター | 1 | アートディレクションのみ |
| 声優 | 1 | 運用のみ（4行） |

## 1. 統合すべきページ

### 1-1. Unityセットアップ（最優先）

現在、環境構築の情報が3か所へ散っており、どれも自分の役職の分しか書かれていない。

| 現状のページ | 内容 | 問題 |
| --- | --- | --- |
| `ワークフロー/Unity導入方法` | UnityHubのバージョン（`6000.3.10f1`）、Androidモジュール、AssetStoreToolsのunitypackage導入 | 事実上プログラマー向け。リポジトリの取得手順が無い |
| `デザイナー/キャラモデラ―/Unity` | 触るシーンとインポート先フォルダ | キャラモデラー配下にあるため、他のデザイナー職から見えない |
| `デザイナー/キャラモデラ―/SourceTree` | 外部記事へのリンク1行 | 同上。プログラマー側にはSourceTreeの記載が無い |

**提案**: ワークフロー直下に「Unityセットアップ」を新設し、上記を吸収したうえで、現在どこにも書かれていない工程を足す。役職ごとに分岐する部分はページ内のトグルで分ける。

想定する目次は次のとおりである。

1. 前提（必要なアカウント: GitHub / Notion / Discord / Google Drive）
2. UnityHubとエディタのインストール（`6000.3.10f1`、Android Build Support）
3. リポジトリの取得（SourceTree、クローン先、初回のLFS/大容量アセットの注意）
4. 初回起動（インポートに要する時間、Library生成、よくあるエラー）
5. AssetStoreToolsの導入（Google Driveのunitypackage、最新の日時を選ぶ）
6. 役職別の追加手順（トグル）
   - プログラマー: パッケージ導入手順への導線、開発規定への導線
   - キャラ/背景モデラー: 作業シーンの置き場、モデルのインポート先
   - エフェクト/モーション: 作業フォルダ
   - プランナー: Planner Master Data ウィンドウの開き方
7. 動作確認（どのシーンを開いて何が動けばセットアップ完了とみなすか）

**注意**: 現状のUnity導入方法は最終更新が古く、Unityのバージョンが実際のプロジェクト設定と一致しているか未検証である。統合の際に`ProjectSettings/ProjectVersion.txt`と突き合わせる。

### 1-2. 納品規定の横断ページ

納品の規定はデザイナー配下の職種ごと（UIデザイナー・イラストレーター・エフェクト・モーション・キャラモデラー・背景モデラー）とサウンドクリエイター配下に、計7ページある。命名規則・フォルダ構成・提出先が各ページに重複して書かれている。

**提案**: 共通部分（提出先、命名規則の原則、レビューの流れ）を「納品の共通ルール」として1ページに抜き出し、職種別ページは差分だけを書く形へ整理する。既存の`Docs/アセット名リスト_命名規則提案.md`は、この共通ルールの素材になる。

### 1-3. 旧方式のアーカイブ

プログラマーページには「旧方式（アーカイブ）」の見出しの下に「アルファ版開発に関して」と班制度（班の仕事の仕方 / 技術班 / 設計班）が並んでいる。見出しはあるが、ページを直接開いた人には現役か旧方式かが判別できない。

**提案**: 各アーカイブページの冒頭へ「このページは運用されていない」旨のコールアウトを入れる。または`ワークフロー/アーカイブ`を作って移動する。

## 2. 新規に必要なページ

### 2-1. オンボーディング（初日にやること）

「オンボーディング」「初日」に該当する記述はワークフロー配下に無い。新しく参加した人が、どの順にどのページを読めばよいかの導線が存在しない。

**提案**: ワークフロー直下に「はじめに」を置き、次を1ページで示す。

1. メンバーハンドブックを読む（理念・タスク管理・責任）
2. Discordのチャンネル構成と、自分が入るチャンネル
3. Notionの見方（仕様概要 / システム概要 / ワークフローの役割分担）
4. Unityセットアップ（1-1）
5. 自分の役職ページ
6. スプリントの参加方法（レビュー日時、役職会議）

### 2-2. ビルドとリリースの運用

「リリース」に該当する記述がワークフロー配下に1件も無い。`AutoBuilder`（`Assets/Editor/Scripts/AutoBuilder`）とGitHub Actionsの`BuildAndRelease.yml`が実装としては存在するが、誰がいつビルドを回すのかがどこにも書かれていない。

**提案**: 「ビルドとリリース」を新設し、次を書く。

- ローカルビルドの手順（Master / Develop、BuildProfilesとAutoBuilderSettings）
- CIビルドの起動条件と成果物の受け取り方
- ビルドが壊れたときの一次切り分けと連絡先
- 動作確認端末とAndroidの実機確認

### 2-3. 社内ツールの使い方

`SinfoniaOperator`（Notion連携・Discord連携）と Planner Master Data ウィンドウについて、ワークフロー配下に記述が無い。前者はリポジトリに実装があり、Notion仕様書の同期に使われている。

**提案**: 「社内ツール」を新設し、ツールごとに「何ができるか / 誰が使うか / 使い方の入口」を1〜2段落で書く。詳細はシステム概要側の既存ページ（`SinfoniaOperator`、`マスターデータ運用ガイド（プランナー向け）`）へリンクする。

### 2-4. バグ報告とQA

「QA」に該当する記述が無く、「バグ」もメンバー個人ページに現れるだけである。バグを見つけた人がどこへ書くのかが決まっていない。

**提案**: 「バグ報告」を新設し、報告先（Notionのタスクデータベースか、Discordの特定チャンネルか）、必要な情報（再現手順・端末・ビルド番号）、優先度の付け方を定める。**これは運用の決定が先に要るため、書く前にディレクター・リードで方針を決める必要がある。**

## 3. 役職ページの粒度をそろえる

現在、ディレクター・シナリオライター・声優はリンク1本のみで、そのページを開いても仕事の進め方が分からない。他の役職ページに合わせ、最低限この3節を持たせる。

| 節 | 内容 |
| --- | --- |
| メンバー | 担当者一覧と連絡先（既にある役職はそのまま） |
| 作業 | 何をどこで作るか。使うツールと置き場 |
| 納品 | 誰へ、どの形式で、どのタイミングで渡すか |

不足しているのは次のとおりである。

| 役職 | 不足している節 |
| --- | --- |
| ディレクター | メンバー、作業（意思決定の範囲と承認フロー） |
| シナリオライター | 作業（シナリオCSVの書き方への導線）、納品 |
| 声優 | メンバー、納品（収録データの形式と提出先） |
| プランナー | 納品（仕様書の書き方は「仕様書 ガイド」にあるが、ワークフロー側から辿れない） |

シナリオライターについては、システム概要側に`シナリオCSV～ドライブ同期～`と`シナリオコマンド使い方`が既にあるため、新規に書くのではなくワークフロー側からリンクするだけで足りる可能性が高い。

## 4. 他ツリーとの重複・分裂

同じ「規定」が、ワークフローとシステム概要の両方に分かれて置かれている。

| 内容 | ワークフロー側 | システム概要側 |
| --- | --- | --- |
| コーディング規約 | `プログラマー/クライアント部門 Unityプロジェクト開発規定`、`開発部門 Unityプロジェクト開発規定` | `コード規定` |
| Git運用 | `アルファ版開発に関して`（旧方式のブランチ名） | `GitHub 運用規定` |
| 設計方針 | `設計班` | `設計思想` |

**提案**: ワークフロー側は「誰が何をするか」に絞り、規定の実体はシステム概要側へ寄せてリンクで繋ぐ。どちらを正本にするかはリードプログラマーの判断が要る。

## 5. 進め方の提案

| 順 | 作業 | 依存 |
| --- | --- | --- |
| 1 | Unityセットアップの統合（1-1） | Unityバージョンの実物確認 |
| 2 | はじめに（2-1） | 1が終わっていること |
| 3 | 役職ページの節をそろえる（3） | ディレクター・声優の運用確認 |
| 4 | ビルドとリリース（2-2） | 実装の確認のみで書ける |
| 5 | 社内ツール（2-3） | 実装の確認のみで書ける |
| 6 | 納品の共通ルール（1-2） | 既存7ページの内容突き合わせ |
| 7 | 旧方式のアーカイブ表示（1-3） | リードの承認 |
| 8 | バグ報告とQA（2-4） | 運用方針の決定が先 |
| 9 | 規定の一本化（4） | リードプログラマーの判断 |

1・2・4・5は既存の情報と実装から書けるため、判断待ちが無い。3・7・8・9は先に人の判断が要る。
