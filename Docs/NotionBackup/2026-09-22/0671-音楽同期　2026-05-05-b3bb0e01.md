## 他のサブシステムとの連携

#### 敵システム
    - `EnemyAttackReservationUsecase `-> `IMusicActionScheduler`
敵が攻撃を予約するため、`IMusicActionScheduler`を実装したのインスタンスを使用している
    - `ShellReservationUsecase `-> `IMusicActionScheduler`
砲兵の砲弾が着地タイミングを予約するため、`IMusicActionScheduler`のインスタンスを使用している

    - `SkillPattern `-> `RhythmPattern`
スキル固有のリズムパターンを表すためにインスタンスを保持している

#### リズムUI
    - `RhythmGuidePresenter `-> `IMusicSyncService`

    - `RhythmGuideRange `-> `BeatType`
リズム情報の一部として保持している

## 改修
  - ▶ `MusicSyncViewModel` を `MusicSyncState` に変更

####  問題点
      `MusicSyncViewModel` は名称上は ViewModel として定義されていたが、実際には UI 表示用のデータではなく、以下のような音楽同期に関する状態を保持する役割を担っていた。
```Plain Text
・PlayTime
・Bpm
・CurrentBeat
・NearestBeat
・AccurateBeat
・BeatLength
```
      本来の ViewModel が担うべき「View への表示データの提供」や「UI 更新のための責務」を持っておらず、責務が不明確な状態となっていた。
      また、更新フローも以下のように複雑になっていた。
```Plain Text
MusicSyncView (Update)
↓
MusicSyncViewModel (PlayTime更新)
↓
OnUpdateイベント発火
↓
ControllerのTick呼び出し
↓
Application / Domain層で値を参照
```
      この構造には以下の問題がある。
      - View が状態更新の起点となっており、責務が過剰になっている
      - ViewModel がイベント発行の役割まで担っており、責務が肥大化している
      - イベント駆動によって更新経路が間接的になり、処理の流れが追いづらい
      - 層をまたいだ依存関係が暗黙的に発生し、構造が不透明になる
      その結果、設計上の責務分離が崩れ、将来的な拡張やデバッグ時に問題となる可能性があった。

####  対応内容
      `MusicSyncViewModel` を `MusicSyncState` に改名し、責務に合わせて View 層から Adaptor 層へ移動した。
      これにより、このクラスは UI 表示とは切り離された「音楽同期状態の保持」に特化したクラスとして再定義した。
      また、状態更新通知に使用していた `OnUpdate` イベントを削除し、更新フローをイベント駆動から明示的な呼び出しへ変更した。
      具体的には、`MusicSyncController` が `Tick()` メソッドを通して状態更新を行う構造へ変更した。
```Plain Text
MusicSyncView
↓
MusicSyncController(Tick)
↓
MusicSyncState / MusicSyncService
```
  - ▶ `RhythmState` の履歴管理を1本化

####  問題点
      `RhythmState` は、1回のリズム入力を以下の3つの `RingBuffer` に分けて保存していた。
```C#
RingBuffer<BattleActionType>
RingBuffer<BeatType>
RingBuffer<float>
```
      これは、同じインデックスの値が同じ入力を表している前提の設計だった。
      そのため、将来的にどれか1つだけ追加・削除・補正した場合、履歴の対応関係がズレる可能性があった。

####  対応内容
      `RhythmInputRecord` というデータクラスを追加し、1回の入力を以下のように1つにまとめた
```C#
RhythmInputRecord
-BeatType
-Timing
-ActionType
```
      `RhythmState` は `RingBuffer``<``RhythmInputRecord``>` を持つ形に変更した。

  - ▶ `RhythmDefinition` の責務分離

####  問題点
      `RhythmDefinition`が以下の債務を持っていた
      - BPMや拍の長さ、リズム定義に関する債務
      - 指定された拍・小節から実行時刻を計算する責務
      特に`RhythmDefinition` 内にあったGetExecuteTimeメソッドは、敵の音楽同期行動などの実行予約に関する処理であり、責務が広くなりすぎていた。

####  対応内容
      `RhythmDefinition` には、BPM・1拍の長さ・1小節の長さ・拍子判定などのリズム定義に関する処理だけを残した。
      実行時刻の計算は、新しく静的な `MusicTimingCalculator` クラスに分離した。
```Plain Text
RhythmDefinition
→ BPM、BeatLength、BarLength、BeatType判定

MusicTimingCalculator
→ ExecuteRequestTiming から実行時刻を計算
```
  - ▶ `RhythmPattern` の不変性修正

####  問題点
      `RhythmPattern` は `readonly struct` として定義されていたが、内部に配列をそのまま保持していた。
      配列は参照型のため、コンストラクタで受け取った配列をそのまま保持すると、外部から配列の中身を変更できてしまう。
```C#
BeatType[] source= { BeatType.Four };
RhythmPattern pattern= new RhythmPattern(source);

source[0] = BeatType.Eight;
```
      この場合、`pattern` の中身も変わってしまう。
      つまり、`readonly struct` であっても、値オブジェクトとして完全に不変ではなかった。

####  対応内容
      コンストラクタで受け取った配列をコピーして保持するように変更した。
      また、内部配列を直接返さず、`ReadOnlySpan``<``BeatType``>` で読み取り専用として公開するようにした。


  - ▶ 拍子、BPMを表す変数の型を統一

#### 問題点
      　拍子やBPMを表す変数は、`int`、`long`、`float`、`double`の複数混在しているため、計算と型変換の時に精度ロスが発生する可能性た高いため、doubleに統一するべき。

#### 対応内容
      　BPM関連の型、及び拍子関連の型を`double`に変更した。

## 問題点（ログ）

#### 全体的にコメント・サマリーが書かれていない箇所がある
    コーディング規約違反のため、追加しましょう。

#### 「60d」や「4d」などマジックナンバーが書かれている
    マジックナンバーは規約違反のため、定数化しましょう。

#### MusicSyncViewModelの所在レイヤー
    　MusicSyncViewModelは実装上、PlayTimeやBPMなどの値をMusicPlayerから受け取って伝達する仕組みとなっている。
　よって、このクラスの役割はAdaptorであるべきではないか、という疑問が生じた。
    対応案：
　MusicSyncViewModelをAdaptorに移動する。移動後のクラス名は「MusicSyncState」とする。

#### RhythmDefinitionの責務
    　今のRhythmDefinition が「拍子」と「実行予約」の責務を両方持っているため、責務過多ではないかと思われる。
    対応案：
　BPMや拍の定義関連だけ残して、他の機能を分離して別のクラスにする。

#### RhythmPatternの配列保持
    　RythmPatternはreadonly structだが、コンストラクターが受け取った配列の参照をそのまま持っているため、不変ではなくなっている。
    対応案：
　コンストラクターが受け取った配列をToArrayしてprivate fieldに設定する。

#### BPMのデータ型
    　今のBPMはint型で管理されているが、BPMは小数である場合も多々あるので、doubleにするべきではないか。
    対応案：
　BPM関連の値の型をdoubleに変更する。

#### Beat構造体
    - ▶ データ型について
      　この構造体は、コンストラクターが使用される時にlong型が渡されて、引数自体の定義がfloat、さらに構造体のフィールドがdoubleとなっている。
      対応案：
　コンストラクターを呼ぶ時にlongが入るのは多分仕方なし。引数の型はフィールドと統一したいのでdoubleにする。
    - ▶ GetLengthメソッドが使われていない
      　このメソッドではなく、代わりにBeatを使用している構造体RhythmDefinitionのメソッドGetExecuteTimeにて類似な計算をしている。
      対応案：
　メソッドの語義としてはBeatが持って問題ない。リファクタリングの状況を見て、このメソッドを使用するようにするか、削除するか決める。
