SinfoniaOperatorは3つの`.NET`プロジェクトに分かれている。役割の境界を保守時に見失わないよう、まずこの分割の理由から説明する。

### プロジェクト構成
| プロジェクト | ターゲット | 役割 |
|---|---|---|
| `SinfoniaOperator.Core` | `netstandard2.1;net10.0` | Notion API連携、Discord送信、設定管理（`OperatorConfig`）の共通ライブラリ |
| `SinfoniaOperator`（Exe） | `net10.0` | Bot本体。CLIサブコマンドで日次通知・仕様検索インデックス生成・常駐Botを切り替える |
| `SinfoniaOperator.SpecSearch` | `net10.0` | 仕様検索専用ライブラリ。チャンク分割・埋め込み生成・検索インデックス |

#### なぜCoreだけ`netstandard2.1`も対象にしているか
`SinfoniaOperator.Core`は、ビルド後に`Assets/Editor/Plugins/SinfoniaOperator/`へ自動コピーされ、Unity Editor拡張（Notionタスク表示・作業ログ送信）から参照される。Unity側から参照可能にするため`netstandard2.1`を維持している。`csproj`の`CopyToUnity`ターゲットがこのコピーを担う。
この制約があるため、Coreには**Unity非互換なAPIを持ち込まない**（`PriorityQueue`など、netstandard2.1に無いものは使用禁止）。

#### なぜ`SpecSearch`を別プロジェクトに切り出したか
仕様検索機能はONNX Runtime（`Microsoft.ML.OnnxRuntime`）と`Lokad.Tokenizers`という比較的重量級の依存を持つ。これをCoreに混ぜると、Unity側へコピーされる成果物にも巻き込まれてしまう。Unity Editorには不要な依存であるため、`net10.0`単独ターゲットの別プロジェクトとして切り離した。
Bot本体（Exe）は`SpecSearch`をプロジェクト参照するが、Coreは`SpecSearch`を参照しない。依存の向きはBot → SpecSearch / Bot → Core であり、SpecSearchとCoreの間に依存関係は無い。

### Bot本体（Exe）のCLIサブコマンド
`SinfoniaOperator.cs`の`Main`が、第一引数によって挙動を振り分ける。
| 引数 | 挙動 | 実行元 |
|---|---|---|
| （なし） | 今日のタスク・タスクアラート・（月曜のみ）スプリントをDiscordへ通知して終了する | GitHub Actions（毎朝07:00 JST） |
| `send --channel <種別> --message <本文>` | Notionを読まず、指定チャンネルへ単発メッセージを送って終了する | 外部プロセスからの軽量呼び出し |
| `index` | 仕様書からベクトル検索インデックスを生成してファイルへ保存する | 手動、または仕様更新後の再生成 |
| `serve` | Discord Gatewayへ接続したまま常駐し、`/spec`スラッシュコマンドに応答する | Oracle Cloud VM上のsystemdサービス |
**この分岐の順序と挙動は変更しないこと。** デフォルト（引数なし）の日次通知は既存のGitHub Actionsワークフロー（`.github/workflows/SinfoniaOperator.yml`）が依存している。新しいサブコマンドを追加する場合は、既存の分岐より前に判定を割り込ませない。

#### 常駐（`serve`）とバッチ（デフォルト）の違い
日次通知は「Discordへログイン→送信→即終了」という一過性のプロセスであり、GitHub Actionsのスケジュール実行に向いている。一方`serve`は`DiscordSocketClient`の接続を維持し続け、`InteractionCreated`イベントを待ち受ける。両者は同じ`DiscordBotManager`クラスを使うが、`serve`側だけが`ConfigureSpecSearch`で仕様検索インデックスと埋め込みモデルを注入し、`/spec`コマンドを登録する。
`serve`は`PosixSignalRegistration`でSIGINT/SIGTERMを捕捉し、systemdの`stop`要求に対してグレースフルシャットダウンする。Windows上での動作検証は行っていない（Linux VMでの常駐を前提に実装している）。

### 設定管理の仕組み
`OperatorConfig`（Core）が設定値の解決を一元化している。優先順位は次のとおり。
1. JSON設定ファイル（`sinfonia-operator.env.json`は公開設定、`sinfonia-operator.secrets.json`はGit除外の秘匿設定）
2. 環境変数（JSONに無いキーのフォールバック）
設定キー名の文字列リテラルは`OperatorConfigKeys.cs`（Core）に一元化しており、Bot・Unity両方がこの定数を参照する。**新しい設定キーを追加するときは、必ずここに定数を足してから使う。** 文字列を直接埋め込むと、キー名の変更漏れに気づけなくなる。
詳細な設定キー一覧は「設定・環境変数リファレンス」ページを参照する。
