## 詳細

#### コーディングの注意点
  [header_4] 概要
    　GCはheapに割り当てられているメモリを解放する仕組みである。割り当てられるメモリの量がある閾値を超えたり、割り当てできるメモリがなくなった場合、GCが発生して、ゲームがカクつく。GCの発生を減らせば、ゲームがよりスムーズになる。
    　概して、heap割り当てを抑えるため、下記の方針でコーディングすることが望ましい：
　・ロード時にオブジェクトをキャッシュする
　・ゲーム中の処理で極力newしない
　・大量で頻繁に生成/消滅するものに対してobject poolingを活用する
　・内部でメモリ割り当てが発生するコードは書かない
    　本資料は、ゲーム中にGCの発生を抑えるため、注意すべきことを記載している。
  [header_4] インゲーム中に、オブジェクトの作成・破棄を回避する
    　オブジェクトを作成する（参照型のnewや、Instantiate）時に、heapにメモリが割り当てられる。これはGC発生に繋がる。
    **NGなこと：**
・Update/FixedUpdate/LateUpdate内でnewする
・ループ処理内newする
・頻繁に呼ばれる処理内でnewする
・頻繁に生成/消滅されるもの（ザコ敵、弾など）をInstantiate/Destroyする
    **やるべきこと：**
・フィールドにして、ローディング段階でnewしてキャッシュしておく
・Object Poolingを活用する
　参考：[https://huchat-gamedev.net/explanation-object-pool/](https://huchat-gamedev.net/explanation-object-pool/)
  [header_4] コレクションの扱い方
    　前述にも書かれているが、基本的に「事前にnew」、「容量確保」、「使い回し」という方針となる。
　なお、一部の場合のforeachと、Linq全般は内部でメモリ割り当てが発生するので、インゲームの処理内では使うのを避けること推奨する。
    **NGなこと：**
・むやみにforeachを使う
　一部のコレクションはforeachでループする場合にBoxingが発生し、
　メモリが割り当てられる。
　参考：[https://blog.virtualcast.jp/blog/2020/03/foreach_gc_alloc/](https://blog.virtualcast.jp/blog/2020/03/foreach_gc_alloc/)
・Linqメソッドを使う
　とても便利だが、使うたびのイタレータが生成する。
　なお、条件指定のラムダ式、ToList()などもメモリ割り当てに繋がる。
    **やるべきこと：**
・代わりにforを使う
・Linqを禁止
・インゲームに発生する処理でのnewを避け、代わりに初期化段階で確保しておく
  [header_4] boxingの回避
    　boxingは、intやstructなどの値型をobjectやインターフェースなどの参照型に変換する処理である。もともとstackにある値をheapにコピーすることになり、GCが発生する原因となる。
　boxingが発生する場合がほとんど、値型を参照型/インターフェースとして扱おうとする場合。
    **回避すべきこと：**
・object型変数に値型や列挙型を代入する
・ArrayListの使用
・インターフェース経由の呼び出し、代入
　例：インターフェースFooを実装した構造体StructAを、Foo型の変数に代入する。
・引数にparams object[]を使ったメソッド
　呼び出し時、配列の割り当てと渡された引数数分のboxingが発生する。
・Nullableを使う（`int? x = 10;`）
　その本質はboxingに類似した、値型を「nullを許容できる型」への変換をしている。
・文字列の一部の使い方（後述）
  [header_4] 文字列の扱い方
    　C#では文字列は「不変な参照型」であり、heapに割り当てられます。頻繁な文字列生成や連結も、GCの発生に繋がる。
　なお、変数埋め込み（`$”HP : {hp}”`）の時、boxingも発生することもある。
    **NGなこと：
**・「+」を使って文字列を連結する
　使うたびに新しい文字列が作成されるので、メモリ割り当てが発生する。
・文字列に変数を埋め込む。実行する度に新しいheap割り込みが発生する。
　例えば：`int hp = 10; string log = $“HP : {hp}”;`
　この場合、内部でhpがobjectに変換されるため、boxingが発生する。
・ビルドデータにUnityのDebug.Log系を残す
　UnityのDebug.Logはboxing、フォーマット、追跡などいろいろしているので、
　メモリ消費が激しい。ビルドデータに残っていると性能への影響が出る。
    **やるべきこと：**
・文字列を連結する時、StringBuilderを使用する
　使い回しと、再利用の前にClearも忘れずに
・頻繁に使われる文字はキャッシュするか、constで定数化する
・時刻のような文字は、「00～59」の文字を配列などに入れて、
　使うときインデックスなどで取り出すという手もある
・`#if !UNITY_EDITOR`や、独自実装のloggerなどで、ビルドデータで
　Debug.Logを遮断する仕組みを入れる
  [header_4] ラムダ式/匿名関数について
    　C#のラムダ式/匿名関数には、「キャプチャ」という概念があり、式外部の変数を使うことを呼ぶ。キャプチャしている匿名関数が実行されるたびにクロージャが発生して、メモリ消費が発生する。
　キャプチャしていなければ、内部でラムダ式がキャッシュされるので、メモリ消費の心配はない。
　※「IL2CPPの場合キャプチャしなくても呼ばれるたびにメモリ消費する」という情報があった。影響が出ている場合調査すべき。
```C#
// 例：

// OK：キャプチャしていないラムダ式
Func<int, int> f = x => x * 2;

// NG：キャプチャしているラムダ式
int a = 10;
Func<int> f = () => a + 1; // <- 式外部の変数「a」を使っている
```
    
  [header_4] 構造体を使う時の注意点
    　「構造体は値型で、そのメモリがstackに割り当てられる」とされているが、boxingされたり、中身に参照型が定義されたりすると、heapへのメモリ割り当てが発生するので、注意すべき。
```C#
// よくある例：

// 中身に参照型がある
struct MyData
{
    public int value;
    public string name; // stringが参照型のため、この変数の中身がheapにある
}

// インターフェースを実装する場合
interface IFoo
{
    void Do();
}

struct MyStruct : IFoo
{
    public void Do() {}
}

MyStruct s = new MyStruct();
IFoo foo = s; // インターフェースとして使っているため、boxingが発生する

void Call(IFoo foo) {}
Call(s); // 同様に、インターフェースとして使われている
```

#### UnityのNonAlloc APIを使おう
  　NonAlloc APIは、一部のAPIに対して、Unity公式が提供した「NonAlloc」版である。これらのAPIはAllocを削減できる作りとなっている。値設定の方法が違うので、使い方も通常版と異なる。
  　例えば、「Physics.BoxCastAll」の戻り値がhitした対象の配列であり、呼び出すたびに新しい配列が生成されるので、Allocが発生する。「Physics.BoxCastNonAlloc」は事前にnewされた配列を引数として受け取り、hitした対象をその配列に書き込むので、Allocが発生しない。
  　ただし注意すべき点として、事前に配列をnewする時に要素数を検討することが必要。
  - Physics.BoxCastAll → Physics.BoxCastNonAlloc
  - Physics.CapsuleCastAll → Physics.CapsuleCastNonAlloc
  - Physics.RaycastAll → Physics.RaycastNonAlloc
  - Physics.SphereCastAll → Physics.SphereCastNonAlloc
  - Physics.OverlapBox → Physics.OverlapBoxNonAlloc
  - Physics.OverlapCapsule → Physics.OverlapCapsureNonAlloc
  - Physics.OverlapSphere → Physics.OverlapSphereNonAlloc
  使用例：
```C#
public class BoxCastNonAllocExample : MonoBehaviour
{
    // ボックスキャストのパラメータ
    public Vector3 boxCenter = Vector3.zero;
    public Vector3 boxHalfExtents = new Vector3(1f, 1f, 1f);
    public Vector3 castDirection = Vector3.forward;
    public float maxDistance = 10f;
    public Quaternion orientation = Quaternion.identity;
    public LayerMask layerMask;

    // 結果を格納するための配列を事前に用意しておく
    private RaycastHit[] results = new RaycastHit[10];

    void Update()
    {
        // BoxCastNonAlloc は、指定した配列にヒット情報を書き込み、書き込まれた数を返す
        int hitCount = Physics.BoxCastNonAlloc(
            boxCenter,
            boxHalfExtents,
            castDirection,
            results,  // <- 事前に用意した配列
            orientation,
            maxDistance,
            layerMask
        );

        Debug.Log($"BoxCastNonAlloc hits count: {hitCount}");

        // 実際のヒット情報は配列resultsの先頭からhitCount分だけ有効
        for (int i = 0; i < hitCount; i++)
        {
            RaycastHit hit = results[i];
            Debug.Log($"Hit object: {hit.collider.name} at distance: {hit.distance}");
        }
    }
}
```
  ※Physics2DのNonAlloc APIも存在しますが、KillChordは3Dゲームなので省略とします。

#### Incremental GCについて
  　GCが発生する前提の話になるが、UnityにはGCを和らげる仕組み「Incremental GC」が存在する。
　Incremental GCをオンにすると、GCが発生する時、一気にメモリを解放するではなく、複数フレームに分散して解放処理を行って行くことで、ゲームのカクつきを減らすことができる。

#### Span<T>について
  　Span<T>／ReadonlySpan<T>は配列や文字列などの連続したデータにアクセスする時に利用する構造体型で、パフォーマンス向上のためによく用いられる。
  　Spanを利用する場面として、一つは配列の一部を切り抜てアクセスしたい時。Spanを使わない場合、配列の一部を取得しようとすると（例えばstring.substring()）、その一部のデータがコピーされて新しいデータになり、メモリ割り当てが発生する。Spanは配列要素の参照だけ持っているので、データコピーが発生しない。
```C#
// 例
public class SlicingOptimization
{
    public void Traditional(byte[] array)
    {
        // 従来の方法 - 新しい配列が作成される
        var slice = new byte[10];
        Array.Copy(array, 0, slice, 0, 10);
    }

    public void Optimized(byte[] array)
    {
        // Span<T>を使用 - 新しいメモリ割り当てなし
        Span<byte> span = array.AsSpan();
        Span<byte> slice = span.Slice(0, 10);
    }
}
```
  　もう一つは、stackalloc式と併せて使用することで、stack上にメモリを確保して、そのメモリを用いて高速で処理できる一時配列を作成することもできる。stackで割り当てられたメモリは、処理スコープから抜けるとすぐ解放されるので、heap割り当てやGCが発生しない。
```C#
// 例
public class StackAllocationOptimization
{
    public void ProcessLargeArray(byte[] largeArray)
    {
        // スタック上に一時バッファを確保
        Span<byte> buffer = stackalloc byte[1024];
        
        // バッファを使用して処理
        for (int i = 0; i < largeArray.Length; i += buffer.Length)
        {
            int count = Math.Min(buffer.Length, largeArray.Length - i);
            largeArray.AsSpan(i, count).CopyTo(buffer);
            ProcessBuffer(buffer[..count]);
        }
    }

    private void ProcessBuffer(Span<byte> buffer)
    {
        // バッファ処理ロジック
    }
}
```
  　ただし、Spanを利用する際に、いくつか注意すべき点がある：
　・stackallocでstackを確保する場合、大きすぎるとStackOverflowの危険性がある。
　・非同期メソッドでは、内部的でメソッドのデータをクラス化してheapに
　　割り当てるので、ref struct型であるSpan<T>は使えない。
　　代わりに、機能が類似でheapに割り当てられるMemory<T>を使うべき。
　・Spanはクラスや構造体のフィールドにすることができない。
　・Spanはboxingできない。
