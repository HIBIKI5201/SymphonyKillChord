### 結論
装備しているスキルの構成に応じて、戦闘中 BGM のフレーズを **CRI セレクターで小節ごとに切り替える**仕組みを実装した。曲自体は差し替えず、原曲フレーズと各スキル専用フレーズを、音楽的に同期させたまま小節単位で入れ替える。
切り替えの順番（シーケンス）は装備スキル数に応じて構築する。
- **2スキル装備時** — `[原曲, スキル1, 原曲, スキル2]` の4小節ループ
- **3スキル装備時** — `[原曲, スキル1, スキル2, スキル3]` の4小節ループ
毎フレーム小節の変わり目を監視し、変わったタイミングで次に鳴らすセレクターラベルを CRI に予約する。実際の音の切り替えは CRI 側のブロック境界で反映される。

### 注意事項
- `**MusicPlayerExtension**`** は既存クラスへの一旦の拡張クラスであり、将来的にはこの中身を **`**MusicPlayer.cs**`** 本体へ統合することを目的としている**。現状は CRI の `SetSelectorLabel` 呼び出しをラップしているだけ。
- **ビート同期情報がキューに埋め込まれていないと、CRI のコールバックは一切発火しない**。後述のイベント駆動方式（[案A](/p/38a7e7b728bf803fa9f1ea76057c87a4?pvs=25#7b49fe60691c480bb257a3c7287a5d5b)）を採用する場合は AtomCraft 側のオーサリングが前提となるため、**サウンド／デザイナーさんと要相談**。
- 小節判定に使う「拍」は `MusicSyncState` が「再生時間 ÷ BPM」から算出した値を参照している。この BPM はオーサリングデータ由来ではなく、**現状は手入力のテスト値**（`MusicSyncView` の `_testBpm`）である。プロジェクト全体の音楽同期がこの「手動 BPM ＋ 時間計算」方式で統一されている。
- セレクター名（`Selector_BGM`）と各ラベル名（`SelectorLabel_S00` 等）は CRI の ACB 定義と完全一致している必要がある。一致していないと切り替わらない。
- `BgmSelectorLabelTable` の原曲ラベル（`_originalLabel`）が未設定だと、原曲フレーズの位置に空ラベルが送られてしまう。アセット側の設定漏れに注意。
- InGameSceneに`EquipmentInitializer`を配置してください

### 機能の概要
装備スキルからセレクターシーケンスを構築し、小節ごとに切り替えるサービスを新規実装。主な特徴は以下の通り：
- **スキル構成からのシーケンス構築** — 装備スキルIDを `BgmSelectorLabelTable` でラベル名に変換し、2スキル／3スキルそれぞれの4小節ループ配列を生成する
- **小節同期での切り替え** — 小節の変わり目を検出し、次に鳴らすラベルを CRI に予約。切り替えは次のブロック頭で音楽的に揃って反映される
- **データ駆動の対応表** — スキルID → セレクターラベル名の対応を `ScriptableObject`（`BgmSelectorLabelTable`）で外部設定でき、コード変更なしに割り当てを変えられる
- **CRI 拡張の集約** — セレクター操作を `MusicPlayerExtension` に集約。将来 `MusicPlayer` 本体へ統合する前提の暫定アダプタ

### 実装されたコンポーネント説明

#### 全体アーキテクチャ
```Plain Text
EquipmentBgmInitializer (MonoBehaviour, シーンに配置)
  ├─ Start()  : ServiceLocator から MusicPlayer / SkillBuildDefinition / MusicSyncState を取得
  │             → EquipmentBgmService を生成して ServiceLocator に登録
  └─ Update() : MusicSyncState.CurrentBeat を Service.Tick() に渡す（小節監視）

EquipmentBgmService
  ├─ BuildSequence() : 装備スキル + BgmSelectorLabelTable からラベル列を構築
  │      2スキル: [原曲, S1, 原曲, S2]  /  3スキル: [原曲, S1, S2, S3]
  └─ Tick(currentBeat) : 小節の変わり目を検出し、次のラベルを CRI に予約

BgmSelectorLabelTable (ScriptableObject)
  └─ スキルID → セレクターラベル名 の対応表（+ 原曲ラベル）

MusicPlayerExtension
  └─ SetSelectorLabel(selector, label) : CRI の SetSelectorLabel をラップ
       │
       ▼
MusicPlayer.AtomSource.player (CRI) ── セレクター切替 ──▶ 次ブロック頭で反映
```
---

#### EquipmentBgmInitializer
`MonoBehaviour`。モジュールの初期化と毎フレームの駆動を担当する。`Start()` で ServiceLocator から `MusicPlayer` / `SkillBuildDefinition` / `MusicSyncState` が登録されるまで待機し、`EquipmentBgmService` を生成して登録する。
- `Start()` — 各依存を非同期取得し、Service を生成・登録
- `Update()` — `MusicSyncState.CurrentBeat` を `Service.Tick()` へ渡す
- `OnDestroy()` — ServiceLocator から Service の登録を解除
インスペクタで対応表（`BgmSelectorLabelTable`）と、1ステップを進める間隔（小節数）を設定する。
---

#### EquipmentBgmService
装備スキルの構成に基づき、CRI セレクターを小節ごとに切り替える中核ロジック。コンストラクタでシーケンスを構築し、初期ラベルを設定する。
- `BuildSequence()` — 装備中スキルを走査し、`BgmSelectorLabelTable` でラベル名に変換してシーケンス配列を生成
- `Tick(currentBeat)` — 小節（拍 ÷ 1小節の拍数）の変わり目を検出し、次のラベルを CRI に予約
```C#
public void Tick(int currentBeat)
{
    if (_sequence.Length == 0) return;

    int currentStep = currentBeat / (BEATS_PER_MEASURE * _measuresPerStep);
    if (currentStep == _previousStep) return; // 小節が変わっていなければ何もしない
    _previousStep = currentStep;

    _queuedIndex = (_queuedIndex + 1) % _sequence.Length;
    _musicPlayer.SetSelectorLabel(SELECTOR_NAME, _sequence[_queuedIndex]);
}
```
---

#### MusicPlayerExtension
`MusicPlayer` への拡張メソッド。CRI の `CriAtomExPlayer.SetSelectorLabel` を呼び、続けて `Update()` を呼ぶことでセレクターの切り替えを反映させる。スキル発動などに伴う BGM 切り替えの窓口として使う想定。
```C#
public static void SetSelectorLabel(this MusicPlayer musicPlayer,
    string selectorName, string labelName)
{
    musicPlayer.AtomSource.player.SetSelectorLabel(selectorName, labelName);
    musicPlayer.AtomSource.player.Update(musicPlayer.PlayBack);
}
```
現状は暫定の拡張クラスであり、将来的にはこの処理を `MusicPlayer.cs` 本体へ統合する。
---

#### BgmSelectorLabelTable
スキルID と CRI セレクターラベル名の対応表を保持する `ScriptableObject`。原曲ラベルと、スキルIDごとのラベルエントリ一覧を持つ。
- `TryGetLabel(skillId, out label)` — スキルIDに対応するラベル名を返す
- `OriginalLabel` — 原曲のセレクターラベル名
コードを変更せず、アセット上でスキルとラベルの割り当てを編集できる。

### 切り替えタイミングの方式と将来の選択肢
現状は **Update で毎フレーム小節の切り替えを確認する方式**を採用している。負荷面では「null チェック＋整数除算1回＋比較」程度で実コストはほぼゼロのため、最適化目的で無理にイベント駆動へ変える必要はない。一方で「コードの見通し」や「オーディオとの正確な同期」を目的に、将来イベント駆動化する余地があるため記録しておく。

#### 案A: CRI のビート同期コールバック
AtomCraft 側でキューにビート同期情報（BPM・拍子・オフセット）を埋め込めば、小節／拍が進むたびに CRI からコールバックを受け取れる。毎フレーム監視が不要になり、`barCount`（小節数）が直接取れるので自前の小節計算も `MusicSyncState` 依存も不要になる。
- イベント: `CriAtomExPlayer.OnBeatSyncCallback`
- コールバック情報: `CriAtomExBeatSync.Info`（`barCount` / `beatCount` / `bpm` / `numBeats` / `label` など）
- 購読対象は `MusicPlayer.AtomSource.player`。コールバックはメインスレッドの更新タイミングで呼ばれるため、`SetSelectorLabel` 等をそのまま呼べる
```C#
_musicPlayer.AtomSource.player.OnBeatSyncCallback += OnBeatSync;

private void OnBeatSync(ref CriAtomExBeatSync.Info info)
{
    // 最初の通知は基準小節の確定だけ（index0 が鳴っている小節）
    if (_lastBarCount == uint.MaxValue) { _lastBarCount = info.barCount; return; }
    if (info.barCount == _lastBarCount) return; // 小節の変わり目以外は無視
    _lastBarCount = info.barCount;

    if (--_measuresRemaining > 0) return;  // まだ切替小節に達していない
    _measuresRemaining = _measuresPerStep; // カウンタをリセット
    Advance();                             // 次のラベルを予約
}
// 破棄時に OnBeatSyncCallback -= OnBeatSync; を忘れずに
```
**前提:** ビート同期情報がキューに無いと `OnBeatSyncCallback` も `GetBeatSyncInfo` も一切発火しない。採用には AtomCraft のオーサリング＋ ACB リビルドが必要で、サウンド／デザイナーさんと要相談。

#### 案B: 既存の拍計算を R3 ストリーム化して購読
すでに `MusicSyncState` が毎フレーム拍を計算しているため、これを `ReactiveProperty<int>` 化して「小節が変わった時だけ」流せば、`EquipmentBgmService` は自前の Update を持たず購読するだけで済む。新しいループを足さず既存の1本のクロックに相乗りする形で、AtomCraft 側の追加作業は不要。ただし共有クラス `MusicSyncState`（コア層）への変更が必要になる。
```C#
musicSyncState.CurrentBeatRx
    .Select(beat => beat / BEATS_PER_MEASURE) // 小節番号へ変換
    .DistinctUntilChanged()                   // 小節が変わった瞬間だけ発火
    .Subscribe(_ =>
    {
        if (--_measuresRemaining > 0) return;
        _measuresRemaining = _measuresPerStep;
        Advance();
    })
    .RegisterTo(/* CancellationToken */);
```

#### 方式比較
| 方式 | 追加作業 | 備考 |
|---|---|---|
| Update （現状） | なし | 実コストほぼゼロ。 |
| 案A CRI ビート同期 | **サウンド: ACB オーサリング必須** | 最も正確。キューにビート同期情報が必要 |
| 案B R3 ストリーム | コア層（`MusicSyncState`）改修 | 既存ループ再利用・新規依存なし |
現時点ではオーサリング対応（サウンド側依頼）が必要な案Aには着手せず、**Update 方式を維持**する。将来イベント駆動化する場合は、オーサリング体制が整えば案A、そうでなければ案B が有力。
