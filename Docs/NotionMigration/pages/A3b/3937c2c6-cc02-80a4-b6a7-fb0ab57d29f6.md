## EventBusの静的イベント（static）によるライフサイクル・メモリリーク問題
状態: 解決済み（`EventBus<T>` は静的コンストラクタで `EventBusResetRegistry` にリセット処理を登録し、サブシステム初期化時に静的リスナーを消す）
`EventBus<T>` が静的（`static`）クラスとして実装され、静的イベント `_onEvent` にリスナーが登録される設計になっている。
Unityにおいては、シーンロードをまたぐ際やプレイモードを終了した際、明示的に `Unregister` が呼ばれなかったリスナー（ゲームオブジェクトやコンポーネント等）への参照が static イベントに残ったままになり、
- メモリリーク（解放されるべきオブジェクトがGCされない）
- すでに破壊されたオブジェクトに対するイベント送信による `MissingReferenceException` / 空参照エラー
といった致命的な不具合を容易に引き起こす。

## ServiceLocator（サービスロケーターパターン）への依存と依存関係のブラックボックス化
状態: 未解決（方針判断が必要。2026-07-16 時点で 137 箇所・49 ファイル。大半は Composition 層の初期化クラスで使っている）
`IngameComposition` 等において、`ServiceLocator.TryGetInstance` を使った動的なインスタンス取得が多用されている。

可能な限りコンストラクタインジェクションや DI フレームワークを使い、エントリポイント（Composition Root）で明示的に依存関係を注入する設計へ移行すべきである。

## RingBuffer<T>.AsReadonlySpan() における stackalloc と副作用
状態: 未解決（`RingBuffer.cs` は同じ実装のまま、`RhythmState` から使われている）
`AsReadonlySpan()` は、バッファの開始位置が 0 でないとき、`stackalloc` で配列サイズの一時バッファを取り、内容を並べ直して `_head` を 0 に戻す。
取得だけのつもりのメソッドで内部状態が変わる。また、容量や要素サイズが大きいとスタックオーバーフローでクラッシュするおそれがある。
順番どおりに走査するイテレータや、バッファを崩さずに走査するメソッドを用意すべきである。

## HealthEntityとCharacterEntityの間の不変量管理の分散
状態: 未解決
HP の上限判定は `HealthEntity.ChangeHealth` 側、0 下限の計算とダメージ・回復の計算は `CharacterEntity` 側にあり、体力の不変量の管理が分散している。
`HealthEntity` に `TakeDamage`・`Heal` などのドメイン操作を定義し、境界条件の判定を `HealthEntity` の中に閉じ込めるべきである。

## ScenarioCsvUtilityのゲーム中における文字列アロケーション（GC Alloc）の懸念
状態: 未解決
シナリオ CSV のパース処理 `ParseCsvLine` で `StringBuilder`・`List<string>`・部分文字列・`Trim()` を多用しており、プレイ中に走ると GC によるフレーム落ちの要因になる。
`ReadOnlySpan<char>` を使うアロケーションの無いパーサーにするか、事前に ScriptableObject などへ変換して実行時はパースしない設計にすべきである。

## Adaptor層（Controller / Presenter）への UnityEngine 依存の流出
状態: 未解決（`PlayerController.cs`・`EnemyAIController.cs` とも `using UnityEngine;` のまま）
設計思想では Adaptor 層はピュア C# の伝達層だが、`PlayerController` は `Vector2`・`Vector3`・`Quaternion` を直接やり取りし、`EnemyAIController` は `Vector3` と `Debug.Log` を使っている。
必要最小限のピュア C# の値型に変換してやり取りするか、インターフェースを介して Unity の型を隠すべきである。
