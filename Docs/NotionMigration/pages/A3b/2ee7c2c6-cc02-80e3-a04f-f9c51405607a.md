### 2. 統合先「システム概要 / 音楽」の末尾（「🔄処理フロー」節の後ろ）に追加する

- ▶ 背景: 旧モックからの設計判断
  2025-11 の音楽同期戦闘モック（`Assets/DevelopProducts/Mocks/MusicBattle_Mock/`）で決めたことと、現行実装への引き継ぎを残す。
  - リズム判定の集約: モックでは、各モジュールが `InputBuffer` のイベントを直接受けて、それぞれ判定していた。判定のタイミングがモジュールごとにずれ、同じフレームで複数の判定が走るのが問題だった。そこで、音楽同期側だけが入力を受けてリズム情報を付けて配る方針にした。現行では `MusicSyncService` が拍の種類の判定（`GetCurrentBeatType`）と行動の履歴（`RhythmState`）をまとめて持つ。スキルの入力履歴は `SkillRhythmState` が別に持つ
  - 拍の種類の決め方: モックの `MusicInputHandler` は、前回の入力との間隔から最も近い拍子を選んでいた。現行は、小節の中の位置（`GetBarProgress`）を `RhythmJudgmentDefinition` の判定範囲に当てて `BeatType` を決める
  - 実行タイミングの指定: モックの「小節タイミング」構造体（小節フラグ・拍子スケール・拍数）は、現行の `ExecuteRequestTiming`（`BarFlag` と `Beat`）になった。拍子と拍数は精度の問題から `double` にそろえた
  - 予約の実行: モックの「予約内容」（発火タイミングと実行アクション）は、現行の `ScheduledAction`（アクションと `CancellationToken`）になった。発火時刻は `MusicTimingCalculator` で再生時間（秒）に換算し、早い順の優先度付きキューに入れる考え方はモックと同じである
