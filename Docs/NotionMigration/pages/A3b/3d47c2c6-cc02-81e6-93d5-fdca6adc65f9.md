## 適用する本文

すべての設定キーは`SinfoniaOperator.Core/OperatorConfigKeys.cs`に定数として定義されている。新しいキーを追加するときは、まずここに定数を足してから使う。

## 設定の読み込み優先順位
`OperatorConfig`が次の順で値を解決する。
1. JSON設定ファイル（`sinfonia-operator.env.json`が公開設定、`sinfonia-operator.secrets.json`がGit除外の秘匿設定）
2. 環境変数

CLIの第一引数以降にJSON設定ファイルのパスを渡した場合は、指定したファイルを順に読み込み、既定の場所は探さない（`index`/`serve`サブコマンドの2番目以降の引数がこれにあたる）。JSONに無いキーは環境変数から取る。引数を省略した場合は、カレントディレクトリと実行ファイル位置の祖先ディレクトリから既定のファイル名（公開設定・秘匿設定、および旧名の`sinfonia-operator.settings.json`）を探索する。

## 仕様検索Bot関連
| キー | 用途 | 既定値 |
|---|---|---|
| `SPEC_SEARCH_INDEX_PATH` | 検索インデックスファイルの保存・読込先パス | 必須（既定無し） |
| `SPEC_SEARCH_EMBEDDING_MODEL_PATH` | ONNX埋め込みモデルファイルのパス | 必須（既定無し） |
| `SPEC_SEARCH_DISCORD_GUILD_ID` | `/spec`をGuild限定登録する場合のGuild ID | 未設定ならグローバル登録 |
| `SPEC_SEARCH_TOP_K` | 検索結果の返却件数（1〜10） | 3 |
| `SPEC_SEARCH_PRIORITY_PATH` | 検索の重み付けルールJSON（`SinfoniaOperator/spec-search-priority.json`など）のパス | 未設定なら重み付けしない |
| `GEMINI_API_KEY` | AI要約に使うGemini APIキー（秘匿情報） | 未設定ならAI要約を行わない |
| `GEMINI_MODEL` | AI要約に使うGeminiのモデル名 | `gemini-3.6-flash` |

`SPEC_SEARCH_EMBEDDING_MODEL_PATH`で指定したONNXファイルと同じディレクトリに、`sentencepiece.bpe.model`という名前でトークナイザファイルを置く必要がある（パスはコード側で自動的に導出される）。

## ブランチ整理（`/branches`）関連
| キー | 用途 | 既定値 |
|---|---|---|
| `GITHUB_REPOSITORY` | ブランチ調査の対象にするリポジトリ（`owner/name`形式）。`serve`ではこれを設定したときだけ`/branches`を登録する | 未設定なら`/branches`を登録しない |
| `GITHUB_TOKEN` | GitHub APIのアクセストークン（秘匿情報） | 未設定なら匿名アクセス（レート制限が厳しい） |
| `BRANCH_CLEANUP_DISCORD_GUILD_ID` | `/branches`をGuild限定登録する場合のGuild ID | 未設定なら`SPEC_SEARCH_DISCORD_GUILD_ID`と同じ扱い |

VMへの自動配備は、`/branches`の登録ログを稼働確認に使う。そのためVMの設定には`GITHUB_REPOSITORY`を必ず入れる。

## 秘匿情報の扱い
`DISCORD_BOT_TOKEN`・`NOTION_TOKEN`・`GEMINI_API_KEY`・`GITHUB_TOKEN`は秘匿情報であり、リポジトリにコミットしない。ローカル開発では`sinfonia-operator.secrets.json`（Git除外）、GitHub Actionsでは`Secrets`、Oracle Cloud VMではVM上にのみ置く環境ファイル`/etc/sinfonia-specsearch.env`（root所有・権限600。systemdの`EnvironmentFile`として読み込む）で管理する。VMへ転送する際は、ターミナル出力や差分表示に値そのものを露出させないよう注意する（`jq`などでトークンだけを抽出して環境ファイルへ書き込む方法が安全）。
