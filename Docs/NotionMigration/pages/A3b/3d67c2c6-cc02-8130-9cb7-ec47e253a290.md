# 説明 {color="gray_bg"}
複数のUnity `BuildProfile`を順番にビルドし、それぞれを専用のサブフォルダへ出力するエディタ拡張である。
ローカルでの手動ビルド用のEditorWindowと、CI（GitHub Actions）のバッチモードから直接呼び出されるエントリポイントの両方を持ち、両者はビルド処理の中核ロジックを共有している。

# 詳細 {color="gray_bg"}

## クラス一覧
| クラス | 役割 |
|---|---|
| `AutoBuildWindow` | メニュー`Tools/AutoBuilder`から開くEditorWindow。4つの枠ごとに「Release Master Build」「Release Development Build」「Demo Master Build」「Demo Development Build」のボタンを並べ、ローカルでの一括ビルド操作を提供する。パスやBuildProfileが不正な枠はボタンの代わりにエラーを表示する |
| `AutoBuildExecuter` | ドメインリロードに耐えるビルド実行本体。`SessionState`にセッションを保存し、リロード後も続きから再開する |
| `AutoBuilder` | CI（バッチモード）用のエントリポイント。コマンドライン引数を解釈し`AutoBuildExecuter`へ処理を委譲する（`RunFromCli`）。CIがProfileごとにプロセスを分けるための、対象Profile名の書き出し（`ExportProfileNamesFromCli`）も持つ |
| `AutoBuilderSettings` | `ProjectSettings/KillChord/AutoBuilderSettings.asset`に保存される設定（枠ごとの出力先パス・対象BuildProfile配列）を保持する`ScriptableSingleton` |
| `AutoBuildSlot` / `AutoBuildMode` | 枠（ゲームデータ種別×ビルドモード）と、ビルドモード（`Development` / `Master`）を表す型 |
| `AutoBuilderProvider` | Project Settingsウィンドウ（`KillChord/AutoBuilder`）上でAutoBuilderSettingsを編集するための`SettingsProvider` |

## 仕組み

### 設定（AutoBuilderSettings）
ゲームデータ種別（Release/Demo）とビルドモード（Master/Develop）の組み合わせごとに、出力先パスとBuildProfile配列を持つ4つの枠がある。

| 枠 | パスのフィールド | BuildProfileのフィールド | 現在の出力先 | 現在登録しているBuildProfile |
|---|---|---|---|---|
| Release Master | `ReleaseMasterPath` | `ReleaseMasterBuildProfiles` | `Builds/Release/Master/` | Release_Master の4プラットフォーム |
| Release Develop | `ReleaseDevelopPath` | `ReleaseDevelopBuildProfiles` | `Builds/Release/Dev/` | Release_Dev の4プラットフォーム |
| Demo Master | `DemoMasterPath` | `DemoMasterBuildProfiles` | `Builds/Demo/Master/` | `Demo_Master_Windows`のみ |
| Demo Develop | `DemoDevelopPath` | `DemoDevelopBuildProfiles` | `Builds/Demo/Dev/` | `Demo_Dev_Windows`のみ |

現在値の正本は`ProjectSettings/KillChord/AutoBuilderSettings.asset`である。Demoの枠をWindowsだけにしているのは、体験版（TGS 2026）をPC向けにのみ配布するためである（#1555）。体験版はAndroidとWindowsの2つでビルドする方針で、Demoの枠に`Demo_Master_Android`・`Demo_Dev_Android`を足す（未実装、#2079）。
BuildProfileは`Assets/Settings/Build Profiles/`に`<種別>_<モード>_<プラットフォーム>`の形式で16個ある（Release/Demo × Master/Dev × Android/Windows/iOS/macOS）。Demoの8個だけがスクリプトシンボル`KILLCHORD_DEMO`を持ち、このシンボルの有無がBuildProfileの種別の正本になる。
パスが空、末尾がスラッシュで終わっていない、BuildProfileが空・null混入・重複している場合はいずれも`AutoBuilderProvider`のGUI上で警告が表示される。

### ローカル実行（AutoBuildWindow → AutoBuildExecuter）
1. `AutoBuildWindow`の枠ごとのボタン（例：「Demo Master Build」）を押すと`AutoBuildExecuter.Run(path, profiles)`が呼ばれる。
2. 対象の`BuildProfile`配列を順番にビルドする。出力先は`path/<ProfileName>/<ProductName><拡張子>`。
3. セッション状態（現在の処理位置、出力先、失敗有無など）は`SessionState`へJSONとして保存される。ビルドプロファイル切り替え等でドメインリロードが発生しても、`InitializeOnLoadMethod`経由で自動的に処理を再開する。
4. 同一プロファイルへの再試行回数には上限（`MAX_PROFILE_ATTEMPT_COUNT`=10）があり、超過した場合はそのプロファイルを失敗としてスキップし次へ進む。
5. ビルド中に発生したエラー/例外/アサートのログは、ドメインリロードでConsoleが消える前にセッションとは別のキーへ記録され、リロード後に再出力される。
6. 各プロファイルのビルドが成功すると、出力ディレクトリは`path/<ProfileName>.zip`へZIP圧縮されて元データは削除される（ディスク使用量を1プロファイル分に抑えるため）。ZIPは一時ファイル`<ProfileName>.zip.partial`として作り、完成してから正式な名前へ移す（未完成のファイルがリリース対象に紛れないようにするため）。WindowsのパスがMAX_PATHを超える場合も拡張長パスで読み込む。失敗した場合は出力ディレクトリごと削除され、リリース対象に含まれない。
7. 全プロファイル終了後、開始前に設定されていたBuildProfileへ復元し、手動実行時はダイアログで成否を通知する。

### CI実行（AutoBuilder.RunFromCli）
CIはUnityを1プロセスで起動して完走させ、そのまま終了するため、`AutoBuildExecuter`のようなドメインリロード耐性の仕組みは不要であり、`RunFromCli`はセッション状態を永続化しない。
- コマンドライン引数`-gameDataVariant`（`release`/`demo`）は必須である。無いか不正な値ならビルドせずに失敗する。
- `-buildMode`（`Development`/`Master`、省略時は両方）で枠を選び、`-selectedProfiles`（カンマ区切りのプロファイル名）でさらに絞り込む。名前は大文字小文字と記号を無視して部分一致で照合する。
- 選んだ枠に登録されたBuildProfileの種別（`KILLCHORD_DEMO`の有無）が`-gameDataVariant`と違う場合は、ビルド前に失敗する。
- 出力先は環境変数`UNITY_BUILD_OUTPUT_DIR`を優先し、未設定時は`<プロジェクト>/../Builds`を使用する。
- 最終的に同じ`AutoBuildExecuter.Run`を`isBatchMode: true`で呼び出し、ビルド本体のロジックはローカル実行と共有する。
- 全プロファイル終了後、`EditorApplication.Exit(exitCode)`でUnityプロセスを終了する（0: 全成功、1: いずれか失敗または例外）。
- `ExportProfileNamesFromCli`は、同じ引数（と書き出し先`-profileListFile`）を受け取り、対象のBuildProfile名をファイルへ書き出して終了する。CIはこの一覧を使ってProfileごとにUnityを起動し直す。

## `.github/workflows/BuildAndRelease.yml`との対応
CIは自前のビルドパイプラインを持たず、AutoBuilderのCLIエントリポイント（`AutoBuilder.RunFromCli`）をそのままバッチモードで呼び出しており、ローカルビルドと処理の実体は同一である。起動条件の詳細・ディスク容量の対策・リリースの公開規則は「ワークフロー / ビルドとリリース」ページにまとめている。
- トリガーは`develop`/`main`へのPRマージ、または`workflow_dispatch`による手動実行のみ。`develop`から`main`へのPRは、ディレクターが節目のタイミングで出す（「GitHub 運用規定」を参照）。
- ベースブランチから`BuildMode`を決定する（`develop`→`Development`/タグ接頭辞`dev`、`main`→`Master`/タグ接頭辞`release`）。
- ゲームデータ種別は、手動実行では入力`build_variant`（`demo`/`release`、既定`demo`）、PRマージ起動ではGitHub Environment`AutoBuildAndRelease`の変数`BUILD_VARIANT`で決まる。
- `workflow_dispatch`時のみ、Android/Windows/MacOS/iOSの各チェックボックス入力を`-selectedProfiles`引数に変換してプロファイルを絞り込める（PRマージ起動時は絞り込みなし）。
- 実行は自己ホストのWindowsランナーで行う。ホストOSで作れないmacOS/iOSのProfileは除外するため、自動リリースの実際の成果物はReleaseがAndroidとWindows、DemoがWindowsになる。
- ビルド出力先は`ProjectSettings/KillChord/AutoBuilderSettings.asset`をテキストとして直接パースし、種別とモードに対応するパス（例：`DemoMasterPath`）を取得して`UNITY_BUILD_OUTPUT_DIR`環境変数としてUnityプロセスへ渡す。
- Google Driveから最新のZIPを取得して中の`.unitypackage`を展開・配置し、展開で上書きされたGit管理のUXML・USSをHEADから復元し（`.github/scripts/RestoreTrackedUiAssets.ps1`）、`NuGetForUnity.Cli`でNuGetパッケージを復元する。
- まず`ExportProfileNamesFromCli`で対象Profile名を取得し、Profileごとに下記コマンドでUnityをバッチモード起動する（1プロセス1Profile）。
```
Unity.exe -batchmode -projectPath <repo> -executeMethod KillChord.Editor.AutoBuilder.AutoBuilder.RunFromCli -gameDataVariant <release|demo> -buildMode <Development|Master> -selectedProfiles <Profile名> -logFile <logfile>
```
- Unity側は`AutoBuildExecuter`がプロファイルごとに都度ZIP化・元データ削除まで済ませているため、CI側では再圧縮はせず、タグ名を付与してファイル名を変更・配置するのみ。
- 最後に`softprops/action-gh-release`でタグ付きのGitHub Releaseを作成し、各プロファイルのZIPを添付する。DevelopmentまたはDemoはprerelease扱いになり、「Latest」はMasterかつReleaseのときだけ付く。タグ名には種別が入らないため、体験版と製品版のリリースはタグ名では区別できない。タグに種別（Release/Demo）を入れる（未実装、#1990）。
- 一部のProfileが失敗しても、成功した分はリリースし、最後にジョブを失敗にする。
- ローカルで`RunFromCli`の再現に成功したのにCIで失敗する場合は、ビルドロジック自体よりも環境差異（Google Driveから毎回取得し直す`.unitypackage`依存関係、NuGet復元状態、`UNITY_EXE_PATH`等のシークレット・変数）を疑うべきである。

## ビルド前検証
ビルドの直前に、次の検証が順番に実行される。いずれも失敗すると`BuildFailedException`でビルドを止める。ローカル実行でもCI実行でも同じである。

| 順番 | クラス | 検証する内容 |
|---|---|---|
| 1 | `GameDataVariantBuildProcessor`（-1000） | ゲームデータ種別（`KILLCHORD_DEMO`の有無）と、Addressablesのグループ・必須エントリが合っているか。`KILLCHORD_DEMO`が共通のPlayer Settingsに入っていないか |
| 2 | `UiDocumentBuildValidator`（-300） | Title / OutGameのUXMLを依存先から再インポートし、GUIDの不整合・インポートエラー・必須コンテナの欠落が無いか（Title: TitleContainer / MenuContainer / CreditContainer、OutGame: Home / StageSelect / SkillTree / SkillBuild / SettingContainer） |
| 3 | `FontBuildValidator`（-200） | UI ToolkitとTextMesh Proの既定フォント、Dynamic Atlas・Multi Atlasの設定、必須の日本語グリフ、元TTFまでの依存、各PanelSettingsが共通のText Settingsを参照しているか。手動ではメニュー`Tools/Build/Validate Fonts`で実行できる |
| 4 | `AddressableStoreBuildValidator`（-100） | Addressablesのストア登録が正しいか |
| 5 | `AddressableKeyValidator`（0） | Addressablesのキーが正しいか |

フォントやUIを追加・変更したときは、ビルドする前に`Tools/Build/Validate Fonts`を手元で実行する。
