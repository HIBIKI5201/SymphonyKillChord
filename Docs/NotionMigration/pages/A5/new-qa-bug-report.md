## 報告先
不具合はGitHubのIssueに起票する（2026-09-22決定）。リポジトリのファイルには不具合の記録を残さない。
[bookmark] https://github.com/HIBIKI5201/SymphonyKillChord/issues
| 見つけた人 | 報告の仕方 |
|---|---|
| 開発メンバー | 自分でIssueに起票する |
| CBTのテスター | Googleフォーム（F5 不具合報告）で1件ずつ報告する。開発側が集計してIssueに起票する。テスターには起票させない |
| AIエージェント | record-problem-logスキルで記録する。書き先はIssueに変える予定である（今は`spec/plan/problem_logs/`に書く） |

## Issueの書き方
1件の不具合につき1つのIssueにする。本文には次の項目を書く。
| 項目 | 書くこと |
|---|---|
| 現象 | 何が起きたか |
| 本来の動き | 本来どうなるべきか。不具合と「仕様どおりだが不満」を分けるために必ず書く |
| 再現手順 | 順番に書く。毎回起きるか、たまに起きるか、1回だけかも書く |
| 環境 | ビルドの版番号（タイトル画面の番号、またはリリースのタグ）・プラットフォーム・端末 |
| 原因 | 分かった時点で書き足す |
| 対処 | 直した内容と、そのPR |
| 再発防止 | 同じ不具合を防ぐためにしたこと |
- QAシートの項目で見つけた場合は、項目のID（例`CBT:8-8`）を書く
- スクリーンショットや動画を添える

### 重要度
QAの重要度と同じ3段階を使う。
| 重要度 | 意味 |
|---|---|
| A | CBTに提出できない |
| B | 提出はできるが、14日間のうちに必ず直す |
| C | 本番公開までに直す |

### ラベル
| ラベル | 付けるもの |
|---|---|
| `bug` | 不具合 |
| `TGS` | TGS向けの修正 |
| `runtime-audit` | Runtime実装監査（コード品質）の指摘 |
不具合ログ専用のラベル（案`problem-log`）はまだ無い。【要確認: 作るかを八幡さんに】

## 直し方
- `hotfix/[Issue番号]`のブランチで直し、`develop`へPRを出す
- PRの本文に`Fixes #[Issue番号]`を書く。`develop`はリポジトリの既定ブランチなので、マージするとIssueが自動で閉じる
- ブランチの規則とPRの書き方は、クライアント部門 Unityプロジェクト開発規定の「GitHub運用規定」にある
[[クライアント部門 Unityプロジェクト開発規定]]

## コード品質の指摘
Runtime実装監査の指摘も、仕様ではなくコード品質の問題としてIssueにする。ラベル`runtime-audit`を付ける（2026-09-22時点で27件）。担当は決めていない。

## 仕様に関わる結論が出たとき
Issueは記録であり、仕様ではない。不具合を調べた結果、仕様を変える・書き足す結論が出たら、Notionの仕様書を直す。Issueに書いたままにしない。
