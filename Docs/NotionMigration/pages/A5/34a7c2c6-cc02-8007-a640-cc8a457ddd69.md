## SymphonyKillChordプロジェクトの場合

### ディレクトリ
以下のディレクトリにランタイム向けのソースコードを実装する。
```C#
Assets/Scripts/Runtime/
```
このディレクトリの下にあるレイヤー層のフォルダの中にファイルやフォルダを作成し実装する。
レイヤー層のフォルダは次の7つである。
| フォルダ | 層 |
|---|---|
| `0.Utility` | 横断基盤（EventBus・DataID・定数など） |
| `1.Domain` | Domain |
| `2.Application` | Application |
| `3.Adaptor` | Adaptor |
| `4.View` | View |
| `5.InfraStructure` | InfraStructure |
| `6.Composition` | Composition |
各層の役割はシステム概要の設計思想に従う。`0.Utility`をどの層から参照してよいかは【要確認: リードプログラマーに】

エディタ拡張の場合は、以下のディレクトリにエディタ向けのソースコードを実装する。
```JavaScript
Assets/Editor/Scripts/
```
このディレクトリの下にフォルダを作成し実装する。

### スクリプティング
名前空間を必ず設定する。
名前空間名は `KillChord.Runtime.[レイヤー名].[カテゴリー]`  とする。
レイヤー名はフォルダ名から番号を除いたものである。例えば`1.Domain/InGame/Skill`のファイルは`KillChord.Runtime.Domain.InGame.Skill`になる。
エディタ拡張の名前空間名は`KillChord.Editor.[カテゴリー]`とする（例`KillChord.Editor.AutoBuilder`）。

### GitHub運用規定
基本的な命名や運用規則は [[GitHub 運用規定]] に従う。
ただし、ブランチ命名の際は `feature/[段階]/[プロダクト名]/[個人名]` とする。
プロダクトの更新時は、 `feature/[段階]/[プロダクト名]/master`  に対してPRを行う。
作業者はmasterブランチにセルフマージを行ってよい。
作業が完了したら、masterからdevelopにPRする。
リードがこれを確認する。承認されれば作業者はdevelopブランチにマージを実行する。

#### ブランチの種類
| ブランチ | 用途 | PRの向き先 |
|---|---|---|
| `feature/[段階]/[プロダクト名]/[個人名]` | 通常の作業。段階には`demo`（体験版）・`beta`・`release`（製品版）・`research`（研究）・`tools`・`docs`などが入る | 同じ階層の`master` |
| `feature/[段階]/[プロダクト名]/master` | プロダクトの取りまとめ | `develop` |
| `feature/[段階]/[プロダクト名]/agent` | AIエージェントの作業。`agent`は個人名の位置に入れる | 同じ階層の`master` |
| `hotfix/[対象]` | 小さな修正 | `develop` |
| `develop` | 開発版の集約 | `main` |
ブランチ名にレイヤー名は入れない。2階層目は段階である。
`agent`をブランチ名の先頭に使わない。`agent/[作業名]`の形は旧運用である。
不具合はGitHub Issueで管理し、`hotfix/tgs-[Issue番号]-[内容]`のように`hotfix/`の下にIssue番号を入れたブランチで直して、PR本文に`Fixes #[Issue番号]`を書く（TGSの直前 2026-09-16〜09-19 から使っている）。
`designer/…`・`develop/…`（`feature/designer/master`などのデザイナー系を含む）のブランチの扱いは未決である。【要確認: designer/… と develop/… の扱いを八幡さんに】

#### 自動化
| ワークフロー | 動く条件 | 内容 |
|---|---|---|
| AutoCreateMasterBranch | `feature/`で始まり、4階層以上で、末尾が`master`でないブランチを作ったとき | 同じ階層の`master`ブランチを作る |
| ValidateFeaturePRTarget | 4階層以上の`feature/`ブランチからPRを作成・更新したとき | 向き先が同じ階層の`master`でなければ、コミットステータス`feature-pr-target`を失敗にする |
| AutoCreateDevelopPullRequest | `feature/**/master`へのPRがマージされたとき | `master`から`develop`へのDraft PRを、PRテンプレートの構成で作る。同じPRが既にある場合と、差分が無い場合は作らない |
`feature/[段階]/[プロダクト名]/agent`も「`feature/`で始まり4階層以上で、末尾が`master`でない」ブランチなので、個人名のブランチと同じくAutoCreateMasterBranchとValidateFeaturePRTargetの対象になる。
AutoCreateMasterBranchは、ブランチを作った時点の内容で`master`を作る。そのため作業ブランチと`master`が同じコミットのままになり、`master`へのマージが一度も起きずに自動のDraft PRが作られないことがある。この場合は`develop`向けのPRを手で作る。

#### PRの書き方
PRの本文は`.github/PULL_REQUEST_TEMPLATE.md`の構成で書く。
- 必須チェック: 「コンパイルエラーが無いことを確認した」「変更が関係しうるシーンでPlayModeを最低1回通した」
- 本文の節: 概要 / 原因 / 対処 / 確認済みの内容 / 未確認・残論点
- 確認できていないことは「未確認・残論点」に隠さず書く
CIやドキュメントだけを変えるPRで、PlayModeのチェックを付けられない場合の扱いは【要確認: リードプログラマーに】

#### レビュー
- `develop`へのマージには、PRと1件の承認が要る。承認の後にpushした場合は、改めて承認が要る【要確認: GitHubのruleset設定を】
- CodeRabbitが、Draftでない PRを日本語で自動レビューし、PR本文に要約を付ける。レビュー規約として指定している`Assets/Docs/AGENTS.md`は存在しないため、規約を読まずにレビューしている

#### develop から main へ
`develop`から`main`へのPRで反映する。`main`へのマージでMasterビルドのリリースが作られる。手順はビルドとリリースのページを参照する。
[[ビルドとリリース]]

#### AIエージェントの作業ブランチ
AIエージェントも実装とPRの作成を行う。レビューは人が行う。
AIエージェント（Claude Code・Codexなど）は、リポジトリ直下の`AGENTS.md`に従う。
- 編集・コミットは、`feature/[段階]/[プロダクト名]/agent`の形の作業ブランチ（例`feature/demo/just-judgement/agent`）で行う。`agent/[作業名]`は使わない
- 同じ階層の`master`へ直接コミットしない。`master`の更新は作業ブランチからのセルフマージだけで行う
- PRの本文はPRテンプレートの構成で書き、確認済み・未確認を正確に書く
- テストの実行や`develop`へのマージの可否は、依頼した人の指示に従う

### 制約
1. 担当プロダクトのディレクトリ以外は編集しない
もしくは編集してもプッシュしない
2. グローバル設定を変えたい際はリードに連絡して、マスターのブランチがまず編集を適用し、次に個人ブランチがプルして適用する
3. マスターシーンを編集するときは、チケットシステム（`Window/KillChord/TicketSystem`）でチケットを取ってから編集し、PRをマージしたらチケットを返す【要確認: 運用として決まったかをリードプログラマーに】
