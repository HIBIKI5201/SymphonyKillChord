## 適用する本文

## ビルドとリリース
> 💡 
  **このページについて**
プレイできる形のビルドが、誰の操作でどのように作られるかをまとめたページである。
ローカルでの手動ビルドと、GitHub Actionsによる自動ビルドの2系統がある。

## 自動ビルド（GitHub Actions）
通常のリリースはこちらである。**個人が手を動かす必要はない。**

### 起動する条件
`BuildAndRelease.yml`が動くのは次の2つの場合である。
| 契機 | 内容 |
|---|---|
| Pull Requestのマージ | `develop`または`main`へのPRがマージされたとき。マージせずにクローズしたPRではビルドしない |
| 手動実行 | GitHubのActions画面から起動する。下表の項目を選ぶ |

手動実行で選ぶ項目は次のとおりである。
| 項目 | 選択肢 | 既定値 |
|---|---|---|
| build_mode（ビルドモード） | `Development` / `Master` | `Development` |
| build_variant（ゲームデータ種別） | `demo`（体験版） / `release`（製品版） | `demo` |
| Android / Windows / MacOS / iOS | オン / オフ | すべてオン |
| clean_build（クリーンビルド） | オン / オフ | オフ。トラブル時だけオンにする |
| cpu_usage_percent（Unityが使うコアの割合） | 25% / 50% / 75% / 100% | 25% |

PRのマージで動く場合、ゲームデータ種別はGitHubのEnvironment`AutoBuildAndRelease`の変数`BUILD_VARIANT`で決まる。`demo`と`release`以外が入っているとビルドは失敗する。

### 毎回ビルドされるわけではない
PRがマージされるたびに走ると1日に何度もリリースが作られてしまうため、**最終リリースからの経過時間**を確認する工程が先に入っている。閾値を超えていない場合、ビルドはスキップされる。マージしたのにリリースが作られない場合、失敗ではなくこの判定である可能性が高い。
- 閾値はリポジトリ変数`RELEASE_THRESHOLD_HOURS`で決まる。未設定なら72時間である
- `develop`へのマージは`dev-`、`main`へのマージは`release-`で始まるリリースの中で最新のものと比べる
- 手動実行はこの判定を行わず、必ずビルドする

### 成果物の受け取り
ビルドが成功するとリリースとして公開される。動作確認は原則としてこのリリース物で行う。
| 項目 | 規則 |
|---|---|
| 版番号 | リポジトリ変数`VERSION_BASE_<ビルドモード>`（例`v1.0.X`）のXを、`BUILD_VERSION_<ビルドモード>`のパッチ番号で置き換える。パッチ番号はビルドモードごとに1つで、体験版と製品版で共有する |
| タグ | `dev-<版番号>`（Development）／`release-<版番号>`（Master）。今はタグに体験版・製品版の区別が入らない。タグに種別を入れる（未実装、#1990） |
| prerelease | Developmentのビルドと、体験版（demo）のビルドはprereleaseになる |
| Latest | Masterかつ製品版（release）のときだけ付く |
- アップロードは最大3回まで試す。それでも公開を確認できない場合、ZIPをArtifact`unreleased-build-<実行番号>-<試行番号>`として7日間残す。公開を確認できたときだけパッチ番号を進める
- 一部のBuildProfileが失敗・タイムアウトしても、成功した分はリリースする。失敗した分はリリースの本文に書かれ、ジョブは最後に失敗扱いになる
- Unityのログと、警告・エラー行をまとめた`workflow_issues.log`がArtifactとして残る
ストアへの登録と配信の手順は、配信・ストア登録のページにある。
[[配信・ストア登録]]

### develop と main の流れ
作業ブランチの変更は`develop`へ集め、`develop`から`main`へPRを出して反映する。`develop`から`main`へのPRは、ディレクターが節目のタイミングで出す。
| マージ先 | ビルドモード | タグの接頭辞 |
|---|---|---|
| `develop` | Development | `dev-` |
| `main` | Master | `release-` |
手動実行では、`Master`を選ぶと`main`扱い、`Development`を選ぶと`develop`扱いになる。

### 実行環境
| 項目 | 内容 |
|---|---|
| ランナー | 自己ホストのWindowsランナー（`self-hosted, windows`） |
| 同時実行 | ビルドは同時に1本だけ。後から来たものはキューで待つ |
| タイムアウト | ジョブ全体1440分、BuildProfile1つあたり7200秒 |
| Unityの場所 | リポジトリ変数`UNITY_EXE_PATH`。未設定なら`.github/unity-paths.json`と`ProjectSettings/ProjectVersion.txt`から探す |
| CPU | 自動実行は論理CPUの半分（Windowsでは最大4）。手動実行は指定した割合 |

## ローカルビルド
CIの失敗を再現したいときや、リリースを待たずに手元で確認したいときに使う。

### AutoBuilder
Unityのメニューから次を開く。
```
Tools/AutoBuilder
```
ビルド先のパスと使用するBuildProfileは`AutoBuilderSettings`（`ProjectSettings/KillChord/AutoBuilderSettings.asset`）に保存されており、体験版・製品版とMaster・Developの組み合わせごとに4つの枠がある。ウィンドウには枠ごとに「<種別> <モード> Build」のボタンが並ぶ。
| 枠 | 出力先の現在値 | 設定項目 |
|---|---|---|
| ReleaseMaster | `Builds/Release/Master/` | `ReleaseMasterPath` / `ReleaseMasterBuildProfiles` |
| ReleaseDevelop | `Builds/Release/Dev/` | `ReleaseDevelopPath` / `ReleaseDevelopBuildProfiles` |
| DemoMaster | `Builds/Demo/Master/` | `DemoMasterPath` / `DemoMasterBuildProfiles` |
| DemoDevelop | `Builds/Demo/Dev/` | `DemoDevelopPath` / `DemoDevelopBuildProfiles` |
設定は保存時に検証される。パスが空である、末尾がスラッシュでない、BuildProfileが未設定である、同じBuildProfileが重複している、といった場合はエラーになる。枠の種別とBuildProfileの種別が食い違う場合も、ビルド前に失敗する。
コマンドラインから起動する場合は`-gameDataVariant release`または`-gameDataVariant demo`が必須である。

### BuildProfile
BuildProfileはUnityの機能であり、`Assets/Settings/Build Profiles/`に置かれている。プラットフォームやシーン構成の違いはここで分かれる。
名前は`<種別>_<モード>_<プラットフォーム>`の形式で、次の16個がある。
| 項目 | 値 |
|---|---|
| 種別 | `Release`（製品版） / `Demo`（体験版） |
| モード | `Master` / `Dev` |
| プラットフォーム | `Android` / `Windows` / `iOS` / `macOS` |
- 体験版（`Demo_`）の8個だけが、スクリプトシンボル`KILLCHORD_DEMO`を持つ
- すべてのBuildProfileにシーン一覧を明示的に設定している
- AutoBuilderSettingsに登録されているのは、製品版の2枠が各4個、体験版の2枠が`Demo_Master_Windows`と`Demo_Dev_Windows`の各1個である（体験版（TGS 2026）設定。TGSに向けて体験版をPCのみにした）
- 自己ホストのWindowsランナーでは、macOSとiOSのBuildProfileを作らない。そのため自動リリースの成果物は、製品版がAndroidとWindows、体験版がWindowsになる
- 体験版はAndroidとWindowsの2つでビルドする。体験版の枠に`Demo_Master_Android`と`Demo_Dev_Android`を戻す（未対応、#2079）

## ビルドが失敗したとき
まず切り分ける。
1. **自分の変更が原因か** — 直前のコミットを外した状態でローカルビルドを試す
2. **CIだけで落ちるか** — ローカルで通るのにCIで落ちる場合、Addressablesやライセンス関連の環境差が疑わしい
3. **そもそも起動しているか** — リリース経過時間の判定でスキップされているだけでないかを確認する
切り分けた結果を添えて、プログラマーチャンネルで相談する。ログを貼る際は、**最初のエラー**から貼ること。後続のエラーは波及であることが多い。

### CIが毎回行う片付け
| 対象 | 扱い |
|---|---|
| 作業ツリー | `git clean -ffdx -e Library/`と`reset --hard`で毎回戻す |
| `Library` | ビルドを速くするため残す。空き容量が40GB未満のとき、または手動実行で`clean_build`をオンにしたときだけ消す。消しても40GB無ければ失敗する |
| RUNNER_TEMPの残り、Gradleキャッシュ、Android SDKのキャッシュ、1日より古いランナーのログ | 消す |
| NuGetキャッシュ | 残す |
`Library`が壊れていると疑われるときだけ、手動実行で`clean_build`をオンにする。

### CIが自前で補っている環境差
ローカルでは通るのにCIで落ちるときは、次の処理を疑う。
| 処理 | 内容 |
|---|---|
| 外部パッケージの展開 | Google Driveのフォルダから更新日時が最新のZIPを1つ取り、中の`.unitypackage`を展開して配置する |
| UIの復元 | 展開後、Git管理のUXML・USSと`.meta`をHEADの内容に戻す（外部パッケージがUIを上書きしてTitleのUXMLが欠けた事故への対策） |
| NuGetの復元 | `NuGetForUnity.Cli`でNuGetパッケージを復元する。無ければdotnet toolで入れる |
| 終了コードの取得 | Windows PowerShell 5.1でUnityの終了コードが取れない問題に対処している |

## その他の自動処理
リポジトリには、ビルド以外にも次のGitHub Actionsが動いている。開発中に自動で何かが起きた場合、これらが原因であることがある。
| ワークフロー | 契機 | 内容 |
|---|---|---|
| AutoCreateMasterBranch | `feature/`ブランチの作成時（4階層以上で、末尾が`master`でないもの） | 対応するmasterブランチを自動で作る |
| ValidateFeaturePRTarget | PRの作成・更新時 | `feature/`ブランチのPRが正しい向き先かを検証する |
| AutoCreateDevelopPullRequest | `feature/**/master`へのPRのマージ時 | `master`から`develop`へのDraft PRを、PRテンプレートの構成で自動作成する。同じPRが既にある場合と、差分が無い場合は作らない |
| Sinfonia Operator | 毎日7時（JST）と手動 | DiscordとNotionの管理処理を実行する |
| Deploy Sinfonia Operator | `develop`へのpush（SinfoniaOperatorのソースを変更したとき）と手動 | 仕様検索BotをOracle Cloudのサーバーへ配備する |
| Deploy Astro to GitHub Pages | `main`へのpush時 | ホームページをデプロイする |
