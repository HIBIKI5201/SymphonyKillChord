## 適用する本文

## ブランチ

### 構成

#### main ブランチ
- **目的**：安定して動作するバージョンの保持
- **内容**：
  - 動作確認済みのビルド版（Vertical Slice：垂直スライス）を保存
  - 最終的なバックアップとして機能
- **マージ**：リリースやバージカルスライスの完成時に `develop` からマージ
  - `develop` から `main` へのPRは、ディレクターが節目のタイミングで出す（main への反映でホームページのデプロイとビルドが自動で走るため。下記「自動化」参照）
---

#### develop ブランチ
- **目的**：最新の開発バージョンを統合
- **内容**：
  - 基本的には動作可能
  - 機能追加や修正によりバグが発生する可能性あり
- **マージ**：各 `feature` ブランチや `hotfix` ブランチからのマージ先
---

#### feature ブランチ
- **目的**：新機能や改善の開発
- **内容**：
  - 開発中の個別機能を隔離して作業
- **マージ**：完了後に `develop` へマージ
---

#### hotfix ブランチ
- **目的**：致命的なバグの即時修正
- **内容**：
  - `develop` へのマージ後などに発生した不具合に対応
- **マージ**：修正後は `develop`（必要に応じて `main` にも）へマージ

### 命名規則
- ロウワーチェーンケース
- ブランチ名にレイヤーは入れない
- featureはfeature/段階/プロダクト名/個人名
  - 段階は開発の段階を表す（例: `demo`、`beta`、`research`、`release`）
  - 統合先の機能開発マスターブランチは feature/段階/プロダクト名/master
  - AI エージェントが作業するときは、個人名の位置を `agent` にする（例: `feature/demo/home-tutorial/agent`）。`agent` をブランチの先頭に使わない（`agent/作業名` は旧運用）
  - `…/agent` も「feature/ で始まり 4 階層以上、末尾が master でない」ブランチなので、下記「自動化」の AutoCreateMasterBranch・ValidateFeaturePRTarget の対象になる
- デザイナーのブランチは feature/段階/プロダクト名/designer
- hotfixはhotfix/<Issue番号>
  - TGS 期の不具合修正は `hotfix/tgs-<Issue番号>` とし、PR 本文に `Fixes #<Issue番号>` を書く
- 【要確認: develop/… の扱いを八幡さんに】

### 自動化
上記のブランチ運用は、GitHub Actionsにより一部自動チェック・自動化されている。
- **AutoCreateMasterBranch**（`.github/workflows/AutoCreateMasterBranch.yml`）
`feature/`から始まるブランチが作成されると発火する。ブランチ名が4階層以上（`/`が3つ以上）かつ末尾が`master`でないことを条件に、同じ階層の`feature/.../master`ブランチが存在しなければ自動作成する。作業者が個人ブランチを切るだけで、対応する機能開発マスターブランチが用意される。
- **ValidateFeaturePRTarget**（`.github/workflows/ValidateFeaturePRTarget.yml`）
PRの作成・更新時に発火する。マージ元が`feature/`配下の個人ブランチ（4階層以上かつ末尾が`master`でない）の場合、マージ先が対応する`feature/.../master`ブランチであるかを検証し、結果をコミットステータス（`feature-pr-target`）として表示する。マージ先が不正な場合はステータスが失敗となり、正しいマージ先が提示される。
- **AutoCreateDevelopPullRequest**（`.github/workflows/AutoCreateDevelopPullRequest.yml`）
`feature/**/master` へのPRがマージされると発火する。その`master`から`develop`へのDraft PRを、PRテンプレートの構成の本文付きで自動作成する。同じ`master`から`develop`への開いているPRが既にある場合と、`develop`との差分が無い場合（「No commits between」）は作成しない。
AutoCreateMasterBranchは個人ブランチ作成時点の内容で`master`を作るため、個人ブランチと`master`が同じコミットのまま一度もマージが起きないことがある。この場合はDraft PRが作られないので、`develop`へのPRを手動で作成する。
- **Unity Build and Release**（`.github/workflows/BuildAndRelease.yml`）
`develop`または`main`へのPRがマージされると発火し、ビルドとリリースを行う。手動実行もできる。詳細はワークフローの「ビルドとリリース」ページを参照する。
- **Deploy Astro to GitHub Pages**（`.github/workflows/HomePageDeploy.yml`）
`main`へのpushで発火し、ホームページをビルドしてGitHub Pagesへデプロイする。詳細は [[ホームページ仕様]] を参照する。
- **CodeRabbit**（`.coderabbit.yaml`）
PRを日本語で自動レビューする。Draft PRはレビューしない。`.meta`・`.unity`などはレビュー対象から外している。
- **develop の保護ルール**
`develop`への変更はPR必須で、承認1件と、最後のpushの後の別の承認が必要である。【要確認: PR #1528 作成時点の設定。現在の ruleset を管理者が GitHub の設定画面で確認する】

## PR作成ガイドライン

### 目的
レビュアー（リードプログラマー）が差分やDiscordを探索することなく、
**このPR文だけでApprove/Reject/意思決定のいずれかを判断できる状態**にすること。
情報の多さではなく、判断に必要な事実が過不足なく揃っていることを優先する。
あくまでレビューを高速化するためのものであるため、マスターブランチからDevelopブランチにプルリクエストを送る際にのみこれらの手順を踏む。
【要確認: hotfix・agent などの作業ブランチも develop へ直接PRを出しており、PRテンプレートは全てのPRに挿入される。適用範囲を「master から develop へのPRのみ」とするか「develop へのPR全て」とするかをリードプログラマーに確認する】
---

### 0. PR提出前の必須フロー（最優先・例外なし）
以下の2つを満たさないPRは、内容の出来不出来に関わらず**提出禁止**とする。
1. **コンパイルエラーが無いことを確認する**
コンパイルエラーが残ったままのPRは論外。レビュー以前の問題であり、レビュアーの時間を奪う。
2. **変更が関係しうるシーンでPlayModeを最低1回通す**
コンパイルが通ることと、実際に動くことは別問題。致命的なバグ（起動不可・進行不能・クラッシュなど）を
レビュー前に自分の手で潰しておく。「関係しうるシーン」は、変更したスクリプト・アセットが
参照/使用されている全シーンを指す。複数ある場合は主要なものだけで済ませず、思いつく範囲は通すこと。
この2点は本文の「確認済みの内容」欄より前に、PRテンプレート冒頭のチェックボックスとして必須項目化されている。
チェックが入っていない・入れられない状態のPRは出さないこと。
C#・シーン・アセットを変えないPR（CI・ドキュメント・ツールだけの変更）では、2. の PlayMode の確認を必須にしない。その場合は本文でPlayModeを通していない理由を書く（例 #1827）。
---

### 1. 本文構成
以下の見出しで整形する。

#### 概要
何が起きていた不具合・要望で、何を実現したかを1〜2文で。

#### 原因
表面的な現象ではなく、技術的な原因（何と何にズレ・矛盾があったか）を書く。

#### 対処
実際に変更したコード・仕組みを具体的に。
クラス名、メソッド名、フラグ名などメモにあれば必ず含める。
「〜するように修正しました」で終わらせず、何を使ってどう実現したかまで書く。

#### 確認済みの内容
- 正常系・異常系・境界値のうち、メモに含まれるものを箇条書きで。
- どの方法で確認したか（PlayMode/実機/ユニットテストなど）を各項目に明記する。
- 影響範囲の確認（他機能への副作用チェック）があれば含める。

#### 未確認・残論点
- 確認できていない項目を隠さず明記する。
- 「多分大丈夫」で終わらせず、そう考える技術的根拠がメモにあれば併記する。根拠がなければ「根拠は未整理」と正直に書く。
- リードプログラマーの意思決定が必要な論点があれば、選択肢とそれぞれの利点・代償、自分の推しを添える。

#### 注意事項
- 断定的な自己弁護や過剰な謙遜は不要。事実ベースで簡潔に。
- 最後に「ご確認いただけますと幸いです」などの一言で締める。
- DevelopブランチへのPRの際にのみこれらを適用する
---

### 2. PR作成後の必須フロー
PRが承認され、マージする際に以下を行う。
1. 自分の作業ブランチ(名前ブランチ)の削除、マスターブランチの削除を行う
ブランチが増えすぎて、100を超えるなどの事態を防止する
2. リードプログラマーに対してマージを完了した旨を報告する
---

### 3. PRテンプレートについて
上記構成と必須チェック項目は、リポジトリの `.github/PULL_REQUEST_TEMPLATE.md` に反映済み。
GitHub上で新規PRを作成すると本文欄に自動挿入されるため、このガイドラインを見ながら手動整形する必要はない。
表示された項目を埋めるだけで、自然にこの構成に従うことになる。

## AI エージェントの運用
自律 AI エージェントのブランチ・PR 運用は、リポジトリの `AGENTS.md` で次のとおり定めている。
AI エージェントも実装・修正と PR の作成を行う。AI の変更を取り込む PR のレビューは人が行う（コード規定 CG-002）。
- 編集・修正・コミットは、指定された作業ブランチ（例: `feature/demo/just-judgement/agent`）で行う。レビュー対応も同じブランチで行う
- 同じ階層の `master` では直接編集・コミットしない。`master` は作業ブランチからのセルフマージでだけ更新する
- `feature/` で始まる作業ブランチは、同じ階層の `master` へセルフマージしてよい（例: `feature/demo/just-judgement/agent` → `feature/demo/just-judgement/master`）
- 作業ブランチから直接 `develop` へ PR を作らない。`master` への取り込み後、上記の AutoCreateDevelopPullRequest が `develop` 向けの Draft PR を作る
- 作業ブランチは `feature/段階/プロダクト名/agent` とする。`agent/〇〇` 形式（`feature/` で始まらず、PR 先を `develop` とする）は旧運用である
- PR 本文は PR テンプレートの構成で書き、確認済み・未確認を正確に書く
- テストの実行と `develop` へのマージの可否は、そのときのユーザーの指示に従う
