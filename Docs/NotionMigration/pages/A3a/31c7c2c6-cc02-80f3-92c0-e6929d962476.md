## 開発環境

### DP-001 Runtime
マスタービルド向けのソースコード。
エディタやテスト機能が含まれてはならない。
場所は `Assets/Scripts/Runtime/`。

### DP-002 Develop
開発ビルド向けのソースコード。
Runtimeモジュールにテスト機能を与える。
場所は `Assets/Scripts/Develop/`（アセンブリ `KillChord.Develop`）。

### DP-003 Editor
Unityエディタ用ソースコード。
エディタ拡張やツールを与える。
場所は `Assets/Editor/Scripts/`（アセンブリ `KillChord.Editor`）。

### DP-004 DevelopProducts
技術研究向けのソースコード。
先行研究用のデモコードを実装する。
場所は `Assets/DevelopProducts/`。

### DP-005 Demo
体験版専用のソースコード。
体験版のタイマー・強制出撃・終了演出など、製品版に含めない処理を実装する。

## **基底概念**
- 大規模に拡張性のあるシステムであること
- 仕様の変更に柔軟であること
- 大人数での開発に対応できること

### **指向**
- クリーンアーキテクチャ
- ドメイン駆動設計
- SOLID原則
- GRASP原則
- KISS法則
- クエリ・コマンド原則
- MVVM

## **アーキテクチャ**
基礎概念はクリーンアーキテクチャ。 副次概念はドメイン駆動設計。

### DP-010 依存性
ただしUnityフレームワークへの依存は許容する。 
ただしUnityライフサイクルへの依存は抑える。
つまりピュア層で
- using UnityEngine
などは許容されるが
- MonoBehaviour継承
などは許容されない

### DP-011 レイヤー
- Domain
- Application
- Adaptor
- View
- InfraStructure
- Composition
に分ける。
下層への参照を行いたい場合は、自層にinterfaceを追加し、下層がそれを実装してCompositionがDI注入する。
他モジュールへの依存は、Adaptor層のみが依存し、Composition層が依存性解決を行う。

レイヤーごとにフォルダとアセンブリを分けている。フォルダ名の先頭の番号は名前空間に含めない（コード規定 CG-040）。

| レイヤー | フォルダ | アセンブリ | 名前空間 |
| --- | --- | --- | --- |
| Utility | `Assets/Scripts/Runtime/0.Utility` | `KillChord.Utility` | `KillChord.Runtime.Utility` |
| Domain | `Assets/Scripts/Runtime/1.Domain` | `KillChord.Domain` | `KillChord.Runtime.Domain` |
| Application | `Assets/Scripts/Runtime/2.Application` | `KillChord.Application` | `KillChord.Runtime.Application` |
| Adaptor | `Assets/Scripts/Runtime/3.Adaptor` | `KillChord.Adaptor` | `KillChord.Runtime.Adaptor` |
| View | `Assets/Scripts/Runtime/4.View` | `KillChord.View` | `KillChord.Runtime.View` |
| InfraStructure | `Assets/Scripts/Runtime/5.InfraStructure` | `KillChord.InfraStructure` | `KillChord.Runtime.InfraStructure` |
| Composition | `Assets/Scripts/Runtime/6.Composition` | `KillChord.Composition` | `KillChord.Runtime.Composition` |

各レイヤーが参照できるレイヤーは、アセンブリの参照設定で固定している。参照できないレイヤーの型を使うとコンパイルエラーになる。

### DP-014 Utility（0.Utility）
横断基盤の層。ピュアクラス。
EventBus、DataID などの識別子、共通のコレクション、定数（`Collections` / `Constant` / `Identity` / `Persistent` など）を置く。
現在は Domain から Composition までの全レイヤーがこの層を参照している。
【要確認: 「どの層からも参照してよい横断基盤」として規則に書くか、参照してよい層を限定するかをリードプログラマーに確認する】

### **各レイヤーの説明**
（既存の画像を残す）

#### **DP-020 Domain**
データ層。ピュアクラス。 参照レイヤーはなし。
ロジックで使用するデータの保存層。 データに関するロジックを持つ。

#### **DP-021 Application**
処理層。ピュアクラス。 参照レイヤーはDomain。
Domainを操作してロジックを処理する。

#### **DP-022 Adaptor**
伝達層。ピュアクラス。 参照レイヤーはDomain/Application。
Applicationの処理を呼び出したり、Domainのデータを他のApplicationへ橋渡しする。 View層へデータを受け渡すViewからの入力をApplicationに受け渡す。
Viewへの受け渡しはViewModelを使用する。

#### **DP-023 View**
表示層。Unityフレームワーク。 参照レイヤーはAdaptor。
ゲームオブジェクトやレンダリングの操作を行う。 入力を受け取ってAdaptorに受け渡す。

#### **DP-024 InfraStructure**
データ転送層。Unityフレームワーク。参照レイヤーはDomain、Application、View。
ScriptableObjectやDataBaseを使用して取得する実装を行う。

#### **DP-025 Composition**
初期化層。Unityフレームワーク/ピュアクラスのハイブリッド。 参照レイヤーはDomain/Application/Adaptor/View/InfraStructure。
Domain、Application、Adaptor、View、InfraStructureのシステムの依存性注入を行う。

## **クラス設計**

### Domain層

#### DP-101 Entity
Domain層にある値が可変な参照型オブジェクト。
型は`class` 。
- ▶ サンプルコード
```C#
public class Entity
{
    public Entity(string id)
    {
        _id = id;
        _value = 0;
    }

    public string ID => _id;
    public float Value => _value;

    public void ChangeValue(float value) => _value = value;

    private readonly string _id;
    private float _value;
}
```
公開プロパティは読み取り専用にし、変更は`ChangeValue`のように意図が伝わるメソッド経由で行う。オートプロパティの`public set`は使用しない（コード規定 CG-051）。

#### DP-102 ValueObject（VO）
Domain層にある値が不変な値型オブジェクト。
型は`readonly struct` 。
- ▶ サンプルコード
```C#
public readonly struct ValueObject : IEquatable<ValueObject>, IComparable<ValueObject>
{
    public ValueObject(float value = 0)
    {
        if (value < 0) { throw new ArgumentException("value is can't negative", nameof(value)); }
        _value = value;
    }

    public float Value => _value;

    public static bool operator ==(ValueObject left, ValueObject right) => left.Equals(right);
    public static bool operator !=(ValueObject left, ValueObject right) => !left.Equals(right);
    public static bool operator <(ValueObject left, ValueObject right) => left.CompareTo(right) < 0;
    public static bool operator <=(ValueObject left, ValueObject right) => left.CompareTo(right) <= 0;
    public static bool operator >(ValueObject left, ValueObject right) => left.CompareTo(right) > 0;
    public static bool operator >=(ValueObject left, ValueObject right) => left.CompareTo(right) >= 0;

    public int CompareTo(ValueObject other) => _value.CompareTo(other._value);
    public bool Equals(ValueObject other) => _value == other._value;
    public override bool Equals(object obj) => obj is ValueObject other && Equals(other);
    public override int GetHashCode() => _value.GetHashCode();

    private readonly float _value;
}
```

### InfraStructure層

#### DP-141 Asset
InfraStructure層にある、データを入力するScriptableObjectクラス。
Domain層などに対となるクラスが存在し、それのパラメータを導入できるようにする。
種類が増えていくデータ（判定条件、演出など）は、抽象基底クラス（`XxxAssetBase`）を用意し、`[SerializeReference, SubclassSelector]` を付けたフィールド（配列 / List）でインスペクタから多態的に選択できるようにする。基底クラスは`abstract Create()`を持ち、対応するDomain層の型へ変換する。こうすると、新しい種類を足したときにインスペクタの選択肢が自動で増え、他のコードを変えずに済む。

#### DP-142 Repository
InfraStructure層に実装があり、Application層に抽象がある。
DBの取得処理やScriptableObjectなど。

### **Composition層**

#### DP-301 Initializer
Composition層にある初期化やDIを実行するクラス。
`InGameInitializationModuleBase` / `OutGameInitializationModuleBase` / `PersistentInitializationModuleBase` のいずれかを継承し、`Init()` → `ResourceLoadAsync(CancellationToken)` → `Build()` → `Ready()` の順で呼ばれるライフサイクルを実装する。
各Initializerは `ModuleName` と `Order`（実行順）を持ち、`InitializationCoordinator<TModule>` が `Order` の昇順で全モジュールをフェーズごとに実行する。いずれかのフェーズで失敗（false）を返すと、以降のフェーズは実行されない。
シーン終了時は `Shutdown()` を登録順の逆順で呼び出す。

#### DP-302 Container
Composition層にあるモジュールのサービスを包括して保持し、他サービスに伝達するクラス。
他モジュールへ公開する実行時オブジェクトは `〇〇ModuleContainer` のような専用クラスへまとめ、`ServiceLocator.RegisterInstance` で登録する。他モジュールは `ServiceLocator.TryGetInstance<T>()` で取得する。モジュール間連携は、コンストラクタDIではなく、この Container を介した ServiceLocator 経由の公開を標準とする。
【要確認: 現在のコードは `GetInstance<T>()` の呼び出しが `TryGetInstance<T>()` より多い（61 件と 18 件）。`TryGetInstance<T>()` に統一するのか、使い分けを書くのかをリードプログラマーに確認する】

#### DP-303 Debugger
Composition層にあるエディタ向け機能のクラス。
Runtime には置かず、Develop アセンブリの `Assets/Scripts/Develop/Composition/` に置く（例: `SkillBuildDebugger`）。

#### DP-306 非同期処理の型
Composition層のモジュールライフサイクル（`ResourceLoadAsync` など）は、Unityネイティブの `Awaitable` / `Awaitable<T>` を返す。
Application層・Adaptor層のユースケースやシーン遷移などのAPIは `Task<T>` / `ValueTask<T>` を返す。
両者の橋渡しが必要な箇所（Composition側の完了待機をApplication層から呼び出すなど）に限り、Application層でも `Awaitable` を使用してよい。
