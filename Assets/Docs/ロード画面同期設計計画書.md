# ロード画面×初期化モジュール同期設計計画書

- 作成日: 2026-07-13
- 対象: ロード画面の終了タイミングと、各シーンの初期化モジュール（`Init`/`ResourceLoadAsync`/`Build`/`Ready`）ライフサイクルの同期
- 調査方法: `Assets/Scripts/Runtime`のロード画面・シーン遷移・初期化モジュール関連コードの静的調査

## 1. 目的

現状、ロード画面はシーンのロード（`SceneManager`によるシーンオブジェクトグラフの読み込み）が完了した時点で終了しており、そのシーンに配置された各初期化モジュールの`Init`→`ResourceLoadAsync`→`Build`→`Ready`が完了しているかどうかを待たない。

本書は、ロード画面を管理する仕組みが「対象シーンの初期化モジュール群がすべて完了するまで」終了しないように変更するための設計をまとめる。

## 2. 現状分析

### 2.1 ロード画面が終了する条件

- `LoadingScreenView.HandleLoadingCompleted(bool success)`（`4.View/Persistent/Load/LoadingScreenView.cs:106`）が`LoadingScreenController.LoadingCompleted`イベントを受けてロード画面を非表示にする。
- `LoadingScreenController`（`3.Adaptor/Persistent/Load/LoadingScreenController.cs`）の`Begin()`（33行目）がセッションを開始して`LoadingStarted`を発火し、`LoadingSession.Complete()`/`Fail()`（160〜171行目）が`owner.End(this, success)`（100行目）経由で`LoadingCompleted`を発火する。
- **セッションを閉じる主体は`LoadingOperationExecutor.ExecuteAsync`**（`2.Application/Persistent/Load/LoadingOperationExecutor.cs:31-77`）であり、呼び出し元から渡された`operation`デリゲートが`true`を返した時点で`session.Complete()`を呼ぶ。つまりロード画面の終了条件は「`operation`デリゲートが何をもって`true`を返すか」に完全に依存している。

### 2.2 シーンロード処理そのもの

- `SceneTransitionService`（`5.InfraStructure/Persistent/SceneManagement/SceneTransitionService.cs`）の`LoadAdditiveAsync`（80行目）等は`SymphonyFrameWork.System.SceneLoad.SceneLoader.LoadScene/UnloadScene`を呼ぶだけで、シーンオブジェクトグラフの読み込みが終わった時点で`true`を返す。**初期化モジュールの存在や状態には一切関知しない。**
- `SceneTransitionUsecase`（`2.Application/Persistent/SceneManagement/SceneTransitionUsecase.cs`）は`_executor.ExecuteAsync(progress => _service.LoadAdditiveAsync(...), ct)`という形で`LoadingOperationExecutor`に処理を委譲しており、ここでも`operation`の中身はシーンロードのみである。

### 2.3 初期化モジュールのライフサイクルと実行主体

- モジュール契約は`IInitializationModule`（`6.Composition/Bootstrap/IInitializationModule.cs`）: `bool Init()` → `Awaitable<bool> ResourceLoadAsync(CancellationToken)` → `bool Build()` → `bool Ready()` → `void Shutdown()`。
- 実行順序と失敗時の扱いは共通の`InitializationCoordinator<TModule>.InitializeAsync`（`6.Composition/Bootstrap/InitializationCoordinator.cs:25-70`）が担い、Init全モジュール→ResourceLoadAsync全モジュール→Build全モジュール→Readyの順にフェーズ単位で実行する。いずれかのモジュールがいずれかのフェーズで`false`を返すと、その時点で`InitializeAsync`は`false`を返して残りをスキップする（209〜214行目でログのみ、ロールバックや`Shutdown()`呼び出しはコーディネーター側には無い）。
- このコーディネーターを起動するシーンごとの「ルート初期化クラス」が3種類存在し、**扱いが統一されていない**:

| シーン種別 | ルートクラス | モジュール実行の起動方法 | ロード画面セッションとの関係 |
| --- | --- | --- | --- |
| InGame | `IngameComposition`（`6.Composition/InGame/Bootstrap/IngameComposition.cs`） | `Start()`内で`operationExecutor.ExecuteAsync(...)`を自ら呼び、そのデリゲート内でステージシーンの追加ロード・`WaitForStageSceneReadyAsync`（215〜241行目、最大120フレーム待機）・`CollectModules()`・`_initializationCoordinator.InitializeAsync(...)`をすべて実行し、戻り値をそのままセッションの成否にしている（53〜102行目）。 | **結合済み**。モジュール初期化完了までロード画面が閉じない。 |
| OutGame | `OutGameSceneInitializer`（`6.Composition/OutGame/OutGameSceneInitializer.cs:39-65`） | `async void Start()`内で`CollectModules()`→`_initializationCoordinator.InitializeAsync(_modules, null, destroyCancellationToken)`を実行するが、`ILoadingOperationExecutor`やロードセッションを一切参照しない。失敗時も`Debug.LogError`のみ。 | **未結合**。呼び出し元（`TitleStartController`など）のロードセッションはこの完了を待たずに閉じている。 |
| Persistent | `PersistentEntryPoint`（`6.Composition/Persistent/PersistentEntryPoint.cs:36-62`） | 上記OutGameとほぼ同型の`async void Start()`。さらに`Ready()`（79〜89行目）が`LoadFirstSceneAsync()`をfire-and-forgetで呼び、初回シーンロードもモジュール初期化完了とは無関係に進む。 | **未結合**。 |

つまり「モジュール初期化完了を待ってからロード画面を閉じる」という挙動は、現状**InGameの1経路のみ**に個別実装されており、しかも`IngameComposition`自身が`ExecuteAsync`とモジュール収集・実行の両方を1クラスに抱え込む形になっている。OutGame・Persistentには同等の仕組みが無い。

### 2.4 参考になる既存パターン: `IStageSceneInstance`

`IngameComposition.WaitForStageSceneReadyAsync`（215〜241行目）は、追加ロードしたステージシーン側が`ServiceLocator`に`IStageSceneInstance`を登録するまで最大120フレームポーリングするという形で、「別シーンの初期化完了をシーン外から待つ」既存の前例になっている（登録元: `StageSceneInitializer`等、`6.Composition/InGame/Player`配下）。今回の設計はこのパターンを一般化し、OutGame・Persistentにも同種の仕組みを適用する。

## 3. 設計方針

1. 「シーンをロードする」と「そのシーンのルート初期化クラスがモジュール初期化を完了する」を、**シーン種別によらず同一のロードセッション内で連結する**。
2. ルート初期化クラス（`OutGameSceneInitializer`／`PersistentEntryPoint`、および将来的に`IngameComposition`が担っている役割）は、モジュール初期化の成否を**ログだけでなく、シーン外から観測可能な状態として公開する**。
3. シーン遷移の起点となるクラス（`TitleStartController`、`OutGameSortieUseCase`、`StageResultController`、`PersistentEntryPoint.LoadFirstSceneAsync`）側の変更は最小限にする。個別に待機ロジックを書かせず、共通の待機処理を`SceneTransitionUsecase`側に集約する。
4. 既存の`IStageSceneInstance`ポーリング方式と矛盾しない設計にし、将来的に`IngameComposition`側もこの共通機構へ寄せられるようにする。

## 4. 詳細設計

### 4.1 シーン初期化完了シグナルの導入

新規に、シーン単位の初期化完了状態を表す仕組みを`2.Application/Persistent/SceneManagement`配下に追加する。

- `ISceneInitializationReadiness`（インターフェース）: シーン名をキーに初期化の完了を問い合わせる契約。
  - `Awaitable<bool> WaitForReadyAsync(string sceneName, CancellationToken cancellationToken)`
    対象シーンのルート初期化クラスが完了を通知するまで待機し、成功可否を返す。まだ登録が無い場合は登録されるまで待つ（後述のタイムアウト付き）。
- `SceneInitializationReadinessRegistry`（実装クラス、`ServiceLocator`にPersistentスコープで登録する常駐サービス）:
  - `void BeginTracking(string sceneName)` — シーンロード開始前に呼び出し元が登録し、そのシーンの完了を待てる状態にする。
  - `void Complete(string sceneName, bool isSuccess)` — ルート初期化クラスがモジュール初期化完了後に呼び出す。
  - `Awaitable<bool> WaitForReadyAsync(string sceneName, CancellationToken cancellationToken)` — 完了通知を待つ。内部実装は`IStageSceneInstance`待機と同様のフレームポーリング、または`AwaitableCompletionSource`相当の仕組みでよい（実装時に選定）。
  - 最大待機フレーム数（例: 既存の`MAX_STAGE_READY_WAIT_FRAME = 120`に合わせる）を超えた場合はタイムアウトとして`false`を返す。

このレジストリは複数シーンが同時にロード中になるケース（例: OutGame遷移中に別のシーンも動く等）を想定し、**シーン名をキーにした辞書**で管理する（`IStageSceneInstance`が単一グローバル登録なのに対し、こちらは複数同時トラッキングに対応させる）。

### 4.2 各シーンルート初期化クラスの変更

- `OutGameSceneInitializer.Start()`（39〜65行目）: `_initializationCoordinator.InitializeAsync(...)`完了後、成否を`SceneInitializationReadinessRegistry.Complete(gameObject.scene.name, isSuccess)`で通知するように変更する。`_modules.Count == 0`の早期returnパス（42〜45行目）でも同様に`Complete(..., true)`を呼び、シーンに初期化モジュールが無い場合でも待機側がタイムアウトしないようにする。
- `PersistentEntryPoint.Start()`（36〜62行目）も同様に変更する。
- `IngameComposition`については、内部で`WaitForStageSceneReadyAsync`＋モジュール初期化を独自に行っている構造自体は維持しつつ、将来的な統一のために4.3で追加する共通待機APIと同じレジストリへ完了通知するよう揃えることを推奨する（本フェーズでは必須ではない）。

### 4.3 `SceneTransitionUsecase`の拡張

- `SceneTransitionUsecase.LoadAdditiveAsync`（86〜96行目）を、内部で`_executor.ExecuteAsync`に渡す`operation`デリゲートを拡張し、シーンロード成功後に`SceneInitializationReadinessRegistry.WaitForReadyAsync(sceneName, ct)`を続けて`await`するようにする。両方成功して初めて`true`を返す。
- `operation`実行前に`SceneInitializationReadinessRegistry.BeginTracking(sceneName)`を呼び、ロード完了前からシーンルート初期化クラスの`Start()`が先に完了通知してしまう競合（Unityのスクリプト実行順序次第であり得る）を防ぐ。
- この変更により、**ロードセッションは1つのまま**「シーンロード＋モジュール初期化」を覆うようになり、`IngameComposition`のように2重にセッションを開閉する必要がなくなる。
- `ChangeSceneAsync`・`UnloadThenChangeSceneAsync`など、内部で新規シーンを追加ロードする他のメソッドも同様に対象とする。

### 4.4 呼び出し側への影響

`SceneTransitionUsecase`内で完結するため、以下の呼び出し元はほぼ無変更で恩恵を受けられる。

- `TitleStartController.StartGameAsync`（`3.Adaptor/OutGame/Title/TitleStartController.cs:25-56`）
- `OutGameSortieUseCase.RequestSortieAsync`（`2.Application/OutGame/Sortie/OutGameSortieUseCase.cs:37-69`）
- `StageResultController.CompleteAsync`/`RetryAsync`（`3.Adaptor/InGame/Result/StageResultController.cs`）
- `PersistentEntryPoint.LoadFirstSceneAsync`（134行目付近） — ただし、こちらは`SceneTransitionController.LoadAdditiveAsync`という別経路（`ILoadingOperationExecutor`を介さない直接呼び出し）を使っているため、`SceneTransitionController`側も同じ変更を反映するか、`SceneTransitionUsecase`経由に統一するかを実装時に判断する必要がある。

### 4.5 失敗時の扱い

- ルート初期化クラスのモジュール初期化が失敗した場合、`Complete(sceneName, false)`が呼ばれ、`WaitForReadyAsync`が`false`を返す。`SceneTransitionUsecase.LoadAdditiveAsync`はこれを`operation`の失敗として扱い、`LoadingOperationExecutor`が`session.Fail()`を呼ぶ。ロード画面自体は現状の仕様通り成功・失敗どちらでも非表示になる（`LoadingScreenView.HandleLoadingCompleted`は`success`の値によらず非表示化する）。
- 初期化モジュールが失敗した状態でシーンオブジェクト自体はロード済みのまま残る点は現状の`InitializationCoordinator`の挙動（ロールバック無し）を踏襲する。ロールバックや自動リトライは本設計のスコープ外とし、必要であれば別途検討事項とする（7章に記載）。

### 4.6 タイムアウト

- `WaitForReadyAsync`に最大待機時間（フレーム数または秒数）を設け、ルート初期化クラスが存在しない・登録漏れがあるシーンでも無限待機にならないようにする。タイムアウト時は`false`を返し、失敗として扱う。
- 既存の`IngameComposition.MAX_STAGE_READY_WAIT_FRAME = 120`を踏襲した値をデフォルトとし、シーン種別ごとに調整可能にする。

## 5. 実装順序

| 順序 | 作業内容 |
| --- | --- |
| 1 | `ISceneInitializationReadiness`／`SceneInitializationReadinessRegistry`を追加し、Persistentスコープで`ServiceLocator`に登録する |
| 2 | `OutGameSceneInitializer`・`PersistentEntryPoint`のStart()完了時に`Complete()`を呼ぶよう変更する |
| 3 | `SceneTransitionUsecase`の各メソッドに`BeginTracking`→シーンロード→`WaitForReadyAsync`の待機を組み込む |
| 4 | `PersistentEntryPoint.LoadFirstSceneAsync`が使う`SceneTransitionController`経路を`SceneTransitionUsecase`経由に統一するか検討・対応する |
| 5 | 実機/エディタでOutGame・Persistentの遷移時にロード画面が初期化完了まで表示され続けることを確認する |
| 6 | （任意）`IngameComposition`を共通レジストリへ寄せて、InGame経路の二重セッション構造を解消する |

## 6. 動作確認観点

- OutGame遷移（Title→OutGame、リザルト→OutGame）で、`OutGameSceneInitializer`配下のモジュールが多い状態（意図的に重い`ResourceLoadAsync`を仕込む等）でも、ロード画面が初期化完了まで表示され続けること。
- 初期化モジュールが1つも無いシーンでロード画面が正しく（タイムアウトを待たずに）終了すること。
- いずれかのモジュールが`Build()`等で`false`を返した場合に、ロード画面が異常に長時間居座らず、失敗として終了すること。
- Persistent起動時（アプリ起動直後）に、初回シーンのモジュール初期化前にプレイヤー操作が可能になっていないこと。

## 7. リスク・要確認事項

- **二重ロードセッションの解消範囲:** `IngameComposition`は現状すでに正しく動いているため、本設計への統合（4.1後段）は必須ではなく任意とした。統合しない場合、InGame経路だけ実装方式が異なる状態が残る点は許容するかどうか要判断。
- **PersistentEntryPointの経路差異:** `LoadFirstSceneAsync`が`SceneTransitionController`（`SceneTransitionUsecase`を介さない）を直接使っているため、4.3の変更だけでは初回起動シーンには適用されない。別途対応が必要。
- **失敗時のロールバック不在:** `InitializationCoordinator`はモジュール初期化失敗時にロールバックや已完了モジュールの`Shutdown()`を行わない。本設計はこの挙動を変更しないため、失敗時にシーンが中途半端な状態で残る問題自体は別課題として残る。
- **タイムアウト値の妥当性:** ロードが重いシーン（アセット量が多い等）でタイムアウトを誤検知しないよう、実機での初期化所要時間を踏まえて調整が必要。
