# 攻撃アニメーション遷移改善計画書

- 作成日: 2026-07-17（同日改訂: プレイヤー/敵の責務分離方針を追加）
- 対象: キャラクターアニメーションのワンショット再生まわり（`CharacterAnimationView`とその周辺）
- 関連文書: `Assets/Docs/ロコモーションAnimatorController常駐BlendTree化計画書.md`（本計画の完了後に着手する後続計画。ロコモーション部分を常駐BlendTreeへ移行するが、本計画のワンショット側の変更はそのまま活きる）
- 目的:
  1. **同一攻撃アニメーションの連続再生時にブレンドさせない** — 連続攻撃で同じアニメーションが再度要求された場合、開始ブレンドを行わずそのまま頭から再生する
  2. **硬直解除後に移動を開始したら移動アニメーションへ遷移する** — 攻撃後の硬直（攻撃インターバル）が解けてプレイヤーが移動し始めたら、攻撃アニメーションの再生完了を待たずに移動アニメーションへブレンドする
  3. **プレイヤー専用の挙動を共通実装から分離する** — アニメーション機構はプレイヤーと敵で共用されているため、今回追加する挙動（および既存のスキル/BeatType対応などプレイヤー限定の仕様）が敵側へ波及しない構造にする

---

## 1. 現状整理（調査済み）

### 1.1 アニメーション再生の仕組み

このプロジェクトのキャラクターアニメーションはAnimator Controllerのステート遷移（`CrossFade`等）を使わず、**Playable API（`PlayableGraph` + `AnimationMixerPlayable`）のミキサーウェイトを毎フレーム手動計算する方式**である。

- `PlayableAnimationController`（`Assets/Scripts/Runtime/4.View/InGame/Animation/PlayableAnimationController.cs`）
  - 全クリップをMixerに接続し、`SetWeight(index, weight)`でウェイトを反映する。
  - `PlayOneShot(index)`（L100-109）は`SetTime(0.0)`で頭出しし、ウェイトを1にするだけ。現在の再生状態は一切見ない。
- `CharacterAnimationView`（`Assets/Scripts/Runtime/4.View/InGame/Animation/CharacterAnimationView.cs`）
  - `Update()`（L48-71）で毎フレーム、①`CharacterAnimationLocomotionCalculator.ApplyBaseWeights`が速度からIdle/Walkのベースウェイトを算出し、②`ApplyOverlayWeight()`（L111-148）がワンショット（攻撃・回避）のオーバーレイウェイトを上書きする。
  - オーバーレイウェイトは`CalculateOverlayWeight()`（L185-207）で「開始ブレンド（enter）→ 全開（1.0）→ 終了ブレンド（exit）」の台形カーブとして計算され、他クリップは`1 - weight`でスケールされる（L120-131）。
  - オーバーレイは`_overlayElapsedBaseTime >= _overlayBaseDuration`（クリップ長ぶんの基準時間経過）で終了し、`_overlayIndex = -1`になる（L137-147）。

### 1.2 攻撃アニメーションの要求フロー（プレイヤー）

```
PlayerView.OnAttack (PlayerView.cs:256-304)
  └→ CharacterAnimationSignal.RequestAttack(beatType / animationKey) (CharacterAnimationSignal.cs:45-73)
       └→ RequestOneShot(index, shouldNotifyDodgeEnded: false) (同 L117-135)
            ├ クリップ長・enter/exitブレンド秒を計算（CharacterAnimationOneShotTimingCalculator、既定 enter=4フレーム / exit=8フレーム @30fps）
            └→ OnRequested(CharacterAnimationRequest) 発火
                 └→ CharacterAnimationView.HandleRequestedHandler (CharacterAnimationView.cs:90-106)
                      ├ PlayableController.PlayOneShot(index)  … 無条件に頭出し＆ウェイト1
                      └ _overlayEnterBlendDuration 等を request の値で無条件に上書き
```

**課題1の原因**: `HandleRequestedHandler`は現在のオーバーレイと新規要求のインデックスを比較しておらず、同じ攻撃クリップが連続で要求されても毎回`EnterBlendDurationSeconds`（既定4フレーム）ぶんの開始ブレンドが走る。前回の攻撃の終了ブレンド中（あるいは終了直後）のポーズから頭のポーズへブレンドするため、「同じ技なのに繋ぎ目でぬるっと補間される」見た目になる。

### 1.3 硬直と移動の関係（プレイヤー）

- 「硬直」の実体は`PlayerAttackController.IsAttacking`（`AttackIntervalEvaluator.IsAttacking`、`Assets/Scripts/Runtime/3.Adaptor/InGame/Battle/PlayerAttackController.cs:60`）。
- `PlayerView.UpdateMovement`（`Assets/Scripts/Runtime/4.View/InGame/Player/PlayerView.cs:316-320`）は`IsAttacking`中のみ移動入力をゼロ化する。**`IsAttackCooldown`（再攻撃の抑制）は移動を妨げない。**
- したがって「硬直解除後に移動開始」＝「`IsAttacking`がfalseになり、移動入力によって速度（`CharacterAnimationViewModel.Velocity`）が非ゼロになる」こと。
- 速度は`PlayerView.UpdateMovement`（L348）が`_characterAnimationViewModel.SetVelocity(...)`で毎フレーム供給しており、`CharacterAnimationView.Update`（L61）が読んでいる。

**課題2の原因**: オーバーレイの寿命はクリップ長（`BaseDurationSeconds`）に固定されており、硬直時間とは独立している。攻撃クリップが硬直より長い場合、硬直が解けて移動を始めても、オーバーレイウェイトが残っている間は攻撃アニメーションが優位のまま（他クリップは`1 - weight`で減衰）となり、**歩いているのに攻撃モーションを再生し続けて滑る**。移動アニメーションへの明示的な遷移経路が存在しない。

### 1.4 プレイヤーと敵の共用状況（今回の分離対象）

アニメーション機構一式（View / Signal / Composition）は**プレイヤーと敵で完全に共用**されている。

| 利用箇所 | 使っているAPI | 備考 |
| --- | --- | --- |
| `PlayerView`（`PlayerView.cs:249, 288-289`） | `RequestDodge()`, `RequestAttack(int beatType)`, `RequestAttack(string animationKey)` | BeatType別攻撃・スキルによるアニメ置換は**プレイヤー限定の仕様** |
| `PlayerInitializer`（L259-261, 310） | `OnDodgeEnded`購読（回避終了→攻撃クールダウン開始・無敵解除） | プレイヤー限定 |
| `EnemyMoveView`（`EnemyMoveView.cs:321, 540`） | `RequestAttack()`（引数なし＝既定攻撃）, `TryRequestOneShot(key)` | 共通APIのみ使用 |
| `EnemyLifeCycle`（L161-164, 502, 516） | `AnimationComposition.Init(view, config, musicSyncState)`（`playerAttackConfig`なし）, `TryRequestOneShot`（死亡・消滅） | 共通APIのみ使用 |

現状の構造上の問題点:

- `ICharacterAnimationSignal`（`Assets/Scripts/Runtime/3.Adaptor/InGame/Animaiton/ICharacterAnimationSignal.cs`）が、共通API（`RequestAttack()`・`TryRequestOneShot`）と**プレイヤー限定API（`RequestDodge`・`OnDodgeEnded`・`RequestAttack(int)`・`RequestAttack(string)`）を1つのインターフェースに同居**させており、敵側からもプレイヤー専用APIが呼べてしまう。
- `AnimationComposition.Init`（`Assets/Scripts/Runtime/6.Composition/InGame/Animation/AnimationComposition.cs:24-28`）は`playerAttackConfig`をオプション引数で受ける形になっており、プレイヤー専用の構築ロジック（BeatType→インデックスのマップ生成）が共通クラスに混在している。
- **敵は攻撃時に移動を伴う**: `EnemyMoveView.OnBeat`は`MoveToAttack()`で移動しつつ`RequestAttack()`を呼び（`EnemyMoveView.cs:319-321`）、NavMeshAgentの`desiredVelocity`がそのまま`SetVelocity`でViewModelに流れる（同 L113-114, 150-151）。**したがって「速度が出たら攻撃オーバーレイをキャンセル」する課題2の挙動を共通実装に入れると、敵の攻撃アニメーションが移動と同時に即キャンセルされる副作用が発生する。** 分離は必須。

## 2. 分離方針（設計の骨子）

**原則: `CharacterAnimationView`（共通・骨を選ばない再生装置）は「誰のアニメか」を一切知らず、挙動の違いはすべて`CharacterAnimationRequest`に載るオプションで駆動する。オプションを立てるのはプレイヤー専用Signalだけにする。**

```
[共通レイヤー]                          [プレイヤー専用レイヤー]
ICharacterAnimationSignal               IPlayerCharacterAnimationSignal : ICharacterAnimationSignal
  ├ RequestAttack()  … 既定攻撃          ├ RequestAttack(int beatType)
  └ TryRequestOneShot(key)              ├ RequestAttack(string animationKey) … スキル置換
                                        ├ RequestDodge()
CharacterAnimationSignal                └ event OnDodgeEnded
  └ 全要求をオプションOFFで発行
                                        PlayerCharacterAnimationSignal : CharacterAnimationSignal
CharacterAnimationView                    └ 攻撃系要求のみオプションON
  └ Requestのオプションに従うだけ            （SkipEnterBlendOnSameClip / CanCancelByMovement）
```

- **敵は共通レイヤーだけを使い続ける**。共通Signalが発行する要求はオプションがすべてOFFなので、**敵の挙動は今回の変更前後でビット単位に同一**になる（課題1・課題2とも敵には適用されない）。
- 課題1（同一クリップでブレンドしない）は一見「共通でも正しい挙動」に思えるが、敵にも適用すると見た目の変化＝検証範囲の拡大になるため、**今回はプレイヤーのみONにし、敵への適用は必要になったときにオプションを立てるだけで済む形**にしておく。
- View層は`_context.ViewModel.Velocity`とRequestのオプションだけを見るため、`PlayerAttackController`等のプレイヤー固有クラスへの依存はView層に一切入らない。

### 2.1 各クラスの責務変更

| クラス | 変更後の責務 |
| --- | --- |
| `ICharacterAnimationSignal`（既存・スリム化） | 共通API（`RequestAttack()`・`TryRequestOneShot`）のみ。プレイヤー限定メンバーを削除 |
| `IPlayerCharacterAnimationSignal`（**新規**） | `ICharacterAnimationSignal`を継承し、`RequestDodge`・`OnDodgeEnded`・`RequestAttack(int)`・`RequestAttack(string)`を持つ |
| `CharacterAnimationSignal`（既存） | 共通実装。全要求をオプションOFFで発行。BeatTypeマップ・回避・スキル関連のコードを持たない |
| `PlayerCharacterAnimationSignal`（**新規**） | `CharacterAnimationSignal`を継承（または合成）。BeatType→インデックス解決・スキルキーによる攻撃置換・回避（`ShouldNotifyDodgeEnded`）を担い、攻撃系要求に`SkipEnterBlendOnSameClip`と`CanCancelByMovement`を立てる |
| `CharacterAnimationRequest`（既存） | オプション群を追加（下記3.0）。`ShouldNotifyDodgeEnded`もオプションの一部として整理 |
| `CharacterAnimationView`（既存） | オプションに従って挙動を切り替えるだけ。プレイヤー/敵の区別を知らない |
| `AnimationComposition`（既存） | 共通の`Init`から`playerAttackConfig`引数を外し、プレイヤー用の`InitForPlayer`（内部で共通Initを利用し、`PlayerCharacterAnimationSignal`を構築）を追加 |

### 2.2 呼び出し側の追随

- `PlayerView`・`PlayerInitializer`: 保持型を`IPlayerCharacterAnimationSignal`（または`PlayerCharacterAnimationSignal`）へ変更。`OnDodgeEnded`購読はプレイヤー専用インターフェースへ移る。
- `EnemyMoveView`・`EnemyLifeCycle`: **コード変更なし**（使用しているのは共通APIのみ。`EnemyLifeCycle`は元々`playerAttackConfig`を渡していないため、共通`Init`のシグネチャ変更にもそのまま適合する）。
- `CharacterAnimationPlaybackMap`の`attackIndices`（BeatTypeマップ）はプレイヤー専用データだが、敵では空のまま実害がないため**今回はマップの分割まではしない**（`PlayerCharacterAnimationSignal`だけが参照する形にAPIアクセスを限定する）。完全なデータ分離は将来課題として注記に留める。

## 3. 実装方針（課題別）

### 3.0 共通基盤: Requestオプションの導入

`CharacterAnimationRequest`（`Assets/Scripts/Runtime/4.View/InGame/Animation/CharacterAnimationRequest.cs`）に以下を追加する（構造体のまま、フラグ3つを個別プロパティにするか`CharacterAnimationOneShotOptions`構造体にまとめるかは実装時判断。既存の`ShouldNotifyDodgeEnded`も同列に整理する）。

| オプション | 意味 | 共通Signal | プレイヤーSignal |
| --- | --- | --- | --- |
| `SkipEnterBlendOnSameClip` | 有効なオーバーレイと同一インデックスの要求なら開始ブレンドを省略 | false | 攻撃系のみ true |
| `CanCancelByMovement` | 再生中に速度が歩行しきい値を超えたら終了ブレンドを前倒し開始 | false | 攻撃系のみ true |
| `ShouldNotifyDodgeEnded`（既存） | 再生完了時に回避終了を通知 | false | `RequestDodge`のみ true |

### 3.1 課題1: 同一アニメーション連続再生時の開始ブレンド抑制

**方針: `CharacterAnimationView.HandleRequestedHandler`で「現在有効なオーバーレイと同じインデックス、かつ`SkipEnterBlendOnSameClip`が立っている要求」を検出し、その場合のみ開始ブレンド時間を0にする。**

- 判定条件: `request.SkipEnterBlendOnSameClip && HasActiveOverlay() && _overlayIndex == request.Index`
  - インデックスはMixer入力＝クリップと1:1対応なので、「同じアニメーションかどうか」の判定として十分。
  - BeatTypeごとに異なる攻撃クリップが割り当てられている場合、**異なる攻撃同士は従来どおりブレンドされる**（インデックスが違うため条件に該当しない）。
  - オーバーレイが既に終了して`_overlayIndex == -1`の場合（Idle/歩きに戻った後の攻撃）は従来どおり開始ブレンドする。「別のポーズから攻撃に入る」ケースなのでブレンドが望ましい。
- 処理内容: 条件成立時は`_overlayEnterBlendDuration = 0f`として上書きする（`request.EnterBlendDurationSeconds`を使わない）。それ以外のフィールド更新と`PlayOneShot`は従来どおり。
  - `CalculateOverlayWeight`はenterブレンド0秒なら即座に1を返すため、頭出し（`SetTime(0.0)`）と同時にフルウェイトで再生される＝「そのまま再生」になる。

### 3.2 課題2: 硬直解除後の移動開始で移動アニメーションへ遷移

**方針: `CanCancelByMovement`が立った要求の再生中に速度が歩行しきい値を超えたら、その時点のウェイトから終了ブレンドを前倒しで開始する。**

`CharacterAnimationView`に以下を追加する。

- フィールド: `_canCancelOverlayByMovement`（Requestから受領）、`_isOverlayCancelling`、`_overlayCancelStartWeight`、`_overlayCancelElapsedBaseTime`
- **キャンセル開始判定**（`ApplyOverlayWeight`の先頭、またはUpdate内のオーバーレイ処理前）:
  - 条件: オーバーレイ有効 かつ `_canCancelOverlayByMovement` かつ まだキャンセル中でない かつ 通常の終了ブレンド区間に未到達（既に自然フェードアウト中なら何もしない） かつ `_context.ViewModel.Velocity.magnitude >= 歩行しきい値`
  - 歩行しきい値は`CharacterAnimationLocomotionCalculator.WALK_THRESHOLD`（現在`private const 0.1f`、`CharacterAnimationLocomotionCalculator.cs:10`）と同じ値を使う。定数を昇格するか共有定数に切り出して二重定義を避ける。
  - プレイヤーは「硬直中は移動入力がゼロ化される」既存仕様（1.3）により、速度がしきい値を超える＝硬直解除済みが保証されるため、View側で`PlayerAttackController`の状態を参照する必要はない（依存追加なし）。
  - 敵はこのオプションが立たないため、攻撃中に移動していてもキャンセルは発生しない（1.4の副作用を構造的に回避）。
- **キャンセルフェード**:
  - 開始時に`_overlayCancelStartWeight = CalculateOverlayWeight()`（現在値）を記録し、`_overlayCancelElapsedBaseTime = 0`とする。
  - 以降のフレームでは通常の台形カーブの代わりに `weight = Mathf.Lerp(_overlayCancelStartWeight, 0f, _overlayCancelElapsedBaseTime / _overlayExitBlendDuration)` を使う（経過は既存と同じく`GetBaseProgressDelta`による基準時間で進め、BPM再生速度と整合させる）。
  - 現在ウェイトからフェードを始めるため、enterブレンド途中など weight < 1 の状態でキャンセルされてもウェイトが跳ねない。
  - ウェイトの遷移先はロジック追加不要: オーバーレイウェイトが下がると既存の`otherScale = 1f - weight`（L120-131）によりベースウェイト（速度由来のWalk）が自然に立ち上がり、**歩きモーションへのクロスフェードになる**。
  - フェード完了（weight == 0 到達）で`_overlayIndex = -1`とし、キャンセル状態をリセットする。
- **新規Request受領時**（`HandleRequestedHandler`）: キャンセル関連の状態を必ずリセットする（キャンセルフェード中に次の要求が来た場合、新しいオーバーレイとして仕切り直す）。

### 3.3 課題1と課題2の相互作用

- 課題1の「同一インデックス判定」は、課題2のキャンセルフェード中も`HasActiveOverlay()`がtrueである限り有効。つまり「攻撃→移動でキャンセルフェード中→即もう一度同じ攻撃」の場合はブレンドなしで頭出しされる。フェードで下がったウェイトが1に跳ねるが、同一クリップの頭出しであり「同じアニメはそのまま再生」という今回の仕様どおりの挙動として許容する（実機確認で気になる場合のみ、キャンセル中は例外的に短いenterブレンドを残す調整を検討する）。

### 3.4 挙動の整理（受け入れ基準を兼ねる）

**プレイヤー**

| ケース | 期待挙動 |
| --- | --- |
| 同じ攻撃クリップを、前回のオーバーレイがまだ有効な間に要求 | ブレンドなしで頭から即再生 |
| 同じ攻撃クリップを、オーバーレイ終了後（Idle/歩き復帰後）に要求 | 従来どおり開始ブレンドあり |
| 異なる攻撃クリップ（BeatType違い）を連続要求 | 従来どおり開始ブレンドあり |
| 攻撃 → 硬直解除 → 移動入力あり | 攻撃アニメの残りを待たず、exitブレンド時間で歩きへクロスフェード |
| 攻撃 → 移動入力なし | 従来どおりクリップ末尾のexitブレンドでIdleへ（変化なし） |
| 攻撃 → 既に自然な終了ブレンド区間 → 移動開始 | 二重にフェードせず、自然なフェードアウトに任せる |
| 回避中（速度非ゼロ） | キャンセルされない（オプションOFF）。`OnDodgeEnded`のタイミングも従来どおり |
| キャンセルフェード中に次の攻撃入力 | 新規オーバーレイとして通常どおり開始（同一クリップならブレンドなし頭出し） |

**敵（リグレッション基準: すべて「従来と完全に同一」であること）**

| ケース | 期待挙動 |
| --- | --- |
| 敵が同じ攻撃を連続で実行 | 従来どおり毎回開始ブレンドあり（課題1は適用されない） |
| 敵が移動しながら攻撃（`MoveToAttack`） | 攻撃アニメはキャンセルされない（課題2は適用されない） |
| 敵の死亡・消滅ワンショット（`TryRequestOneShot`） | 従来どおり |
| `EnemyMoveView`・`EnemyLifeCycle`のコンパイル | ソース変更なしで通る（共通APIのシグネチャ互換を維持） |

## 6. リスク・留意点

- **速度ベースのキャンセル判定は「入力」ではなく「実速度」を見る**ため、ノックバック等の外因で速度が出るケースがあると攻撃アニメがキャンセルされる可能性がある。現状のプレイヤー移動は入力由来のみ（`PlayerController.Update`）なので問題ないが、将来外力を追加する際は判定条件の見直しが必要（本計画では既知の制約として記載に留める）。オプション駆動にしてあるため、その際もプレイヤーSignal側の判断だけで無効化できる。
- **exitブレンド時間の流用**: キャンセルフェードは既存の`ExitBlendDurationSeconds`（既定8フレーム@30fps）を使う。実機で「移動開始時の切り替えが遅い/速い」と感じた場合は、`CharacterAnimationPlaybackMap`のexitブレンドフレーム数（クリップ単位で設定可能）で調整できる。専用のキャンセル用ブレンド時間の追加は、必要になってからで良い。
- **`Mathf.Max`によるウェイト合成**（`CharacterAnimationView.cs:120`）: キャンセルフェードでオーバーレイウェイトがWalkウェイトを下回っても、攻撃クリップは通常ベースウェイト0のためフェード値がそのまま採用される。既存ロジックのまま整合するが、実装時にオーバーレイインデックスがIdle/Walkと重複しない前提であることを確認する。
- **インターフェース縮小の影響範囲**: `RequestDodge`・`OnDodgeEnded`・`RequestAttack(int)`・`RequestAttack(string)`の利用箇所は調査済みで`PlayerView`と`PlayerInitializer`のみ（`EnemyMoveView`は引数なし`RequestAttack()`と`TryRequestOneShot`のみ使用）。ただし実装時に再グレップして取りこぼしがないことを確認する。
- **将来課題（今回はスコープ外）**: `CharacterAnimationPlaybackMap`内のBeatTypeマップ（`attackIndices`）と`CharacterAnimationClipType.Dodge`など、プレイヤー色の強いデータが共通クラスに残る。実害（敵では空/未使用）がないため今回は移設しないが、プレイヤー専用アニメ仕様がさらに増える場合はPlaybackMapの分割を検討する。
