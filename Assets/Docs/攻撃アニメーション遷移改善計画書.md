# 攻撃アニメーション遷移改善計画書

- 作成日: 2026-07-17
- 対象: プレイヤーの攻撃ワンショットアニメーション再生まわり（`CharacterAnimationView`とその周辺）
- 目的:
  1. **同一攻撃アニメーションの連続再生時にブレンドさせない** — 連続攻撃で同じアニメーションが再度要求された場合、開始ブレンドを行わずそのまま頭から再生する
  2. **硬直解除後に移動を開始したら移動アニメーションへ遷移する** — 攻撃後の硬直（攻撃インターバル）が解けてプレイヤーが移動し始めたら、攻撃アニメーションの再生完了を待たずに移動アニメーションへブレンドする

---

## 1. 現状整理（調査済み）

### 1.1 アニメーション再生の仕組み

このプロジェクトのキャラクターアニメーションはAnimator Controllerのステート遷移（`CrossFade`等）を使わず、**Playable API（`PlayableGraph` + `AnimationMixerPlayable`）のミキサーウェイトを毎フレーム手動計算する方式**である。

- `PlayableAnimationController`（`Assets/Scripts/Runtime/4.View/InGame/Animation/PlayableAnimationController.cs`）
  - 全クリップをMixerに接続し、`SetWeight(index, weight)`でウェイトを反映する。
  - `PlayOneShot(index)`（L100-109）は`SetTime(0.0)`で頭出しし、ウェイトを1にするだけ。現在の再生状態は一切見ない。
- `CharacterAnimationView`（`Assets/Scripts/Runtime/4.View/InGame/Animation/CharacterAnimationView.cs`）
  - `Update()`（L48-71）で毎フレーム、①`CharacterAnimationLocomotionCalculator.ApplyBaseWeights`が速度からIdle/Walkのベースウェイトを算出し、②`ApplyOverlayWeight()`（L111-148）がワンショット（攻撃・回避）のオーバーレイウェイトを上書きする。
  - オーバーレイウェイトは`CalculateOverlayWeight()`（L185-207）で「開始ブレンド（enter）→ 全開（1.0）→ 終了ブレンド（exit）」の台形カーブとして計算され、他クリップは`1 - weight`でスケールされる（L120-131）。
  - オーバーレイは`_overlayElapsedBaseTime >= _overlayBaseDuration`（クリップ長ぶんの基準時間経過）で終了し、`_overlayIndex = -1`になる（L137-147）。

### 1.2 攻撃アニメーションの要求フロー

```
PlayerView.OnAttack (PlayerView.cs:256-304)
  └→ CharacterAnimationSignal.RequestAttack(beatType / animationKey) (CharacterAnimationSignal.cs:45-73)
       └→ RequestOneShot(index, shouldNotifyDodgeEnded: false) (同 L117-135)
            ├ クリップ長・enter/exitブレンド秒を計算（CharacterAnimationOneShotTimingCalculator、既定 enter=4フレーム / exit=8フレーム @30fps）
            └→ OnRequested(CharacterAnimationRequest) 発火
                 └→ CharacterAnimationView.HandleRequestedHandler (CharacterAnimationView.cs:90-106)
                      ├ PlayableController.PlayOneShot(index)  … 無条件に頭出し＆ウェイト1
                      └ _overlayEnterBlendDuration 等を request の値で無条件に上書き
```

**課題1の原因**: `HandleRequestedHandler`は現在のオーバーレイと新規要求のインデックスを比較しておらず、同じ攻撃クリップが連続で要求されても毎回`EnterBlendDurationSeconds`（既定4フレーム）ぶんの開始ブレンドが走る。前回の攻撃の終了ブレンド中（あるいは終了直後）のポーズから頭のポーズへブレンドするため、「同じ技なのに繋ぎ目でぬるっと補間される」見た目になる。

### 1.3 硬直と移動の関係

- 「硬直」の実体は`PlayerAttackController.IsAttacking`（`AttackIntervalEvaluator.IsAttacking`、`Assets/Scripts/Runtime/3.Adaptor/InGame/Battle/PlayerAttackController.cs:60`）。
- `PlayerView.UpdateMovement`（`Assets/Scripts/Runtime/4.View/InGame/Player/PlayerView.cs:316-320`）は`IsAttacking`中のみ移動入力をゼロ化する。**`IsAttackCooldown`（再攻撃の抑制）は移動を妨げない。**
- したがって「硬直解除後に移動開始」＝「`IsAttacking`がfalseになり、移動入力によって速度（`CharacterAnimationViewModel.Velocity`）が非ゼロになる」こと。
- 速度は`PlayerView.UpdateMovement`（L348）が`_characterAnimationViewModel.SetVelocity(...)`で毎フレーム供給しており、`CharacterAnimationView.Update`（L61）が読んでいる。

**課題2の原因**: オーバーレイの寿命はクリップ長（`BaseDurationSeconds`）に固定されており、硬直時間とは独立している。攻撃クリップが硬直より長い場合、硬直が解けて移動を始めても、オーバーレイウェイトが残っている間は攻撃アニメーションが優位のまま（他クリップは`1 - weight`で減衰）となり、**歩いているのに攻撃モーションを再生し続けて滑る**。移動アニメーションへの明示的な遷移経路が存在しない。

### 1.4 回避（Dodge）との関係（重要な制約）

- 回避も同じワンショットオーバーレイ機構を使う（`RequestDodge` → `shouldNotifyDodgeEnded: true`）。
- 回避中はコントローラー側が移動を駆動するため**速度は非ゼロ**になる。よって「速度が出たらオーバーレイをキャンセル」という単純な判定を全ワンショットに適用すると、**回避アニメーションが即座にキャンセルされてしまう**。攻撃系のワンショットに限定する仕組みが必要。
- 回避終了時は`NotifyDodgeEnded()`（`CharacterAnimationView.cs:140-143` → `CharacterAnimationSignal.cs:106-109`）で`PlayerInitializer`（L259-261）が攻撃クールダウンを開始しており、この通知タイミングを壊してはならない。

## 2. 実装方針

### 2.1 課題1: 同一アニメーション連続再生時の開始ブレンド抑制

**方針: `CharacterAnimationView.HandleRequestedHandler`で「現在有効なオーバーレイと同じインデックスの要求」を検出し、その場合のみ開始ブレンド時間を0にする。**

- 判定条件: `HasActiveOverlay() && _overlayIndex == request.Index`
  - インデックスはMixer入力＝クリップと1:1対応なので、「同じアニメーションかどうか」の判定として十分。
  - BeatTypeごとに異なる攻撃クリップが割り当てられている場合（`TryGetAttackIndex`）、**異なる攻撃同士は従来どおりブレンドされる**（インデックスが違うため条件に該当しない）。
  - オーバーレイが既に終了して`_overlayIndex == -1`の場合（Idle/歩きに戻った後の攻撃）は従来どおり開始ブレンドする。これは「別のポーズから攻撃に入る」ケースなのでブレンドが望ましい。
- 処理内容: 条件成立時は`_overlayEnterBlendDuration = 0f`として上書きする（`request.EnterBlendDurationSeconds`を使わない）。それ以外のフィールド更新と`PlayOneShot`は従来どおり。
  - `CalculateOverlayWeight`はenterブレンド0秒なら即座に1を返すため、頭出し（`SetTime(0.0)`）と同時にフルウェイトで再生される＝「そのまま再生」になる。
- Signal層・Request構造体の変更は不要（View内で完結する）。

**挙動の整理（受け入れ基準を兼ねる）**

| ケース | 期待挙動 |
| --- | --- |
| 前回と同じ攻撃クリップを、前回のオーバーレイがまだ有効な間に要求 | ブレンドなしで頭から即再生 |
| 前回と同じ攻撃クリップを、オーバーレイ終了後（Idle/歩き復帰後）に要求 | 従来どおり開始ブレンドあり |
| 異なる攻撃クリップ（BeatType違い）を連続要求 | 従来どおり開始ブレンドあり |
| 回避→同じ回避の連続（発生し得る場合） | 同ロジックが適用されるが、頭出し再生になるだけで害はない |

### 2.2 課題2: 硬直解除後の移動開始で移動アニメーションへ遷移

**方針: 「移動によるキャンセル可否」フラグをRequestに追加し、攻撃オーバーレイ再生中に速度が歩行しきい値を超えたら、その時点のウェイトから終了ブレンドを前倒しで開始する。**

#### (a) Request/Signalの拡張

- `CharacterAnimationRequest`（`Assets/Scripts/Runtime/4.View/InGame/Animation/CharacterAnimationRequest.cs`）に`bool CanCancelByMovement`を追加する。
- `CharacterAnimationSignal.RequestOneShot`（L117-135）に同フラグの引数を追加し、呼び出し元で以下のように設定する:
  - `RequestAttack(string)` / `RequestAttack(int)` … **true**（今回の対象）
  - `RequestDodge()` … **false**（1.4の制約。回避は移動でキャンセルしない）
  - `TryRequestOneShot(string, out float)`（スキル等の汎用ワンショット） … **false**（現状挙動を維持。必要になったら呼び出し元単位で切り替えられる形にしておく）

#### (b) View側のキャンセル判定とフェード

`CharacterAnimationView`に以下を追加する。

- フィールド: `_canCancelOverlayByMovement`（Requestから受領）、`_isOverlayCancelling`、`_overlayCancelStartWeight`、`_overlayCancelElapsedBaseTime`
- **キャンセル開始判定**（`ApplyOverlayWeight`の先頭、またはUpdate内のオーバーレイ処理前）:
  - 条件: オーバーレイ有効 かつ `_canCancelOverlayByMovement` かつ まだキャンセル中でない かつ 通常の終了ブレンド区間に未到達（既に自然フェードアウト中なら何もしない） かつ `_context.ViewModel.Velocity.magnitude >= 歩行しきい値`
  - 歩行しきい値は`CharacterAnimationLocomotionCalculator.WALK_THRESHOLD`（現在`private const 0.1f`、`CharacterAnimationLocomotionCalculator.cs:10`）と同じ値を使う。定数を`internal`/`public`に昇格するか、共有定数として切り出して二重定義を避ける。
  - 「硬直中は移動入力がゼロ化される」既存仕様（1.3）により、速度がしきい値を超える＝硬直解除済みが保証されるため、View側でAttackControllerの状態を直接参照する必要はない（依存追加なし）。
- **キャンセルフェード**:
  - 開始時に`_overlayCancelStartWeight = CalculateOverlayWeight()`（現在値）を記録し、`_overlayCancelElapsedBaseTime = 0`とする。
  - 以降のフレームでは通常の台形カーブの代わりに `weight = Mathf.Lerp(_overlayCancelStartWeight, 0f, _overlayCancelElapsedBaseTime / _overlayExitBlendDuration)` を使う（経過は既存と同じく`GetBaseProgressDelta`による基準時間で進め、BPM再生速度と整合させる）。
  - 現在ウェイトからフェードを始めるため、enterブレンド途中など weight < 1 の状態でキャンセルされてもウェイトが跳ねない。
  - ウェイトの遷移先はロジック追加不要: オーバーレイウェイトが下がると既存の`otherScale = 1f - weight`（L120-131）によりベースウェイト（速度由来のWalk）が自然に立ち上がり、**歩きモーションへのクロスフェードになる**。
  - フェード完了（weight == 0 到達）で`_overlayIndex = -1`とし、キャンセル状態をリセットする。攻撃は`ShouldNotifyDodgeEnded == false`なので回避終了通知まわりの挙動には影響しない。
- **新規Request受領時**（`HandleRequestedHandler`）: キャンセル関連の状態を必ずリセットする（キャンセルフェード中に次の攻撃が来た場合、新しいオーバーレイとして仕切り直す）。

#### (c) 挙動の整理（受け入れ基準を兼ねる）

| ケース | 期待挙動 |
| --- | --- |
| 攻撃 → 硬直解除 → 移動入力あり | 攻撃アニメの残りを待たず、exitブレンド時間で歩きへクロスフェード |
| 攻撃 → 移動入力なし | 従来どおりクリップ末尾のexitブレンドでIdleへ（変化なし） |
| 攻撃 → 既に自然な終了ブレンド区間に入っている → 移動開始 | 二重にフェードを開始せず、自然なフェードアウトに任せる |
| 回避中（速度非ゼロ） | キャンセルされない（`CanCancelByMovement == false`）。`NotifyDodgeEnded`のタイミングも従来どおり |
| キャンセルフェード中に次の攻撃入力 | 新規オーバーレイとして通常どおり開始（課題1のロジックとも共存: 同一クリップならブレンドなし頭出し） |

### 2.3 課題1と課題2の相互作用

- 課題1の「同一インデックス判定」は、課題2のキャンセルフェード中も`HasActiveOverlay()`がtrueである限り有効。つまり「攻撃→移動でキャンセルフェード中→即もう一度同じ攻撃」の場合はブレンドなしで頭出しされる。フェードで下がったウェイトが1に跳ねるが、同一クリップの頭出しであり「同じアニメはそのまま再生」という今回の仕様どおりの挙動として許容する（実機確認で気になる場合のみ、キャンセル中は例外的に短いenterブレンドを残す調整を検討する）。

## 4. 実装手順

1. **課題1を先行実装**（変更が`CharacterAnimationView.HandleRequestedHandler`のみで完結し、単独で検証可能なため）
   1. 同一インデックス判定とenterブレンド0化を実装
   2. エディタ実機確認: 同一攻撃の連打／異なる攻撃の交互入力／Idle復帰後の攻撃
2. **課題2を実装**
   1. `CharacterAnimationRequest`にフラグ追加 → `CharacterAnimationSignal`の各Request系メソッドを更新
   2. `CharacterAnimationView`にキャンセル判定・フェード・リセットを実装
   3. エディタ実機確認: 2.2(c)の全ケース（特に回避が誤キャンセルされないこと、BPM変化時にフェード時間が破綻しないこと）
3. **リグレッション確認**
   - 回避→攻撃クールダウン開始（`OnDodgeEnded`経由）が従来どおり動くこと
   - スキルアニメーション（`TryRequestOneShot`経由）の挙動が変わっていないこと
   - 敵など`CharacterAnimationView`を共用するキャラクターがいる場合、その攻撃・移動にも副作用がないこと

## 5. リスク・留意点

- **速度ベースのキャンセル判定は「入力」ではなく「実速度」を見る**ため、ノックバック等の外因で速度が出るケースがあると攻撃アニメがキャンセルされる可能性がある。現状のプレイヤー移動は入力由来のみ（`PlayerController.Update`）なので問題ないが、将来外力を追加する際は判定条件の見直しが必要（本計画では既知の制約として記載に留める）。
- **exitブレンド時間の流用**: キャンセルフェードは既存の`ExitBlendDurationSeconds`（既定8フレーム@30fps）を使う。実機で「移動開始時の切り替えが遅い/速い」と感じた場合は、`CharacterAnimationPlaybackMap`のexitブレンドフレーム数（クリップ単位で設定可能）で調整できる。専用のキャンセル用ブレンド時間の追加は、必要になってからで良い。
- **`Mathf.Max`によるウェイト合成**（`CharacterAnimationView.cs:120`）: キャンセルフェードでオーバーレイウェイトがWalkウェイトを下回ると、`Mathf.Max(_weights[_overlayIndex], weight)`の挙動により攻撃クリップ（通常ベースウェイト0）はそのままフェード値が採用される。既存ロジックのまま整合するが、実装時にオーバーレイインデックスがIdle/Walkと重複しない前提であることを確認する。
