# Skill モジュール依存定義書

## 1. 概要
装備スキルの編成（改造画面）、スキルツリーの解放（進行管理）、および戦闘中でのスキル発動メカニズム、リズムコマンドの入力判定を司る、アウトゲームとインゲームを繋ぐ重要モジュールです。

## 2. レイヤー構成（レイヤー別のクラス定義）
*   **Domain**:
    *   `SkillBuildDefinition` (装備しているスキルの状態を管理するドメインモデル、可変Entity)
    *   `SkillRhythmState` (スキル発動時のリズム入力コマンドシーケンス)
    *   `SkillNodeEntity` (スキルツリー上の各ノード情報)
    *   `PlayerStatusEntity` (ツリー解放による永続的なステータスアップ Entity)
*   **Application**:
    *   `SkillBuildUseCase` (スキルの装備・スロット操作、セーブ・ロード処理)
    *   `SkillTreeService` (スキルツリー解放ロジック)
    *   `SkillCheckService` (インゲーム中のリズムコマンド入力の正誤判定サービス)
*   **Adaptor**:
    *   `SkillBuildPresenter` (編成状態をView用の ref struct DTO に変換して伝達)
    *   `SkillBuildController` (ViewModelの保存要求を受け取り、UseCaseに伝える)
    *   `SkillBuildViewDTO` / `SkillBuildSlotDTO` (ViewModelへ送るDTO群)
*   **View**:
    *   `SkillBuildViewModel` (UI表示状態の保持、イベントバインド)
    *   `SkillBuildScreenView` (改造画面のUI Elements/UI表示実体)
*   **Composition**:
    *   `SkillBuildInitializer` (デバッグ用のスキルリポジトリ等を注入し、依存を解決)
    *   `SkillTreeInitializer` (スキルツリー画面の初期化)

---

## 3. モジュール間依存関係
Skill モジュールが他モジュールとどのように関わっているかを定義します。

### [依存しているモジュール]
*   **Persistent/Savedata**:
    *   *依存箇所*: `SaveData`, `SavedataSystem`
    *   *詳細*: プレイヤーが解放したスキルや装備中のスキルスロットをJSONデータへ永続化・ロードするため、セーブシステムに依存します。`SkillBuildUseCase`（Application）のコンストラクタは抽象（`ISkillBuildRepository`）ではなく`SavedataSystem`の**具象クラス**を直接受け取ります（DIP違反、改善推奨ポイント）。ただし`ServiceLocator`から取得しているのは`SkillBuildUseCase`自身ではなく、呼び出し元の`SkillBuildInitializer`（Composition）であり、そこからコンストラクタ注入されています。`ISkillBuildRepository`（Addressables経由でロードされる`SkillBuildRepository`）自体は実在しますが、`SkillBuildInitializer`がView初期化用に使うのみで`SkillBuildUseCase`へは渡されておらず、DIP違反は解消されていません。
*   **InGame/Player**:
    *   *依存箇所*: `SkillTemplate`, `SkillRepository`
    *   *詳細*: プレイヤーキャラクターが扱えるスキルのアセット（ScriptableObject）や、現在入手済みのスキルデータを参照します。旧ドキュメントの`SkillData`という型名は存在せず、実際は`SkillTemplate`です。

### [依存されているモジュール]
*   **InGame/Player**:
    *   *参照箇所*: `SkillBuildDefinition`
    *   *詳細*: プレイヤーは戦闘開始時に、セーブデータから取得して本モジュールに格納されている「装備中スキル一覧」を参照して、対応するインゲーム用スキルのインスタンスをセットアップします。

---

## 4. アーキテクチャ上の特徴と評価
*   **アウトゲーム/インゲームの情報の橋渡し**:
    セーブデータに保存されるスキルのID構成（ドメイン）が、`SkillBuildUseCase` を通じて極めてシンプルに管理されており、そのデータ構造がインゲームの `PlayerInitializer` で対応するスキル実体にスムーズにバインドされる秀逸な構造になっています。
*   **改善のポイント (セーブシステムへの密結合)**:
    `SkillBuildUseCase` (Application層) のコンストラクタは `SavedataSystem` (Utility/具象) をそのまま受け取る形になっています。`SkillBuildInitializer`（Composition層）が `ServiceLocator.TryGetInstance<SavedataSystem>()` で取得した具象インスタンスをそのままコンストラクタ注入しているため、抽象を挟まない依存になっています。Application層には `ISkillBuildRepository` という抽象・実装（`SkillBuildRepository`、Addressables経由でロード）が既に存在しますが、現状は`SkillBuildInitializer`がView初期化用データの取得にのみ使っており、`SkillBuildUseCase`へは渡していません。`SkillBuildUseCase`のコンストラクタ引数を`SavedataSystem`から`ISkillBuildRepository`（またはそれに準ずる抽象）へ差し替えることで、セーブ先（JSON / DB / Cloud）の切り替えが容易になり、単体テストも可能になります。
