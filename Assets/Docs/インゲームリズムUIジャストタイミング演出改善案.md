# インゲームリズムUI ジャストタイミング演出改善案

- 作成日: 2026-07-20
- 対象: インゲーム戦闘中のリズムガイドUI（`ACLikeRhythmGuideView`）における、ジャストタイミングの視認性改善
- 前提: 本ドキュメントは演出案の検討メモであり、実装計画ではない。実装方針・優先度は別途検討のうえ決定する。
- 参照元: `Docs/G-Lab`配下のAI解析レポート（Vitia UXレビュー）における「action_feedback_traceable」「色や単一チャネルへの依存回避」の指摘を、本UIの実装調査と突き合わせて整理した。

---

## 1. 課題

現状の実装では、ジャストタイミングが「分かりづらい」という課題がある。

## 2. 現状整理（調査済み）

ジャストタイミングの表現は`ACLikeRhythmGuideView.SetBeatAnimation`（`Assets/Scripts/Runtime/4.View/InGame/Music/ACLikeRhythmGuideView.cs:93`）が担っており、判定結果は以下の1チャネルのみで表現されている。

```csharp
// ACLikeRhythmGuideView.SetBeatAnimation（現状）
float targetSizeDelta = isJustTiming ? _justTimingSizeDelta : _inTimingSizeDelta;
// → _outTimingSizeDeltaへ、共通のOutCirc・共通のDurationで縮むアニメーションのみ
```

- **判定チャネルが1つしかない**: ビートブロックの`sizeDelta`（高さ）の差のみでジャスト/通常を区別している。色（`_beatColor`）は判定ゾームごとの固定色であり、判定結果によって変化しない。
- **判定ウィンドウが事前に見えない**: `_justTimingBeatBoxIndex`（ジャスト判定ゾーンの位置）はコード内で計算済みだが、画面上に「ここがジャスト」という帯・ゲート状の常設表示はなく、結果が起きた後にしか差が分からない＝先読みができない。
- **モーションの緩急が同じ**: ジャストも通常タイミングも同じ`Ease.OutCirc`・同じ`_outTimingDuration`で縮むだけで、成立の瞬間の「手応え」が動きの質としては表現されていない。

## 3. 演出案（複数チャネルでの多重化）

単一チャネル（サイズ差のみ）への依存を解消するため、視覚・聴覚・触覚を分離した複数チャネルで判定結果を多重化する方向を軸とする。

| # | 案 | 内容 | 優先度 |
|---|---|---|---|
| 1 | 判定ウィンドウの事前可視化 | `_justTimingBeatBoxIndex`の位置に、バーが流れてくる前から枠・ノッチ・明るい帯を常設表示し、狙う場所を先読みできるようにする | 高 |
| 2 | 判定色の分離 | ゾーン固定色（`_beatColor`）とは別に、ジャスト成立時のみ白〜金などハイコントラストな色へ一瞬フラッシュさせる | 高 |
| 3 | 音・振動の独立チャネル | ジャスト成立専用のSE／コントローラー振動を視覚と独立に発生させ、視覚が敵や照準に取られていても、あるいはミュート環境でも気づけるようにする | 高 |
| 4 | モーションの質の差別化 | ジャスト成立時のみオーバーシュート（一瞬伸びてから縮む）や弾むようなEaseを使い、通常タイミングは素直に縮むだけにする。数値差でなく動きの質で区別する | 中 |
| 5 | 判定テキスト/アイコンのポップアップ | "Just" / "Good"等の短いテキストやアイコンをビート位置近くに一瞬表示する。色弱・見落とし耐性が高い | 中 |
| 6 | 武器変化との連動エフェクト | ジャスト成立の瞬間に武器側にもグロー/パーティクルを発生させ、「入力がここで武器を変えた」という因果を同一フレームで結びつける | 中 |
| 7 | ビートタイプ連動のポストプロセスvignette | ジャスト成立時、既存の`_beatColor`（ゾーンごとの固定色）に合わせた色のvignetteを画面全体に一瞬フラッシュさせる。中央のビートバーを注視していなくても、画面のどこを見ていても気づける | 高 |

優先度は「分かりづらさ」への直接効果（先読み可能性・多重チャネル化）を基準に設定した。1・2・3・7は判定そのものの視認性を底上げする施策、4・5・6は手応え・因果の強化にあたる。

### 3.1 案7の補足: 全画面vignetteのガードレール

案7は既存の`_beatColor`をそのまま流用でき、視線位置に依存しない最も強い周辺視野チャネルになる一方、G-Labレビューが指摘する「色・単一チャネルだけに依存しない」原則には反しやすい施策でもあるため、以下を前提条件とする。

- **色以外の差も持たせる**: vignette色だけでビートタイプを区別させない。強さ・点滅パターンなど色以外の差も併用し、色弱環境でも判別できるようにする。
- **頻度・強度を抑える**: 高速な連打パターンで毎回全画面フラッシュすると、敵予告や照準を隠し、疲労・光過敏のリスクになる（Vitiaレビューで「酔い・疲労」は未検証リスクとして挙がっている）。強度・頻度は控えめにし、設定でも軽減できる余地を残す。
- **ゲームプレイ情報を隠さない**: 照準・敵予告・mission情報などの優先情報を塞がない範囲の強さ・持続時間に留める。

## 4. 検証観点

- ミュート環境（音を切った状態）でもジャスト判定が視覚のみで識別できるか
- 敵・照準・他HUD要素に注意が向いている状態でも、判定結果に気づけるか（周辺視野での検知）
- 判定ウィンドウの事前提示により、初見プレイヤーの成功率・体感の分かりやすさが変化するか
