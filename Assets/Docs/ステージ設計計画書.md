# ステージシステム設計計画書

- 作成日: 2026-07-13
- 対象仕様: `Assets/Docs/ステージ仕様.txt`
- 対象調査: `Assets/Docs/ステージ実装レポート.md`
- 目的: 実装レポートで指摘された未実装・不適合項目を、実装可能な設計として具体化する

## 1. 本書の位置づけ

実装レポートは「何が足りないか」の調査結果であり、優先度A/Bとして対応項目を列挙している。本書はそれらを対象に、既存アーキテクチャ（`0.Utility`〜`6.Composition`の層構成、`ServiceLocator`による手動DI、`InGameInitializationModuleBase`／`OutGameInitializationModuleBase`によるモジュール初期化、`[SerializeReference, SubclassSelector]`によるポリモーフィックなAsset拡張）に沿った設計案を示す。

優先度Cの項目（目視確認・実機計測・アセット照合）は実装設計を伴わないQAタスクのため、本書のスコープ外とし6章で別途扱う。

## 2. 全体方針

- 新規の判定条件・演出定義は、既存の`MissionEvaluationConditionAssetBase`と同様に「Domain側インターフェース実装 + InfraStructure側`SubclassSelector`用Assetクラス」のペアで追加し、インスペクタから選択できる形にする。
- 新規の実行時モジュール（Wave開始通知の購読など）は`InGameInitializationModuleBase`を継承したComposition層クラスとして追加し、`ServiceLocator`経由で他モジュールの`*ModuleContainer`を取得する既存パターンに従う。
- 保存処理は`SaveData`配下の各`*Data`クラス＋`SavedataSystem.LoadAsync/SaveAsync`という既存パターンを踏襲し、新しい永続化の仕組みを増やさない。
- 各Adaptor/Controllerは他モジュールへの直接参照を増やさず、イベント購読で疎結合を保つ（レポートが繰り返し推奨している方針）。

## 3. 実装フェーズと依存関係

```
Phase 0  StageId重複解消                     ─┐（即時・他フェーズに依存しない）
Phase 1  クリア保存 / クリア済み復元           │→ Phase 3のチュートリアル完了保存が依存
Phase 2  評価条件追加（被ダメージ/銃種/コンボ）─→ サブミッション3件化 / ランク算出が依存
Phase 2' サブミッション3件化 + ランク算出
Phase 3  初回チュートリアル自動出撃            （Phase 1に依存）
Phase 4  ステージ固有Wave定義ロード
Phase 4' Wave開始通知 + StageEffectモジュール （Phase 4に依存はしないが同時に着手すると効率的）
Phase 4''複数Stageシーン/背景セット割当
```

Phase 0は他の全項目の前提となるバグ修正のため最優先。Phase 2（評価条件追加）はPhase 2'（3件化・ランク算出）の前提であるため、レポートの優先度A/Bの順序を入れ替え、評価条件追加を先に着手する構成とする。

## 4. 各項目の設計

### 4.0 [Phase 0] StageId重複解消

**対象:** `1.Domain/OutGame/StageSelect/StageTree.cs`、`5.InfraStructure/OutGame/StageSelect/StageTreeAsset.cs`、データアセット `Stage_05.asset` / `Stage_06.asset`

**現状:** `StageTree`のコンストラクタが`Dictionary<StageId, StageNode>`へ`_nodes[nodes[i].Id] = nodes[i];`で登録しており、重複時は検出も警告もなく後勝ちで上書きされる。`Stage_05`と`Stage_06`が共に`StageId=5`を持つため、ボスステージがテストステージに置き換わっている。

**設計方針:**
1. データ修正: `Stage_06`（検証用ステージ）のStageIdを未使用の値へ採番し直す。採番ルール（欠番/末尾追加のいずれか）はステージツリー全体のID一覧を確認した上で決定する。
2. 恒久対策: `StageTree`のコンストラクタに重複検出を追加し、重複時は`InvalidOperationException`を送出する（`MissionDefinitionAsset.Create()`が評価条件ID重複時に同様の方式を取っており、既存の失敗方針と統一する）。
3. 任意: `StageTreeAsset`側で`OnValidate`により重複StageIdをインスペクタ上で警告表示し、データ入力時点で検知できるようにする。

### 4.1 [Phase 1] クリア状態の保存と復元

**対象:**
- `StageProgressSaveDataService.SaveClearAsync(StageId, MissionEvaluationResult)`（`2.Application/Persistent/Savedata`、実装済みだが呼び出し箇所が無い）
- `SaveDataClearStageRepository.GetClearedStageIds()`（`5.InfraStructure/OutGame/StageSelect`、TODOスタブ）
- `StageProgressData.RecordClear/IsStageCleared`（`1.Domain/Persistent/Savedata`、実装済み）
- クリア確定を扱うComposition層（`InGameSequenceDirector`／`SequenceInitializationModule`）

**設計方針:**
1. クリア確定タイミングの一本化: `InGameSequenceDirector`がミッション終了イベントを受けてリザルト表示を行う箇所で、表示直前に`MissionEvaluationResult`を1回だけ生成し、その同一インスタンスを`StageResultPresenter`（表示用）と`StageProgressSaveDataService.SaveClearAsync`（保存用）の両方へ渡す。表示と保存で評価を再計算しない構造とする（レポート推奨方針）。
2. 保存呼び出しはComposition層に置き、`StageProgressSaveDataService`をコンストラクタ注入する。既存の`InGameInitializationModuleBase`系モジュールと同様、`Ready()`時点で必要な参照を解決する。
3. `SaveDataClearStageRepository.GetClearedStageIds()`を実装: `SavedataSystem.LoadAsync<SaveData>()`で`StageProgressData`を取得し、保持する`StageClearData.StageId`（`int`）を`StageId`構造体へラップしたリストを返す。
4. 実装後、`IStageClearRepository`を参照している既存のステージ解放判定（`StageTree`側）が正しく後続ステージを解放することを確認する。

### 4.2 [Phase 2] 評価条件の追加（被ダメージ・使用武器種・コンボ）

**対象:** `1.Domain/InGame/Mission/EvaluationCondition/`（新規クラス）、`5.InfraStructure/InGame/Mission/`（対応するAssetBase派生）、`MissionProgress`（`1.Domain/InGame/Mission`）

**現状:** 評価条件は`IMissionEvaluationCondition`を実装する`ClearTimeEvaluationCondition`のみで、`MissionProgress`は経過時間以外の実績値を保持していない。

**設計方針:**
1. `MissionProgress`に被ダメージ累計・使用武器種の集合・最大コンボ数を保持するフィールドを追加する。既存の`ElapsedTime`同様、値オブジェクトとして表現する。
2. これらの実績値は、ミッション進行ロジックが他モジュールを直接参照するのではなく、Adaptor層に新設するイベントController（例: `MissionProgressRecorderController`）が既存の`AttackResultPresenter`やダメージ処理・コンボ処理のイベントを購読し、`MissionProgress`へ書き込む形にする。
3. 新規条件クラスを追加する:
   - `DamageTakenEvaluationCondition`（被ダメージ累計がしきい値以下で達成）
   - `WeaponVarietyEvaluationCondition`（使用武器種の種類数がしきい値以上で達成）
   - `ComboEvaluationCondition`（最大コンボ数がしきい値以上で達成）
   それぞれに対応する`MissionEvaluationConditionAssetBase`派生クラスをInfraStructure層に追加し、`MissionDefinitionAsset`の`[SerializeReference, SubclassSelector]`リストから選択可能にする。

### 4.2' [Phase 2'] サブミッション3件設定とランク算出

**対象:** `MissionDefinition_1.asset`（データ）、新規Domainクラス（ランク算出）、`StageResultPresenter.PresentVictory()`

**設計方針:**
1. Phase 2で追加した評価条件を用い、本番ミッションデータの評価条件を重複ありで3件設定する（仕様書の想定どおり）。
2. ランクをDomain層の値として定義する（例: `StageRank`enum、`C/B/A/S`）。入力は`MissionEvaluationResult.AchievedCount`とし、達成数0→C、1→B、2→A、3→Sの対応表をロジック化する。
3. `StageResultPresenter.PresentVictory()`内で`UNIMPLEMENTED_VALUE_TEXT`を渡している`rankText`を、上記ランク算出結果に置き換える。4.1で1回だけ生成する`MissionEvaluationResult`をここでも共有し、表示・保存・ランク算出のすべてが同一の評価結果を参照する構造にする。

### 4.3 [Phase 3] 初回起動時のチュートリアル自動出撃

**対象:** `TitleSceneInitializer`（`6.Composition/OutGame/Title`）、`TutorialData.IsTutorialCompleted`（`1.Domain/Persistent/Savedata`、既存だが未参照）、出撃経路（OutGame側の出撃Application/UseCase）

**現状:** 初回起動判定は`!_savedataSystem.Exists<SaveData>()`のみで行われ、遷移先はシーン単位の切り替えに留まる。`TutorialData.IsTutorialCompleted`は分岐に使われていない。

**設計方針:**
1. `TitleSceneInitializer`の分岐条件を、セーブファイル有無ではなく`!TutorialData.IsTutorialCompleted`ベースに見直す（セーブは存在するがチュートリアル未完了、というケースの扱いは要件として要確認）。
2. Titleにロジックを持たせず、通常のステージ出撃と同じ経路（選択ステージ・ミッション・Stageシーンを設定してからロード）を使う。Titleは「チュートリアル出撃要求」という薄いフラグをOutGame側の出撃UseCaseへ渡すだけにする。
3. チュートリアル用StageIdは、`StageNodeAsset`が`StageId==0`を無効値として拒否する現状の制約に合わせ、正の実IDを採番する。仕様書内の「ステージ0」は表示上の呼称として扱い、実装上のIDとは分離する。
4. チュートリアル完了の記録: チュートリアルステージのクリア確定時に`TutorialData.IsTutorialCompleted = true`を設定し、4.1で構築するクリア保存フローに合流させて保存する。

### 4.4 [Phase 4] ステージ固有のWave定義ロード

**対象:** `EnemyInitializer.ResourceLoadAsync()`（`6.Composition/InGame/Enemy`）、`_enemyWaveDefinitionAssetKey`（インスペクタ固定値）、`StageNodeAsset`

**現状:** Wave定義のAddressablesキーは`EnemyInitializer`にインスペクタ設定された単一の固定値であり、ステージごとに切り替えられない。

**設計方針:**
1. `StageNodeAsset`（またはステージ選択ドメインの`StageDefinition`相当）にWave定義のAddressablesキーを追加する。
2. ステージ選択時に保持される「選択済みステージ状態」を経由し、`EnemyInitializer.ResourceLoadAsync()`がインスペクタ固定値ではなくこの状態からキーを取得してロードするように変更する。
3. 変更範囲はInGameシーン内のロード処理に閉じるため、既存のResourceLoadAsyncフェーズの契約（`Awaitable<bool>`）は変えない。

### 4.4' [Phase 4'] Wave開始通知とStageEffectモジュール

**対象:** `EnemyWaveSpawnerState`（`3.Adaptor/InGame/Enemy`、現状`OnWaveCleared`/`OnWaveAllCleared`のみ）、`EnemyWaveSpawnerController.SpawnNextWave()`、`EnemyWaveDefinitionAsset`、新規Composition module

**設計方針:**
1. `EnemyWaveSpawnerState`に`OnWaveStarted(int waveIndex, EnemyWaveDefinition definition)`イベントを追加し、`SpawnNextWave()`実行時に発火させる。
2. `EnemyWaveDefinitionAsset`にWave単位の演出定義参照を追加する。演出定義は`IStageEffectDefinition`のようなDomainインターフェースと、`[SerializeReference, SubclassSelector]`で選択可能な`StageEffectAssetBase`派生（爆発演出、建物倒壊演出、障害物生成など）として、既存の評価条件と同じ拡張パターンで実装する。
3. 新規Composition層クラス`StageEffectInitializer : InGameInitializationModuleBase`を追加し、`Ready()`で`EnemyModuleContainer`から`OnWaveStarted`を購読、対応する演出定義を選択して`MusicSyncModuleContainer.MusicSyncService.RegisterAction(beat, timing, action)`経由でBGM同期実行する。敵生成・演出・障害物・音楽同期を単一クラスに集約せず、Wave IDを介して各モジュールが独立して反応する構造にする（レポート推奨方針）。

### 4.4'' [Phase 4''] 複数Stageシーン/背景セットの割当

**対象:** `StageNodeAsset`、`Stage_01.unity`（本番相当）、`Stage_02.unity`（検証用に近い構成）

**設計方針:** 初期実装では「StageNodeごとに異なるStageシーンを割り当てる」方式を優先する。`Stage_02`を本番相当のアセット構成へ作り込み、最小工数でステージの複数化を実現する。将来的に背景差分を量産する段階になった場合は、「共通StageシーンへAddressablesから背景セットを生成する」方式へ移行する、という段階的な方針とする。

## 6. 優先度Cの扱い（QA項目、本書スコープ外）

以下は実装設計ではなく、各Phase完了後の確認作業としてチェックリスト化し、別途QAタスクとして扱う。

- 正方形・通路なし・屋外限定であることのUnity上での目視確認
- 1ステージ約2分になるかの複数回プレイ計測
- BGM同期演出のタイミングの実機確認（Phase 4'完了後）
- 仕様書記載の背景アセット（道路、柵、電灯、戦車残骸、ドラム缶）の配置照合

## 7. リスク・要確認事項

- **チュートリアルStageId=0の扱い:** 現行実装は`StageId==0`を無効値として拒否するため、仕様書の「ステージ0」表記と実装上のID採番がずれる。呼称と実装の分離方針（4.3節）についてゲームデザイン側との合意が必要。
- **セーブ有無とチュートリアル完了の分岐条件:** 「セーブは存在するがチュートリアル未完了」のケースをどう扱うか（再度チュートリアル導線に入れるか、通常導線にするか）は要件確認が必要。
- **MissionProgressの拡張:** 被ダメージ・武器種・コンボの実績値追加は既存ドメインモデルへの変更を伴うため、既存の`ClearTimeEvaluationCondition`や`MissionRuntimeService`側の呼び出し互換性を崩さないよう設計時に確認する。
- **Wave演出データの制作コスト:** 4.4'は演出定義データ（爆発/倒壊/障害物のAddressablesアセット）の制作を伴うため、背景デザイナー側の作業と並行して進める必要がある。
