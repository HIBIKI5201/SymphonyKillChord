## 2. 現状整理（マージ後・調査済み）

### 2.1 入力まわり

`PlayerInputView`（`Assets/Scripts/Runtime/4.View/Persistent/Input/PlayerInputView.cs`）が唯一の入力受け口で、`InputActionKind`（`Assets/Scripts/Runtime/3.Adaptor/Persistent/Input/InputActionKind.cs`、現状`LockOn = 104`が最後尾）ごとに`event Action<InputContext<T>>`を公開している。キーボード/ゲームパッドは`InputAction.CallbackContext`から`InputContext<T>`を生成し、モバイルはInput Actionsを介さず`MobileInput`から`PlayerInputView`のメソッドを直接呼び出す、という2系統が併存している。

**フリックによるロックオン対象切り替えは既に実装済み**（`MobileInput.cs:19-23, 133-144`）。

```csharp
// MobileInput.OnTrackedTouchCanceled（現状）
float duration = Time.unscaledTime - _touchStartTime;
Vector2 displacement = screenPos - _touchStartPosition;
float minimumDistanceSquared = _flickMinDistance * _flickMinDistance;
if (duration <= _flickMaxDuration && displacement.sqrMagnitude >= minimumDistanceSquared)
{
    _playerInputView.OnMobileLookFlick(displacement.normalized);
}
```

- `PlayerInputView.OnMobileLookFlickInput`（`event Action<Vector2>`、InputContextでラップしないモバイル専用の生イベント、`PlayerInputView.cs:36-37, 211-214`）として通知される。
- 受け手は`CameraSystemView.LookFlickHandlerMobile`（`CameraSystemView.cs:193-219`、`#if UNITY_ANDROID`ブロック内）で、**`LockOnManual`中のみ**動作する。スクリーン空間の`flickDirection`（x, y）を`GetCurrentForward() + cameraT.right * x + cameraT.up * y`でワールド方向に変換し、`_trySwitchTargetFunc`（実体は`TargetingSystem.TrySwitchTarget`）へ渡している。
- **現状、PC（キーボード）・ゲームパッドには対象切り替え入力が存在しない**。`KillChordInputActioMap.inputactions`のInGameマップにも`Dodge`/`Attack`/`Move`/`Look`/`LockOn`の5アクションのみで、切り替え専用アクションはない。
- また、現状のフリックは**上下方向の成分（`flickDirection.y`）も評価に使っており、左右2値ではなく画面上の任意方向で候補評価している**。今回統一する`-1〜1`の1次元値（左右のみ）とは表現力が異なる。

### 2.2 カメラのロックオン状態

`CameraSystemView`（`Assets/Scripts/Runtime/4.View/InGame/Camera/CameraSystemView.cs`）が唯一のカメラ制御クラスで、`private enum CameraLockOnState : byte { Free, LockOnAuto, LockOnManual }`と`if/else`分岐で挙動を切り替える構造は変わっていない。

- `LockOnManual`: ロックオンボタン（`ToggleLockOnState`, `CameraSystemView.cs:359-370`）でON/OFFする。
- `LockOnAuto`: 攻撃入力（`OnAttack`→`TryActiveAutoLockOn`, `CameraSystemView.cs:261-267, 342-352`）で発動する。
- **現状、視点操作や移動入力によってロックオンが即座に解除される処理は存在しない**（c48db1aで削除済み）。代わりに`BuildFrame`（`CameraSystemView.cs:414-451`）内で、`LockOnAuto`のときのみ`_lockOnRangeChecker.IsWithinRange(_camera, targetPosition)`を評価し、対象がビューポート外（`CameraConfig.LockOnViewportMargin`でマージン調整可）に出たら`ClearLockOn()`する。`LockOnManual`はこの判定を行わず、画面外に出ても維持される。
- **「短時間に強い操作をするとロックオンが解除される」仕様（本計画の②）はまだ存在しない**。

### 2.3 ロックオン中の回転計算とオフセット

- `CameraLockOnRotationCalculator`（`Assets/Scripts/Runtime/4.View/InGame/Camera/Calculation/CameraLockOnRotationCalculator.cs`）: `Update`内で`Quaternion.Slerp(cameraBoneRotation, target, 1f - Mathf.Exp(-_parameter.BoneRotateSpeed * context.DeltaTime))`と、**`BoneRotateSpeed`は角度によらず常に一定値**（`CameraLockOnRotationCalculator.cs:28-40`）。**本計画の⑤（角度依存の可変速度化）はまだ実現されていない**。
- `CameraLockOnOffsetCalculator`（`Assets/Scripts/Runtime/4.View/InGame/Camera/Calculation/CameraLockOnOffsetCalculator.cs`、c48db1aで新設・**現存**）: ロックオン中の視点入力を`_offset`（ヨー・ピッチ、`Vector2`）として積算し、`LockOnOffsetClamp`でクランプ、無操作が`LockOnOffsetRecenterDelay`秒続くと`LockOnOffsetRecenterSpeed`で中央へ戻す。この`lockOnOffset`は`CameraLockOnRotationCalculator.TryCalcTargetRotation`（`ApplyOffset`, `CameraLockOnRotationCalculator.cs:118-127`）と`CameraLookAtRotationCalculator.Update`（`CameraLookAtRotationCalculator.cs:57-59`）の両方に加算されており、**削除対象となる仕様⑥そのもの**。
- `CameraFreeLookRotationCalculator`（`Assets/Scripts/Runtime/4.View/InGame/Camera/Calculation/CameraFreeLookRotationCalculator.cs`）は今回のマージでも変更されておらず、フリールック時に生の入力をヨー・ピッチへそのまま積分するのみ。**移動方向への追従処理（本計画の③）は依然として存在しない**。

### 2.4 候補ターゲット・切り替えAPI（Targetモジュール）

`TargetingSystem`（`Assets/Scripts/Runtime/4.View/InGame/Target/TargetingSystem.cs`）は非破壊の候補プレビュー・切り替えAPIを既に備えている。

- `EvaluateBestTarget(center, direction)`（`TargetingSystem.cs:259-290`）: 正面方向内積優先・内積が負なら距離フォールバックという選定ロジック本体（非破壊）。
- `ChangeTarget`: `EvaluateBestTarget`の結果を`_currentTarget`へ確定（`TargetingSystem.cs:180-184`）。
- `UpdateCandidate`: 同じ選定結果を`_currentCandidate`へ反映するのみで`_currentTarget`は書き換えない（`TargetingSystem.cs:191-194`）。**非ロックオン時、`CameraSystemView.BuildFrame`が毎フレーム`_updateCandidateAction`を呼んでいる**（`CameraSystemView.cs:441-448`）。
- `TrySwitchTarget(playerPosition, direction)`: `EvaluateBestTarget`の結果が現在対象と異なれば`_currentTarget`を差し替えてtrueを返す（`TargetingSystem.cs:202-213`）。これが2.1節のフリック切り替えの実体。

`ITargetSystemViewModel`/`TargetSystemController`にも同様のパススルーが揃っており、**対象切り替え自体のAPIは今回新設不要**（`direction`ベクトルの作り方だけを1次元の左右選択に合わせて調整すれば流用できる）。

### 2.5 攻撃命中イベント

`PlayerAttackController.ExecuteAttack`（`Assets/Scripts/Runtime/3.Adaptor/InGame/Battle/PlayerAttackController.cs:76-135`）が攻撃を解決し、**実際にダメージが成立した瞬間にのみ**`EventBus<EOnTakeDamage>.Raise(...)`を発火する（`PlayerAttackController.cs:127-128`）。`ExecuteAttack`内の`TryUpdateCurrentTarget()`は`TargetSystemController.TryGetCurrentTargetEntity`（＝カメラがロックオンしているのと同じ`TargetingSystem`の現在ターゲット）から攻撃対象を取り出しており、対象が居ない場合はイベント発火前に早期returnする（`PlayerAttackController.cs:99-103`）。つまり**`EOnTakeDamage`が飛ぶのは常にロックオン中の現在対象への命中時のみ**であり、`DefenderId`の突き合わせをしなくてもカメラ側の「命中」判定として使える。

> **注意（イベント名と向きの整理）**: `EOnTakeDamage`（`Assets/Scripts/Runtime/0.Utility/Persistent/EOnTakeDamage.cs`）はクラスコメント上「ダメージを受ける時」という汎用命名になっているが、ここで発火するのは**プレイヤー自身の`PlayerAttackController`が攻撃を実行し、その攻撃が対象（敵）に命中した**タイミングである。つまり本仕様④で言う「攻撃を当てた」＝「自分の攻撃が相手に命中した」を指し、「プレイヤーが敵から攻撃を受けた」場合ではない。`DefenderId`は攻撃を受けた側（＝敵）のIDであり、プレイヤーのIDではない点に注意する。

`EventBus<T>`（`Assets/Scripts/Runtime/0.Utility/Persistent/EventBus.cs`）はDIを経由しないstaticイベントバスで、`CameraSystemView`から直接`Register`/`Unregister`できる。**この購読は現状のカメラ側に一切実装されていない**。

## 3. 設計方針

### 3.1 仕様①: ロックオンセレクト入力の統合

新規イベント`PlayerInputView.OnLockOnSelectInput`（`event Action<InputContext<float>>`、PC/ゲームパッド用）と`OnMobileLockOnSelectInput`（`event Action<float>`、モバイル用。既存の`OnMobileLookFlickInput`と同じ「InputContextでラップしない生イベント」という現状の設計パターンを踏襲）を追加し、`InputActionKind`に`LockOnSelect = 105`を追加する（既存`LockOn = 104`の次番）。値は`-1`（左）〜`1`（右）。**単発トリガー**として扱う（PC/ゲームパッドは`context.Phase == InputActionPhase.Started`のみ消費、モバイルは後述のフリック確定時に1回だけ発火）。

プラットフォームごとの発火経路は次のように分離する。

| プラットフォーム | 発火方法 | 変更内容 |
| --- | --- | --- |
| PC（キーボード） | Qキー = `-1`、Rキー = `1` | 新規。`KillChordInputActioMap.inputactions`のInGameマップに`LockOnSelect`アクション（Button種別ではなく1D Axis複合バインディング: Negative=Q, Positive=R）を追加し、`PlayerInputView.OnLockOnSelect(InputAction.CallbackContext)`から通知 |
| ゲームパッド | L1（leftShoulder） = `-1`、R1（rightShoulder） = `1` | 新規。同一アクションに1D Axis複合バインディング（Negative=leftShoulder, Positive=rightShoulder）を追加、同じく`OnLockOnSelect`から通知 |
| モバイル | 既存のフリック判定バッファ（`MobileInput._flickMaxDuration`/`_flickMinDistance`）は**そのまま流用**し、`displacement`の**水平成分の符号のみ**を`-1`/`1`として通知するよう変更 | 既存改修。`MobileInput.OnTrackedTouchCanceled`（`MobileInput.cs:133-144`）の`_playerInputView.OnMobileLookFlick(displacement.normalized)`を`_playerInputView.OnMobileLockOnSelect(Mathf.Sign(displacement.x))`に置き換える |

ポイントは、**フリックの「短時間・強さ」判定は現状通りモバイル入力バッファ（`MobileInput`）に閉じ込め、PC/ゲームパッドは判定を介さず単純なボタン発火にする**こと（ユーザー指示通り）。これにより`CameraSystemView`（消費側）は`OnLockOnSelectInput`/`OnMobileLockOnSelectInput`という統一された左右1次元の入力だけを見ればよく、プラットフォーム分岐は「どちらのイベントを購読するか」の1点に閉じる。

- **既存の`OnMobileLookFlickInput`（`Vector2`）と`CameraSystemView.LookFlickHandlerMobile`は本仕様に統合し、廃止する**。2.1節で確認した通り、現状は上下方向も含めた任意方向で候補評価しているが、今回の統一仕様では左右のみを扱うため、上下方向の情報は使われなくなる（UX的な劣化になる場合は、フリックの上下成分を将来的に別イベント——例えば縦フリックでロックオンのON/OFFなど——に転用することも検討可能だが、本計画のスコープ外とする）。
- **`CameraSystemView`側の消費ロジック**: `LookFlickHandlerMobile`を置き換える形で、`LockOnSelectHandler(InputContext<float> context)`（PC/ゲームパッド用、Startedのみ）と`LockOnSelectHandlerMobile(float direction)`（モバイル用）の2つを追加し、いずれも共通の`TrySelectAdjacentTarget(float direction)`へ委譲する。`TrySelectAdjacentTarget`内の処理は現状の`LookFlickHandlerMobile`とほぼ同じだが、方向ベクトルの合成を`GetCurrentForward() + _cameraT.right * Mathf.Sign(direction)`のみ（`up`成分なし）に簡略化する。
- **既存の「`LockOnManual`中のみ動作する」という制限は維持する**（現状の実装が既にそうなっているため、変更ではなく現状踏襲）。オートロックオン中の対象切り替えを許可するかどうかは本計画のスコープ外とし、必要になった場合は`IsLockOn()`への条件緩和のみで対応可能。
- **値の意味**: 現時点でPC/ゲームパッドは離散入力のため`-1`/`1`の2値のみ、モバイルのフリックも符号のみを使用する。`float`型・`-1〜1`レンジにしているのは、将来モバイルのフリック強度を連続値として使う拡張余地を残すためで、初期実装では符号のみを消費先で利用する。

### 3.2 仕様②: 強い視点操作によるオートロックオン解除（新規）

2.2節の通り、現状は`LockOnAuto`の解除条件が「対象がビューポート外に出る」（`CameraLockOnRangeChecker`）のみで、視点操作による即時解除は既に無い。ここに**「短時間に強く操作した場合の解除」を追加**する。**対象は`LockOnAuto`のみ**とする。`LockOnManual`は専用ボタンによる明示的なON/OFFという性質上、視点操作で意図せず解除されると「トグルの意味がなくなる」ため対象外とする。これは`CameraLockOnRangeChecker`の適用範囲が既に`LockOnAuto`限定になっている現状の設計判断（`CameraSystemView.cs:431-437`）とも整合する。

| 案 | 内容 | 採否 |
| --- | --- | --- |
| A. スライディングウィンドウ | 直近`LockOnBreakWindow`秒間の入力量をキュー等で保持し、合計が閾値を超えたら解除。判定は正確だがキュー管理のコストがかかる | 不採用（現状のCalculator群がいずれもO(1)の単純な状態しか持たない設計思想と合わない） |
| B. 指数減衰アキュムレータ | `_breakAccum`を毎フレーム`_breakAccum -= (_breakAccum / LockOnBreakWindow) * deltaTime`で減衰させつつ、`_breakAccum += input.magnitude * FollowRotationSpeed * deltaTime`を加算する（単位は既存の`CameraFreeLookRotationCalculator`と同じ「度」相当）。`_breakAccum`が`LockOnBreakThreshold`を超えたら解除 | **採用**（O(1)、既存Calculator群の実装コストと揃う） |

- 新規クラス`CameraLockOnBreakTracker`（View層、プレーンC#、`Assets/Scripts/Runtime/4.View/InGame/Camera/Calculation/`）に上記アキュムレータ処理を実装する。`Update(in CameraUpdateContext context, in CameraConfig config) : bool`で「今フレーム閾値を超えたか」を返す。
- `CameraSystemView.BuildFrame`のビューポート判定（`CameraSystemView.cs:431-437`）と並列に、`_lockOnState == CameraLockOnState.LockOnAuto`のときのみ`CameraLockOnBreakTracker.Update(...)`を評価し、`true`なら`ClearLockOn()`を呼ぶ。
- ロックオン解除時・新規ロックオン開始時（`TryActiveAutoLockOn`/`ToggleLockOnState`/`ClearLockOn`）に`CameraLockOnBreakTracker.Reset()`を呼ぶ（既存の`_lockOnOffsetCalculator.Reset()`呼び出し箇所と同じタイミング。3.6節で`_lockOnOffsetCalculator`自体は削除するため、実質的にこの呼び出しを置き換える形になる）。
- `CameraConfig`に`LockOnBreakWindow`（秒、既定0.15程度）、`LockOnBreakThreshold`（度相当、既定値は実機調整）を追加する。

### 3.3 仕様③: 移動方向へのカメラ追従（非ロックオン時、新規）

フリー視点時、視点入力が無い（＝プレイヤーが視点操作していない）かつ移動入力がある場合、カメラのヨーがプレイヤーの現在の向き（`_playerT.forward`）へゆるやかに近づいていくようにする。`_playerT`はプレイヤーの実体Transformで、`PlayerView.UpdateMovement`（`Assets/Scripts/Runtime/4.View/InGame/Player/PlayerView.cs:308-349`）側で既に移動入力＋現在のカメラヨーから求めた向きへキャラクター自身が回転しているため、**カメラは移動方向を改めて計算し直す必要はなく、プレイヤーの向きをそのまま追従先として使える**。

- `CameraUpdateContext`（`Assets/Scripts/Runtime/4.View/InGame/Camera/CameraUpdateContext.cs`）に`PlayerForward`（`Vector3`）フィールドを追加し、`CameraSystemView.BuildFrame`で`_playerT.forward`を渡す。
- `CameraFreeLookRotationCalculator.Update`を拡張し、`context.Input.sqrMagnitude`が`MoveFollowIdleLookThreshold`未満（＝視点操作していないとみなせる）かつ`context.MoveInput.sqrMagnitude > float.Epsilon`のとき、現在のヨーを`context.PlayerForward`のXZ平面上の角度へ向けて`Mathf.MoveTowardsAngle`または`Mathf.LerpAngle`で`MoveFollowRotationSpeed`（度/秒）だけ近づける処理を、既存の入力ヨー加算処理と排他的に実行する。
- ロックオン中（`LockOnAuto`/`LockOnManual`とも）はこの処理を通らない（ボーン回転は`CameraLockOnRotationCalculator`が担当するため`CameraFreeLookRotationCalculator`自体が呼ばれない、`CameraSystemView.UpdateCameraBone`, `CameraSystemView.cs:393-407`参照）。
- `CameraConfig`に`MoveFollowRotationSpeed`（度/秒）、`MoveFollowIdleLookThreshold`（視点入力の無操作しきい値）を追加する。

### 3.4 仕様④: 自分の攻撃命中によるオートロックオンの継続時間延長（新規）

`LockOnAuto`は常に「あと何秒で解除されるか」を表すカウントダウンタイマーを持ち、**自分の攻撃が現在のロックオン対象に命中するたび**（`EOnTakeDamage`が飛ぶたび）にこのタイマーを`AutoLockOnReleaseDelay`秒へ**延長（リセット）**する。命中し続けている限りタイマーが尽きることはなく、ロックオンは維持され続ける。逆に一定時間（`AutoLockOnReleaseDelay`秒）命中しなければタイマーが0になり、自動的に`ClearLockOn()`する。

- `CameraSystemView`に`float _autoLockOnIdleTimer`（残り時間ではなく「命中してから経過した時間」として保持し、`AutoLockOnReleaseDelay`との比較で解除判定する）を追加する。`Initialize`内で`EventBus<EOnTakeDamage>.Register(OnTakeDamage)`、`OnDestroy`で`Unregister`する（2.5節の通り、`EOnTakeDamage`は「自分の攻撃が対象に命中した」ことを表すため`DefenderId`の突き合わせは不要）。
- `OnTakeDamage(EOnTakeDamage e)`: `_lockOnState == CameraLockOnState.LockOnAuto`のときのみ`_autoLockOnIdleTimer = 0f`にリセットする。これが「命中するたびに継続時間を延長する」の実体で、命中の間隔が`AutoLockOnReleaseDelay`未満である限り解除されない。
- `_lockOnState`が`LockOnAuto`になった瞬間（`TryActiveAutoLockOn`成功時）にも`_autoLockOnIdleTimer = 0f`で初期化する。これにより「攻撃入力してから一度も命中しないまま」のケースでも`AutoLockOnReleaseDelay`秒で解除され、居座り続けることを防ぐ。
- `Tick`（または`BuildFrame`）で`LockOnAuto`のときのみ`_autoLockOnIdleTimer += deltaTime`し、`_autoLockOnIdleTimer >= _viewSettings.AutoLockOnReleaseDelay`なら`ClearLockOn()`を呼ぶ。ビューポート判定（3.2節の強操作解除、2.2節の視野外解除）と同じ`LockOnAuto`限定のガードとして並列に追加する。
- `CameraConfig`に`AutoLockOnReleaseDelay`（秒、既定3秒程度、「最後に命中してから解除までの猶予＝1回の命中で延長される秒数」を意味する）を追加する。

### 3.5 仕様⑤: ロックオン追従速度の角度依存可変化

`CameraLockOnRotationCalculator.Update`（`CameraLockOnRotationCalculator.cs:28-40`）が使う`_parameter.BoneRotateSpeed`を固定値から可変値に変更する。`TryCalcTargetRotation`内で既に対象方向とカメラ方向の`angle`（度）を計算しているため（`CameraLockOnRotationCalculator.cs:99`）、これを`Update`側でも参照できるようにする。

- `TryCalcTargetRotation`のシグネチャに`out float angle`を追加し、計算済みの角度を返すようにする（マージン内で早期returnする場合は`angle`にその時点の値を入れて返す）。`TryGetTargetRotation`（公開API、`CameraSystemView.Tick`が`boneTargetRotation`予測に使用）は角度を使わないため、角度を無視するオーバーロードのまま維持する。
- `Update`内で、`effectiveSpeed = Mathf.Lerp(LockOnRotationMinSpeed, BoneRotateSpeed, Mathf.Clamp01(angle / LockOnRotationSpeedAngleRange))`のように角度に応じた回転速度を算出し、`Quaternion.Slerp(cameraBoneRotation, target, 1f - Mathf.Exp(-effectiveSpeed * context.DeltaTime))`へ渡す。`BoneRotateSpeed`（既存フィールド）を「角度が最大に離れているときの速度上限」、新設の`LockOnRotationMinSpeed`を「対象にほぼ正対しているときの速度下限」として扱う。
- `CameraConfig`に`LockOnRotationMinSpeed`（既定は`BoneRotateSpeed`より小さい値）、`LockOnRotationSpeedAngleRange`（度、この角度以上でBoneRotateSpeedに到達、既定60度程度）を追加する。
- 3.6節で`lockOnOffset`引数自体を削除するため、`TryCalcTargetRotation`/`TryGetTargetRotation`/`Update`のシグネチャは「`lockOnOffset`を除去しつつ`out float angle`を追加する」形にまとめて変更する（2回に分けて変更しない）。

### 3.6 仕様⑥: 相対オフセット仕様（`CameraLockOnOffsetCalculator`）の削除

3.2節の通り、ロックオン中の視点操作は「強く行えばオートロックオン解除」という意味だけを持つようになるため、相対オフセットで対象の周囲を覗き込む仕様は不要になる。以下を削除する。

- `Assets/Scripts/Runtime/4.View/InGame/Camera/Calculation/CameraLockOnOffsetCalculator.cs`を削除する。
- `CameraConfig`から`LockOnOffsetSensitivity`/`LockOnOffsetClamp`/`LockOnOffsetRecenterDelay`/`LockOnOffsetRecenterSpeed`（プロパティ・バッキングフィールド・`[Header("Lock On View")]`内の該当項目）を削除する。
- `CameraLockOnRotationCalculator`から`lockOnOffset`引数と`ApplyOffset`メソッドを削除し、`Quaternion.LookRotation(followDir, Vector3.up)`（マージン外の場合はマージンオフセット込み）をそのまま`targetRotation`として返す形に戻す。
- `CameraLookAtRotationCalculator.Update`から`lockOnOffset`引数と`offsetRotation`の合成（`CameraLookAtRotationCalculator.cs:57-59`）を削除する。
- `CameraUpdateFrame`から`LockOnOffset`フィールドを削除する。
- `CameraSystemView`から`_lockOnOffsetCalculator`フィールド・`Initialize`引数・`_lockOnOffsetCalculator.Reset()`の全呼び出し（`TryActiveAutoLockOn`/`ToggleLockOnState`/`ClearLockOn`/`LookFlickHandlerMobile`）を削除する（3.2節で`CameraLockOnBreakTracker.Reset()`がこれらの呼び出し箇所を実質的に置き換える）。
- `CameraSystemInitializer.Initialize`から`CameraLockOnOffsetCalculator`の生成・DI配線を削除する。

## 4. フェーズ構成

### Phase 1: 仕様⑥（相対オフセット仕様の削除）
1. `CameraLockOnOffsetCalculator.cs`を削除し、`CameraConfig`の該当4項目を削除する。
2. `CameraLockOnRotationCalculator`/`CameraLookAtRotationCalculator`/`CameraUpdateFrame`/`CameraSystemView`/`CameraSystemInitializer`から`lockOnOffset`関連の引数・フィールド・呼び出しを除去する。
3. 実機確認: ロックオン中に視点操作しても対象方向以外を向かなくなる（覗き込みができなくなる）ことを確認する。この時点ではまだ②（強操作解除）が無いため、視点操作自体はロックオンに一切影響しない状態になる。

### Phase 2: 仕様②（強操作によるオートロックオン解除）
1. `CameraLockOnBreakTracker`を新設し、`CameraConfig`に`LockOnBreakWindow`/`LockOnBreakThreshold`を追加する。
2. `CameraSystemView.BuildFrame`のビューポート判定（`LockOnAuto`限定）と並列に、`CameraLockOnBreakTracker`の評価・`ClearLockOn()`呼び出しを追加する。ロックオン開始/解除時に`Reset()`を呼ぶ。
3. 実機確認: オートロックオン中、ゆっくりした視点操作では解除されず、素早く強く操作すると解除されること。手動ロックオンは強操作でも解除されないままであることを確認する。

### Phase 3: 仕様④（自分の攻撃命中によるオートロックオンの継続時間延長）
1. `CameraConfig`に`AutoLockOnReleaseDelay`を追加する。
2. `CameraSystemView`で`EventBus<EOnTakeDamage>`の購読/解除を追加し、`_autoLockOnIdleTimer`の初期化・リセット（＝命中による延長）・加算・閾値判定を実装する。
3. 実機確認: オートロックオン中に自分の攻撃を対象へ当て続けると解除されず継続時間が延び続けること、数秒攻撃が命中しないと自動解除されることを確認する。手動ロックオンはこの仕組みの対象外であることを確認する。

### Phase 4: 仕様⑤（ロックオン追従速度の角度依存可変化）
1. `CameraLockOnRotationCalculator.TryCalcTargetRotation`に`out float angle`を追加し、`Update`側で角度に応じた可変速度を計算するよう変更する。
2. `CameraConfig`に`LockOnRotationMinSpeed`/`LockOnRotationSpeedAngleRange`を追加する。
3. 実機確認: ロックオン開始直後（対象から大きく外れている状態）は素早く正面へ向き、正対に近づくにつれて収束がゆるやかになることを確認する。

### Phase 5: 仕様③（移動方向へのカメラ追従）
1. `CameraUpdateContext`に`PlayerForward`を追加し、`CameraSystemView.BuildFrame`から渡す。
2. `CameraConfig`に`MoveFollowRotationSpeed`/`MoveFollowIdleLookThreshold`を追加する。
3. `CameraFreeLookRotationCalculator.Update`に、無操作時の移動方向追従処理を追加する。
4. 実機確認: 非ロックオン時、視点操作をせず移動だけを続けると、カメラが徐々にプレイヤーの背後（進行方向）へ回り込むことを確認する。視点操作を再開すると即座に通常のフリールックに戻ることを確認する。

### Phase 6: 仕様①（ロックオンセレクトの入力統合）
1. `InputActionKind`に`LockOnSelect = 105`を追加する。
2. `KillChordInputActioMap.inputactions`のInGameマップに`LockOnSelect`アクション（1D Axis複合、キーボード: Negative=Q/Positive=R、ゲームパッド: Negative=leftShoulder/Positive=rightShoulder）を追加する。
3. `PlayerInputView`に`OnLockOnSelectInput`（PC/ゲームパッド用）と`OnMobileLockOnSelectInput`（モバイル用）を追加し、`CacheActions`/`OnEnable`/`OnDisable`に配線する。
4. `MobileInput.OnTrackedTouchCanceled`の`OnMobileLookFlick(displacement.normalized)`呼び出しを`OnMobileLockOnSelect(Mathf.Sign(displacement.x))`に置き換える（フリック判定自体のロジックは変更しない）。
5. `PlayerInputView.OnMobileLookFlickInput`と`CameraSystemView.LookFlickHandlerMobile`を廃止し、`CameraSystemView`に`LockOnSelectHandler`（PC/ゲームパッド用）・`LockOnSelectHandlerMobile`（モバイル用）・共通の`TrySelectAdjacentTarget(float direction)`を実装する。`LockOnManual`中のみ動作するという既存の制限は維持する。
6. 実機確認: PCでQ/Rキー、ゲームパッドでL1/R1、モバイルでフリック（左右)を行った際、いずれも手動ロックオン中の対象が入力方向側の別対象へ切り替わることを確認する。対象が居ない場合は現在対象を維持することを確認する。

## 5. リスク・注意点

- **Phase 1と2の順序**: 仕様⑥の削除を仕様②より先に行うのは、削除中に一時的に「視点操作がロックオンに一切影響しない」状態を経由するためで、影響範囲の小さいPhaseから着手する意図。実装者の裁量でPhase 1と2をまとめて1つの変更として進めても問題ない。
- **仕様②の閾値調整**: `LockOnBreakWindow`/`LockOnBreakThreshold`は実機でのプレイフィールに強く依存する。閾値が低すぎると通常の追い視点操作でもオートロックオンが外れやすく、高すぎると解除操作自体が機能しなくなる。3.2節で採用した指数減衰アキュムレータは正確な「直近N秒間の合計」ではなく近似のため、体感と数値が合わない場合はスライディングウィンドウ方式（案A）への切り替えも検討する。
- **仕様④のタイミング**: `EOnTakeDamage`は自分の攻撃が対象にダメージを成立させた瞬間にのみ発火するため、攻撃モーション自体は繰り返していても命中しなければ継続時間は延長されない。回避行動中の敵などに攻撃を外し続けるケースでは数秒でロックオンが外れる仕様として意図通りだが、プレイフィールとして厳しすぎないか実機調整が必要。
- **仕様⑤の角度取得箇所の変更**: `TryCalcTargetRotation`のシグネチャ変更は`TryGetTargetRotation`（`CameraSystemView.Tick`が`boneTargetRotation`予測に使用、`CameraSystemView.cs:297-303`）にも影響する。角度を使わない呼び出し元まで巻き込んで無駄な計算をさせないよう、オーバーロード分割の実装粒度に注意する。
- **仕様③と仕様②の相互作用**: 移動方向追従（仕様③）は視点入力が無いときのみ動作するため、ロックオン解除直後に「移動方向へゆっくり戻る」動きと「強操作の余韻」が同時に起きないよう、`CameraLockOnBreakTracker.Reset()`のタイミング（ロックオン解除時）を確実に行う。
- **仕様①のUXデグレ**: 2.1節の通り、現状のフリックは上下方向も含めて候補評価しているが、統一後は左右のみになる。斜めや縦方向のフリックで意図した対象に切り替えられなくなる体感変化があるため、モバイル実機で違和感が無いか確認する。
- **モバイルのフリック閾値**: `_flickMaxDuration`/`_flickMinDistance`は既存の実装値をそのまま使う想定だが、左右のみの判定に変わることで誤検知の傾向が変わる可能性があるため、実機（実際の指でのタッチ操作）での再チューニングを想定しておく。
- **Q/Rキーの割り当て**: `R`キーは一般的にリロード等に使われがちなキーだが、本プロジェクトでは指示通りQ/Rを既定案とする。Input Actionsのバインディングを変更するだけで済むため、後日別キーへ変更する場合もコード変更は不要。
- **オートロックオン中のロックオンセレクト**: 2.1節・3.1節の通り、現状も今回の統一後も`LockOnManual`限定の挙動を維持する（現状追随）。オートロックオン中に対象を切り替えたいニーズが出た場合は別途検討する。
