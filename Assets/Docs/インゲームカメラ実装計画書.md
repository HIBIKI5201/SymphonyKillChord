# インゲームカメラ実装計画書

- 作成日: 2026-07-15
- 対象: InGameのカメラ（`CameraSystemView`）およびロックオン（Targetモジュール）まわりの仕様変更
- 前提: Camera/TargetモジュールともにDomain/Application層を持たない現状構成（`Assets/Docs/ScriptsDocs/Modules/NotionModuleDocs/Camera.md`/`Target.md`参照）を踏襲し、新規ロジックもView層のプレーンC#クラス（既存の`*Calculator`と同じ位置づけ）として追加する。層構成そのものの是正（Domain/Application層の新設）は本計画のスコープ外とする。

---

## 1. 目的

現在のロックオンカメラには次の課題があり、これを5つの仕様変更で解決する。ロックオンには**自動ロックオン（`LockOnAuto`、攻撃入力で発動）**と**手動ロックオン（`LockOnManual`、専用ボタンで発動）**の2種類があり、変更内容はどちらに対するものかを区別して扱う。

| # | 現状 | 変更後 | 対象 |
| --- | --- | --- | --- |
| ① | カメラ操作（スティック/マウス入力）を行うと、自動ロックオンが即座に解除される | 操作してもロックオンは解除されない | **自動ロックオンのみ**（手動は元々操作で解除されない） |
| ② | ロックオン対象がカメラの視野から外れても、対象が生存している限りロックオンは維持され続ける | 対象がカメラの視野範囲外に出たらロックオンを解除し、自由カメラへ移行する | **自動ロックオンのみ** |
| ③ | ロックオン中の操作入力は無視される（常に対象方向へ強制的に向く） | 操作すると対象を基準にした相対位置を向く（右に入力→対象の右側を注視） | 自動・手動どちらも |
| ④ | ③の相対オフセットを戻す手段がない | 無操作が数秒続くと、相対オフセットが自動的に対象方向へ戻る | 自動・手動どちらも |
| ⑤（新規） | ③の相対オフセットで向いた先に別の敵がいても、ロックオン対象は変わらない | 手動ロックオン中に③の操作で向いた方向に別の敵がいれば、その敵へロックオン対象を切り替える | **手動ロックオンのみ、かつ今回は入力デバイスがモバイル（タッチのフリック）の場合のみ実装する**（PC/ゲームパッドでの切り替え手段は別途検討、本計画では未着手） |
| ⑥ | ロックオンUIは「なし/ロックオン中」の2値のみ | 「候補（今攻撃したらロックオンする対象）」の中間ステートを追加し、点のようなUIで表示する | （ロックオン種別に依らないUIの話） |

## 2. 現状整理（調査済み）

### 2.1 カメラのロックオン状態

`CameraSystemView`（`Assets/Scripts/Runtime/4.View/InGame/Camera/CameraSystemView.cs`）が唯一のカメラ制御クラスで、状態機械やStrategyパターンは存在せず、`private enum CameraLockOnState : byte { Free, LockOnAuto, LockOnManual }` の3値と`if/else`分岐だけで挙動を切り替えている。

- `LockOnManual`: 専用のロックオンボタン（`ToggleLockOnState`）でON/OFFする。現状すでに操作では解除されない。
- `LockOnAuto`: 攻撃入力（`OnAttack`→`TryActiveAutoLockOn`）で発動する。**`BuildFrame`内で、`LockOnAuto`状態かつ何らかの入力（見た目操作 or 移動スティック）があると即座に`ClearLockOn()`が呼ばれる**（該当箇所: `CameraSystemView.BuildFrame`）。これが仕様①の解除対象コード。

```csharp
// CameraSystemView.BuildFrame（現状、変更対象）
if (_lockOnState == CameraLockOnState.LockOnAuto
    && (context.Input.sqrMagnitude > float.Epsilon || context.MoveInput.sqrMagnitude > float.Epsilon))
{
    ClearLockOn();
}
```

`ClearLockOn()`の他の呼び出し箇所は、①ロックオンボタンの明示的トグルオフ、②対象消失時（`_getCurrentTargetPositionFunc().HasTarget == false`）の2つで、いずれも維持する。

### 2.2 ロックオン中の回転計算

- `CameraLockOnRotationCalculator`: カメラの「ボーン」を対象方向へ回転させる。`LockOnAngleMargin`によるデッドゾーンを持つが、プレイヤー入力は一切参照していない。
- `CameraLookAtRotationCalculator`: フリールックの注視点と「プレイヤー・対象の中間点」を`_ratio`（`LockOnRotationSpeed`で補間）でブレンドする。こちらも入力は参照しない。
- 対して`CameraFreeLookRotationCalculator`（フリールック時のみ使用）は生の入力をヨー・ピッチへそのまま積分している。

→ 仕様③④を実現するには、ロックオン時にも入力を積分する経路が必要だが、それを既存の「対象方向」計算に**加算するオフセット**として独立させ、無操作時は自動的にゼロへ戻す仕組みを新設する。

### 2.3 ロックオンUI

専用のレティクル/照準UIは存在せず、敵体力バーHUD（`HUDEnemyHealthView`/`HUDEnemyHealthViewModel`/`HUDEnemyHealthPresenter`/`HUDEnemyHealthInitializer`）がロックオンインジケーターを兼ねている。`HUDEnemyHealthPresenter.Update`が`TargetSystemController.TryGetCurrentTargetEntity`/`TryGetCurrentTargetPosition`の成否だけで表示・非表示（`IsLockon: bool`）を切り替えている。

### 2.4 対象選定ロジック（Targetモジュール）

`TargetingSystem`（`Assets/Scripts/Runtime/4.View/InGame/Target/TargetingSystem.cs`）内の`SelectTarget(center, direction)`が、正面方向内積優先・内積が負なら距離フォールバックという選定を行うが、**`ChangeTarget`経由でのみ呼ばれ、呼ぶたびに`_currentTarget`を書き換える副作用がある**。「候補」を継続的に覗き見る非破壊のクエリは存在しない。

`TryActiveAutoLockOn(currentPosition, direction)`（`OnAttack`から呼ばれる）に渡される`direction`は**カメラの現在の前方向`GetCurrentForward()`**であり、`center`は**プレイヤー位置**である。候補プレビューも同じ`(プレイヤー位置, カメラ前方向)`のペアを使うことで、実際のロックオン選定と一致した見た目にする。

## 3. 設計方針

### 3.1 仕様①②: 解除条件の入れ替え（自動ロックオンのみが対象）

①②はいずれも**自動ロックオン（`LockOnAuto`）専用の変更**である。手動ロックオン（`LockOnManual`）は現状から挙動を変えない＝引き続き「操作では解除されない」「視野から外れても解除されない、対象消失時とボタンの明示的トグルオフでのみ解除される」ままとする。

`BuildFrame`の「入力があれば`LockOnAuto`を解除する」分岐を丸ごと削除する。これにより`LockOnAuto`は「操作では解除されない」という点でのみ`LockOnManual`と同じ挙動になるが、次の視野判定は`LockOnAuto`のときにしか行わない。

代わりに、**`LockOnAuto`の対象がカメラの視野範囲外に出たかどうか**を毎フレーム判定し、外れていれば`ClearLockOn()`を呼ぶ条件を追加する。`LockOnManual`のときはこの判定自体を行わない（手動ロックオンは画面外に出ても維持される、現状通りの挙動）。判定方法は次の2案を検討した。

| 案 | 内容 | 採否 |
| --- | --- | --- |
| A. ビューポート判定 | `Camera.WorldToViewportPoint(targetPosition)`の結果、x/yが`[0,1]`範囲内かつzが正（カメラ前方）かを判定。実際の画面に映っているかを正確に反映する | **採用** |
| B. 角度判定 | カメラ前方向と対象方向の角度がFOVの半分を超えたら解除 | 不採用（アスペクト比を考慮できず、ビューポート判定と等価かそれ以下の精度） |

ビューポート判定はUI側（`HUDEnemyHealthViewModel.Update`）で使っている`WorldToScreenPoint`と同系統の手法であり、既存パターンを踏襲できる。

- 新規クラス`CameraLockOnRangeChecker`（View層、プレーンC#、`Assets/Scripts/Runtime/4.View/InGame/Camera/Calculation/`）:
  - `bool IsWithinRange(Camera camera, Vector3 targetPosition)` を提供。
  - `CameraConfig`に**マージン**（`LockOnViewportMargin`、0〜0.5程度、画面端からどれだけ内側に入っていれば「視野内」とみなすか）を追加し、画面ギリギリでのロックオン解除チラつき（ハンチング）を防ぐ。マージンは表示上のちらつき防止のためであり、UIの候補判定（4章）とは別の値で良い。
- `CameraSystemView`は現在`_cameraT`（Transform）しか保持していない可能性があるため、ビューポート判定に必要な`UnityEngine.Camera`コンポーネント参照を追加で取得・保持する（`_cameraT.GetComponent<Camera>()`、`Initialize`時に一度だけ取得）。
- `BuildFrame`（またはロックオン中のみ実行する`Tick`内の判定箇所）で、`_lockOnState == CameraLockOnState.LockOnAuto`のときに限り`CameraLockOnRangeChecker.IsWithinRange(...)`を評価し、`false`を返したら`ClearLockOn()`を呼ぶ。既存の「対象消失」チェック（Auto/Manual共通）とは別条件として、Auto限定のガードを一つ追加する形になる。

### 3.2 仕様③④: ロックオン中の相対オフセット＋自動再センタリング（自動・手動共通）

このオフセット機構は`LockOnAuto`/`LockOnManual`のどちらでロックオン中でも同じように動作する（`_lockOnState`の種別を見ずに、「ロックオン中かどうか」だけで判定する）。手動ロックオン時のみ、このオフセットに応じてさらに対象切り替えが発生する（3.3節）。

新規クラス`CameraLockOnOffsetCalculator`（View層、プレーンC#、既存Calculator群と同じ位置）を追加し、ロックオン中の入力をこのクラスに閉じ込める。

```csharp
// イメージ（実装時に命名・シグネチャは要調整）
public sealed class CameraLockOnOffsetCalculator
{
    private Vector2 _offset;      // 現在のヨー・ピッチオフセット（度）
    private float _idleTime;      // 無操作の継続時間

    public Vector2 Update(in CameraUpdateContext context, in CameraConfig config)
    {
        if (context.Input.sqrMagnitude > float.Epsilon)
        {
            _offset += context.Input * config.LockOnOffsetSensitivity * context.DeltaTime;
            _offset = ClampOffset(_offset, config.LockOnOffsetClamp);
            _idleTime = 0f;
        }
        else
        {
            _idleTime += context.DeltaTime;
            if (_idleTime >= config.LockOnOffsetRecenterDelay)
            {
                _offset = Vector2.Lerp(_offset, Vector2.zero, config.LockOnOffsetRecenterSpeed * context.DeltaTime);
            }
        }
        return _offset;
    }

    public void Reset() { _offset = Vector2.zero; _idleTime = 0f; }
}
```

- 挙動: 入力がある間はオフセットを加算（`LockOnOffsetClamp`で上下左右の可動範囲をクランプし、対象を見失わない範囲に収める＝「対象の右側を注視する」ような見え方を実現しつつ、真後ろを向くような破綻は防ぐ）。入力が止まると`LockOnOffsetRecenterDelay`秒（数秒、要調整可能な値としてConfig化）待ってから`LockOnOffsetRecenterSpeed`で滑らかにゼロへ戻す。
- 適用箇所: `CameraLockOnRotationCalculator`・`CameraLookAtRotationCalculator`が計算する「対象方向を向く」ベース回転に対し、このオフセットを**加算**した回転を最終的なボーン回転として使う（`Quaternion`のヨー・ピッチ加算、または既存の角度計算に足し込む形で実装）。
- ロックオンが解除された瞬間（`ClearLockOn()`）に`CameraLockOnOffsetCalculator.Reset()`を呼び、次回ロックオン時にオフセットが持ち越されないようにする。
- `CameraConfig`への追加項目: `LockOnOffsetSensitivity`（入力→オフセットの感度）、`LockOnOffsetClamp`（オフセットの最大角度、ヨー・ピッチ別に持たせるかVector2でまとめるかは実装時に決定）、`LockOnOffsetRecenterDelay`（再センタリング開始までの秒数）、`LockOnOffsetRecenterSpeed`（再センタリングの補間速度）。

### 3.3 仕様⑤: 手動ロックオン中、フリック入力で別の敵に切り替える（モバイルのみ）

検討の結果、切り替えのトリガーを「保持中のオフセット方向」から**独立したフリック（素早く払うようなドラッグ）判定**に変更する。理由は、スティック入力は「保持=③のオフセット」「素早く倒して離す=⑤の切り替え」を入力の"静止状態の有無"で区別できるが、**マウスの移動量は元々が瞬間的な差分であり、③（覗き込み）と⑤（切り替え）を同じ基準で区別できないため**。この問題はPC（マウス・ゲームパッド）での解決策は保留とし、今回はスティック的な区別が付けやすい**モバイル（タッチのフリック）専用の機能として実装する**。PC/ゲームパッドでの対象切り替え手段は別途検討し、本計画では実装しない（自動・手動ともに、PC/ゲームパッド入力時は③④のみが有効で、⑤に相当する切り替え操作は存在しない状態のままにする）。

手動ロックオン（`LockOnManual`）中に、タッチのフリック入力を検知した方向を評価し、現在の対象より条件に合う敵が見つかれば対象を切り替える。既存の選定ロジック（内積優先・距離フォールバック、Phase 0で抽出する`EvaluateBestTarget`）をそのまま再利用する。

- **フリックの検知**: モバイル入力（`LookHandlerMobile`系）側で、短時間（例: 100〜150ms程度、要チューニング）のドラッグ量・速度が閾値を超えた場合を「フリック」として検知し、その方向ベクトルを1回だけ通知するイベントとして扱う（3.2節の毎フレーム連続入力である`context.Input`とは別の、単発トリガーにする）。これにより、③（オフセットでの覗き込み）用の連続入力と、⑤（切り替え）用の単発フリックが入力経路として明確に分離される。
- **評価タイミング・入力**: `_lockOnState == CameraLockOnState.LockOnManual`のときにフリックイベントを受け取ったら、その瞬間の`EvaluateBestTarget(playerPosition, flickDirection)`を1回評価する。`flickDirection`は「フリック検知時点のカメラ前方向にフリック方向を加算した方向」とする。
- **切り替え条件**: 評価結果が現在の`_currentTarget`と異なる場合のみ、`ChangeTarget`相当の処理で対象を切り替える（`TargetingSystem`に`_currentTarget`を直接差し替える経路を用意する。`ChangeTarget`の再選定ロジックとは別に、「この対象へ切り替える」というAPIが必要になる）。
- **切り替え後のオフセット**: 対象を切り替えた瞬間、`CameraLockOnOffsetCalculator.Reset()`を呼びオフセットをゼロへ戻す。
- **チャタリング対策**: 単発トリガーになったことで、3.2節で懸念していた「連続評価による高速切り替え」は構造的に起きなくなる（フリック1回につき評価も1回のみ）。ただし2体の敵がほぼ同方向にいる場合の意図しない選択を減らすため、既存の`SelectTarget`と同じ内積しきい値（`DOT_FORWARD_THRESHOLD`）は踏襲する。
- **PC/ゲームパッドの扱い**: `CameraSystemView`側は「フリックイベントを受け取ったら評価する」というAPIのみを持ち、フリック検知そのものはモバイル入力ハンドラ側の責務とする。将来PC/ゲームパッド向けの切り替え手段（専用ボタン等）を追加する際も、同じ「フリックイベント相当のトリガー」を発行するだけで良いようにしておく。

### 3.4 仕様⑥: ロックオンUIへの「候補」ステート追加

「候補」は**非破壊で`_currentTarget`を書き換えない**選定結果として実装する必要がある。既存の`TargetingSystem.SelectTarget`は`ChangeTarget`専用の副作用込みメソッドなので、スコアリング部分を再利用可能な形に切り出す。

1. **Targetモジュール側の変更**（`TargetingSystem.cs`・`ITargetSystemViewModel`・`TargetSystemController`）
   - `SelectTarget`の内部ロジック（内積優先・距離フォールバック）を、`_currentTarget`を書き換えない純粋な選定メソッドとして抽出する（例: `private ITargetableViewModel EvaluateBestTarget(in Vector3 center, in Vector3 direction)`）。既存の`SelectTarget`（`ChangeTarget`用）はこれを呼んで結果を`_currentTarget`に反映する形にリファクタリングする（挙動変更なし）。
   - 新規に`_currentCandidate`フィールドと、非破壊の更新メソッド`UpdateCandidate(in Vector3 center, in Vector3 direction)`（`EvaluateBestTarget`の結果を`_currentCandidate`に反映するだけ、`_currentTarget`には触れない）を追加する。
   - 参照用に`TryGetCurrentCandidateEntity(out CharacterEntity)`/`TryGetCurrentCandidatePosition(out Vector3)`を、既存の`TryGetCurrentTargetEntity`/`TryGetCurrentTargetPosition`と対になる形で追加する。
   - `ChangeTarget`が実際にロックオンを確定させた際は`_currentCandidate`をクリアする（表示の優先度はPresenter側でも制御するため必須ではないが、状態の一貫性のために行う）。

2. **カメラ側の変更**（`CameraSystemView.cs`・`CameraSystemInitializer.cs`）
   - `CameraSystemInitializer`で、既存の`ChangeTarget`/`ClearTarget`ラムダと同様に`UpdateCandidate`ラムダを`CameraSystemView.Initialize(...)`へ渡す。
   - `CameraSystemView.Tick`（または`BuildFrame`）で、**ロックオンしていない間だけ**毎フレーム`_updateCandidateAction(_playerT.position, GetCurrentForward())`を呼ぶ。ロックオン中は候補評価を行わない（呼ぶ必要がないため）。

3. **UI側の変更**（`HUDEnemyHealthView.cs`・`HUDEnemyHealthViewModel.cs`・`HUDEnemyHealthPresenter.cs`）
   - 現状の`IsLockon: bool`を3値の表示ステート（例: `enum LockOnDisplayState { Hidden, Candidate, LockedOn }`）に拡張する。
   - `HUDEnemyHealthPresenter.Update`のロジックを次のように変更する:
     1. `TryGetCurrentTargetEntity`/`TryGetCurrentTargetPosition`が成功 → `LockedOn`（既存通り、体力バー＋対象位置）。
     2. 失敗した場合、`TryGetCurrentCandidateEntity`/`TryGetCurrentCandidatePosition`が成功 → `Candidate`（体力は使わず、位置のみ反映）。
     3. どちらも失敗 → `Hidden`。
   - `HUDEnemyHealthView.SetLockonEnable(bool)`を`SetDisplayState(LockOnDisplayState state)`に置き換え、`Candidate`時は体力バー画像を隠して「点」用の小さいスプライト（ユーザー指示通り、まずは仮のドット画像で代用）のみ表示、`LockedOn`時は従来通り体力バー一式を表示する。
   - クラス名（`HUDEnemyHealthView`等）は据え置く。「候補」を含む名称へのリネームは本計画のスコープ外の任意クリーンアップとする（既存の参照箇所が多く、リネームは別タスクとして切り出すことを推奨）。

## 4. フェーズ構成

### Phase 0: 下準備（挙動変更なしのリファクタリング）
1. `TargetingSystem.SelectTarget`のスコアリング部分を非破壊の`EvaluateBestTarget`に抽出し、`ChangeTarget`はそれを呼ぶ形に書き換える（挙動は現状と完全に同一であることをテスト/実機確認）。

### Phase 1: 仕様①②（自動ロックオンの解除条件の入れ替え）
1. `CameraSystemView.BuildFrame`から入力によるロックオン解除分岐を削除する（Auto/Manual共通で「操作では解除されない」状態にする）。
2. `CameraLockOnRangeChecker`を新設し、`CameraConfig.LockOnViewportMargin`を追加する。
3. `CameraSystemView`に`Camera`コンポーネント参照を追加し、**`LockOnAuto`のときに限り**毎フレーム視野内判定を行い、外れたら`ClearLockOn()`を呼ぶ（`LockOnManual`はこの判定を行わず、現状通り画面外でも維持される）。
4. 実機確認: 自動ロックオン中に操作してもロックオンが外れないこと、自動ロックオン対象を画面外へ追い出すと自由カメラに切り替わること、手動ロックオンは画面外に出ても維持されたままであることを確認する。

### Phase 2: 仕様③④（相対オフセット＋自動再センタリング、自動・手動共通）
1. `CameraLockOnOffsetCalculator`を新設し、`CameraConfig`に`LockOnOffsetSensitivity`/`LockOnOffsetClamp`/`LockOnOffsetRecenterDelay`/`LockOnOffsetRecenterSpeed`を追加する。
2. `CameraLockOnRotationCalculator`/`CameraLookAtRotationCalculator`に、`CameraLockOnOffsetCalculator`が計算したオフセットを加算する処理を組み込む（`LockOnAuto`/`LockOnManual`どちらでも動作する）。
3. `ClearLockOn()`時、および3.3節の対象切り替え時に`CameraLockOnOffsetCalculator.Reset()`を呼ぶ。
4. 実機確認: 自動・手動どちらのロックオン中でも入力すると対象を基準にした相対方向を向くこと、数秒放置すると対象正面へ戻ることを確認する。

### Phase 3: 仕様⑤（モバイル限定・フリックによる対象切り替え）
1. モバイル入力ハンドラ（`LookHandlerMobile`系）に、短時間ドラッグの速度・量から「フリック」を検知し、方向を伴う単発イベントとして発行する処理を追加する。
2. Phase 0で抽出した`EvaluateBestTarget`を使い、`LockOnManual`中にフリックイベントを受け取った瞬間だけ評価する処理を`CameraSystemView`（または`TargetingSystem`側の新規メソッド）に追加する。
3. `TargetingSystem`に、選定ロジックを経由せず対象を直接差し替えるAPI（例: `SwitchTarget(ITargetableViewModel)`）を追加する。
4. 評価結果が現在の対象と異なる場合のみ切り替え、切り替え時に`CameraLockOnOffsetCalculator.Reset()`を呼ぶ。
5. 実機確認: モバイル実行環境で、手動ロックオン中に別の敵の方向へフリックすると、その敵へロックオンが切り替わること、PC/ゲームパッド入力ではこの切り替えが一切発生しないこと、自動ロックオンではこの切り替えが起きないことを確認する。

### Phase 4: 仕様⑥（候補UI）
1. `TargetingSystem`/`ITargetSystemViewModel`/`TargetSystemController`に`_currentCandidate`・`UpdateCandidate`・`TryGetCurrentCandidateEntity`/`TryGetCurrentCandidatePosition`を追加する（Phase 0の`EvaluateBestTarget`を再利用）。
2. `CameraSystemInitializer`で`UpdateCandidate`ラムダを配線し、`CameraSystemView`が非ロックオン時に毎フレーム呼び出すようにする。
3. `HUDEnemyHealthView`/`ViewModel`/`Presenter`を3値の`LockOnDisplayState`に拡張し、`Candidate`時は仮のドット画像を表示する。
4. 実機確認: 非ロックオン時に狙える敵へ点UIが表示され、攻撃するとそのままロックオン（体力バー表示）に切り替わることを確認する。

## 5. リスク・注意点

- **ビューポート判定のマージン調整**: `LockOnViewportMargin`が小さすぎると画面端で自動ロックオン解除のハンチングが起きやすい。実機でのプレイフィールを見ながら調整が必要。
- **オフセットのクランプ範囲**: `LockOnOffsetClamp`を広く取りすぎると「対象を見失う」体感になり、狭すぎると仕様③の意味が薄れる。既存の`LockOnAngleMargin`（現状のデッドゾーン）との役割の違いを混同しないよう、実装時に両者の関係を整理する。
- **フリック検知の閾値調整（モバイルのみ）**: 3.3節のフリック判定は「短時間ドラッグの速度・量」の閾値に依存する。閾値が低すぎると通常の視点操作（③）がフリックとして誤検知されやすく、高すぎるとフリック自体が発生しにくくなる。実機（実際の指でのタッチ操作）での調整が必須。フリックを単発トリガー化したことで、3.2節時点で懸念していた「連続評価による高速切り替え」は構造的に発生しない。
- **切り替え時のオフセットリセット漏れ**: 対象切り替え時に`CameraLockOnOffsetCalculator.Reset()`を呼び忘れると、新しい対象に対して古いオフセットが残ったまま適用され、カメラが不自然な方向を向く不具合になりやすい。
- **自動ロックオン・PC/ゲームパッドでは仕様⑤が発生しないことの徹底**: 仕様⑤は「手動ロックオン」かつ「モバイル」の組み合わせでのみ有効にする。`_lockOnState`の分岐漏れやプラットフォーム判定漏れがあると、自動ロックオン中やPC/ゲームパッドでも対象が勝手に切り替わってしまう。Phase 3実装時・実機確認時に、対象の組み合わせ（Auto/Manual × Mobile/PC/ゲームパッド）を網羅してテストする。
- **PC/ゲームパッドの対象切り替え手段が未定のまま残る**: 本計画ではPC/ゲームパッドでの切り替え入力を意図的に保留にしている。手動ロックオン時に「別の敵に切り替えたい」というニーズ自体はPC/ゲームパッドでも起こり得るため、後日どのような入力（専用ボタン等）にするかの検討が別途必要になる。
- **候補評価の毎フレームコスト**: `UpdateCandidate`は非ロックオン時に毎フレーム全登録対象を走査する（`EvaluateBestTarget`の計算量は現状の`SelectTarget`と同じ）。現状の敵数規模では問題にならない想定だが、大量の敵が同時に登録される場面がある場合は間引き（数フレームに1回評価等）を検討する。
- **`HUDEnemyHealthPresenter`の優先順位**: ロックオン中に別の候補が入れ替わっても`Candidate`表示は行わない（非ロックオン時のみ評価するため、実装上も自然に優先順位が付く）。
- **クラス名と役割のズレ**: `HUDEnemyHealthView`等が「候補」表示も兼ねることになり、クラス名が実態と多少ズレる。リネームは影響範囲が広いため本計画では見送るが、将来的なクリーンアップ候補として記録しておく。
