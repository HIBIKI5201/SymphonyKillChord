# インゲーム戦闘チュートリアル設計計画書

- 作成日: 2026-07-23
- 対象: 初回起動時にタイトルの「はじめる」から直行するチュートリアル戦闘の、戦闘内フロー詳細設計
- 前提: 別途共有された仕様書のうち、以下の理由で今回はスコープ外とする

| 項目 | 扱い |
|---|---|
| アウトグームの説明(ホーム/作戦/改造/研究) | 不要。今回は対象外 |
| チュートリアル専用BGM制御(4拍子/3拍子の切替) | 不要。現状のBGM選定ロジックを変更しない |
| Triadによる無線越しの口頭説明 | 不要。キャラクター演出は追加しない |
| キルコード装備の固定上書き(スキル0＆13) | 不要。セーブデータの初期装備をそのまま使う |
| ストーリー導入(バトル前の状況説明) | 不要 |

つまり本計画書が扱うのは「**バトルフェーズのチュートリアル**」のみであり、既存の`Assets/Docs/初回チュートリアル直接出撃化計画書.md`(タイトル→チュートリアル戦闘への直行導線)とは独立に、戦闘シーン内の進行フローを設計する。

## 1. 現状の実装(前提として再利用するもの)

チュートリアル専用モジュールではなく、Missionシステム共通の「目標シーケンス」機構として実装済み。

- `ObjectiveSequenceClearCondition`(`1.Domain/InGame/Mission/ClearCondition/`) — 複数の`ObjectiveSequenceStep`(達成条件＋案内メッセージ)を配列で持ち、先頭から見て最初の未達成ステップを「現在の目標」として都度計算する複合クリア条件。
- `ObjectiveSequenceClearConditionAsset`/`ObjectiveSequenceStepAsset`(`5.InfraStructure/InGame/Mission/`) — 上記をInspectorで組み立てるアセット。既存の`MissionClearConditionAssetBase`ファミリー(`EnemyKillCountClearConditionAsset`等)をそのまま子条件として再利用できる。
- `MissionRuntimeService.OnObjectiveStepChanged`(`2.Application/InGame/Mission/`) — 現在ステップが変化した際に発火するイベント。
- `ObjectiveSequenceDirector`(`6.Composition/InGame/Mission/`) — ステップ変化に応じて、ゲームプレイの一時停止＋`ObjectiveSequenceDialogueView`(会話ポップアップ)表示＋入力待ちを行う。敵Wave解放は現状「最終ステップに到達した時のみ」。
- `MissionActionKind`(Evade/Attack/Skill)＋`MissionActionRecord`＋`ActionRepeatCountClearCondition` — 「指定行動をn回行う」条件。プレイヤーの攻撃・スキル・回避イベントから`MissionEventController.NotifyActionPerformed`経由で記録される。
- `Tutorial.prefab`(`Assets/Level/Prefabs/Master/InGame/`) — 会話ポップアップUIのCanvas一式。`InGame.unity`に配置済み。

現在`MissionDefinition_Tutorial.asset`に入っている内容(回避3回→攻撃5回→スキル2回→敵撃破2体)は**仮content**であり、本計画書の詳細フローに置き換える。

## 2. 確定チュートリアルフロー

仕様書の詳細説明を、上記の簡略化を反映して整理したステップ列。

| # | ステップ | 達成条件 | 案内テキスト(例) |
|---|---|---|---|
| 1 | 移動 | 移動入力が一度でも発生 | 「プレイヤーの移動はWASDで行える」 |
| 2 | ロックオン確認 | ロックオンを一度取得 | 「近くの敵に照準を合わせるとロックオンできる」 |
| 3 | 攻撃(1拍子) | 1拍子で攻撃がヒット | 「攻撃ボタンをタイミングよく押すと攻撃できる」 |
| 4 | 攻撃(2拍子) | 2拍子で攻撃がヒット | 「拍のリズムによって攻撃の種類が変わる」 |
| 5 | 攻撃(4拍子) | 4拍子で攻撃がヒット | (同上、拍子違い) |
| 6 | 攻撃(8拍子) | 8拍子で攻撃がヒット | (同上) |
| 7 | 攻撃(3拍子) | 3拍子で攻撃がヒット | 「特殊な拍でも攻撃できる」 |
| 8 | 攻撃(6拍子) | 6拍子で攻撃がヒット | (同上) |
| 9 | 敵攻撃の確認 | 敵の攻撃発生を1回観測 | 「敵が攻撃してくることがある」 |
| 10 | 回避 | 敵の攻撃を1回回避 | 「回避ボタンで敵の攻撃をかわせる」 |
| 11 | キルコード確認 | 案内を1回確認(手動進行) | 「現在装備しているキルコードはこちら」 |
| 12 | 敵の撃破 | 敵を規定数撃破(既存の`EnemyKillCountClearConditionAsset`) | 「敵を倒してみよう」 |

**敵の攻撃力は常に0**(チュートリアル用の敵データとして用意し、被弾しても実害が無い状態でステップ9・10・12を安全に体験させる)。敵Waveの解放タイミングは「ロックオン確認」ステップ開始時(#2開始時)に前倒しする — 攻撃練習(#3〜#8)には攻撃対象が必要なため。

## 3. 新規に必要な拡張

### 3.1 敵Wave解放タイミングの一般化

現状`ObjectiveSequenceDirector`は「最終ステップに到達した時だけ`EnemyWaveTimerView`を解放する」ハードコードになっている。これを**ステップごとに解放するかどうかを指定できる**ように変更する。

- `ObjectiveSequenceStep`(Domain)に`bool ReleasesEnemies`を追加。
- `ObjectiveSequenceStepAsset`(Infra)に対応する`[SerializeField] bool _releasesEnemies`を追加。
- `ObjectiveSequenceDirector.HandleObjectiveStepChanged`の判定を`isFinalStep`から`_sequence.GetStep(stepIndex).ReleasesEnemies`に変更。

これにより「攻撃練習のために2番目のステップで敵を出す」といった今回の要件も、将来のボス戦などで「フェーズ2開始時に増援を出す」といった用途も、同じ仕組みでカバーできる。

### 3.2 情報提示のみのステップ(操作条件を伴わない)

「キルコード確認」は達成条件を伴わない、単純な「確認して進む」ステップ。既存の`ObjectiveSequenceClearCondition`は「先頭から見て最初の未達成ステップ」を都度`MissionProgress`の累積値から計算するステートレスな設計のため、常に真となる条件を置くと**即座に達成済み扱いになり、案内を表示する前にスキップされてしまう**。

対応として、Mission側に汎用の「手動確認カウント」を追加する。

- `MissionProgress`に`int ManualAcknowledgeCount`と`RecordManualAcknowledge()`を追加(`RecordActionPerformed`と同じ並び)。
- `ManualAcknowledgeClearCondition(int requiredCount) : IMissionClearCondition` — `progress.ManualAcknowledgeCount >= requiredCount`を見る条件。シーケンス内で情報提示ステップが複数ある場合は、出現順に`requiredCount`を1, 2, 3…と割り当てる。
- `ObjectiveSequenceDirector`は、現在ステップの条件が`ManualAcknowledgeClearCondition`の場合、案内表示→入力待ちの**直後**に`MissionEventController.NotifyManualAcknowledge()`(新設、`NotifyActionPerformed`と同型)を呼び、`progress.RecordManualAcknowledge()`させてから次ステップへ進める。

この仕組みは「キルコード確認」に限らず、今後増える可能性のある純粋な説明ステップ全般に使い回せる。

### 3.3 拍子別攻撃の達成条件

攻撃が「どの拍子でヒットしたか」を記録する必要がある。現状`PlayerAttackController.OnAttackExecuted`は`(string attackName, bool hit)`のみを通知しており、`BeatType`(`1.Domain/InGame/Music/BeatType.cs`、値は1/2/3/4/6/8)を運んでいない。

- `MissionProgress`に`AttackBeatRecord`(`EnemyKillRecord`と同型、`BeatType`ごとのヒット回数を記録するEntity)を追加。
- `PlayerAttackController.OnAttackExecuted`のシグネチャに`BeatType beatType`を追加(`ExecuteAttack`内で既に`beatType`をローカル変数として持っているため、渡すだけで済む)。
- `MissionActionPerformedUsecase`とは別に`MissionAttackBeatUsecase`(またはイベント引数を拡張する形で`MissionRuntimeService.OnActionPerformed`にオーバーロードを追加)を用意し、`AttackBeatRecord`へ記録する。
- `AttackBeatTypeClearCondition(BeatType requiredBeatType) : IMissionClearCondition` — `progress.AttackBeatRecord.GetCount(beatType) >= 1`を見る新しい葉条件(`ActionRepeatCountClearCondition`と同格)。

3拍子・6拍子のステップ(#7・#8)は、現在のチュートリアル戦闘BGMのリズム定義(`MusicSyncService`/リズム判定アセット)が実際にそれらの拍子を含んでいるかをデータ側で確認する必要がある。BGM自体の切替は行わない方針のため、**現行BGMのリズムマップに3拍子・6拍子が含まれていない場合はこの2ステップは実現できない**。実装着手前に対象BGMのリズム定義を確認すること。

### 3.4 ロックオン確認・敵攻撃確認の達成条件

いずれも「一度でも発生したら達成」という形なので、3.3と同様に既存の`MissionActionKind`ファミリーへ種別を追加する形で対応する。

- `MissionActionKind`に`LockOn`・`WitnessEnemyAttack`を追加。
- ロックオン: `TargetSystemController`/`PlayerAttackController.HasCurrentLockOnTarget`が新規にtrueへ変化した瞬間を捉えるイベントを追加(現状はプロパティのみで変化通知が無いため)。
- 敵攻撃確認: 敵側に既存の`EnemyAIController.OnAttackReserved`/`OnAttack`イベント(`3.Adaptor/InGame/Enemy/EnemyAIController.cs`)が既にあるため、これをComposition層で購読して`MissionEventController.NotifyActionPerformed(MissionActionKind.WitnessEnemyAttack)`へ橋渡しするだけでよい(新規イベントの追加は不要)。
- 回避(#10)は、既存の`MissionActionKind.Evade`(`PlayerController.OnDodgeSucceeded`由来、回避入力が成立しただけで発火)ではなく、**実際に敵の攻撃を無効化できた時だけ発火する`CharacterEntity.OnDamageAvoided`**(`1.Domain/InGame/Character/CharacterEntity.cs`、既存)を新しい発火源として使う。「敵からの攻撃を回避した」という意味に厳密に合わせるため。

### 3.5 移動の達成条件

`PlayerController.Update`(`3.Adaptor/InGame/Player/PlayerController.cs`)には移動成立の通知が無い。`MissionActionKind.Move`を追加し、入力ベクトルが非ゼロの時に一度だけ発火する`event Action OnMoved`を`PlayerController`に追加する(`OnDodgeSucceeded`と同じ形)。

### 3.6 敵の攻撃力を0にする(コード変更なし、データのみ)

既存の敵Wave定義・攻撃定義アセット(`EnemyWaveDefinitionAsset`、敵の攻撃仕様アセット群)は完全にデータ駆動のため、コード変更は不要。**チュートリアル専用の敵Wave定義**(既存の`enemy_wave_default`を複製し、参照する攻撃定義だけ確定ダメージ0のバリアントに差し替えたもの)を新規作成し、`BattleStage_Tutorial.asset`の`_enemyWaveDefinitionId`をそちらに向ける。

### 3.7 ミッション確認画面への現在目標表示

仕様書の「ミッション確認画面で行うことの確認」に対応する。既存の`MissionHudView`/`MissionHudPresenter`は`MissionDefinition.MainMissionText`という**ミッション全体で固定の説明文**を表示する仕組みしか持たない。現在ステップに応じて表示を切り替えるには、

- `MissionRuntimeService.OnObjectiveStepChanged`を`MissionHudPresenter`側でも購読し、現在ステップの`ObjectiveSequenceStep`(案内メッセージ、または別途「HUD用の短い説明文」フィールドを追加してもよい)を`MissionHudViewModel`へ反映する。

この部分はHUDの表示ロジックにのみ関わる変更で、`ObjectiveSequenceDirector`(ポーズ＋ポップアップ側)とは独立して追加できる。

## 5. 実装順序

1. `MissionActionKind`拡張・`MissionProgress`拡張(`AttackBeatRecord`/`ManualAcknowledgeCount`)
2. `AttackBeatTypeClearCondition`/`ManualAcknowledgeClearCondition`とその Asset を追加
3. `ObjectiveSequenceStep`/`ObjectiveSequenceStepAsset`に`ReleasesEnemies`を追加し、`ObjectiveSequenceDirector`のロジックを「最終ステップ固定」から「ステップ指定」に変更
4. `PlayerAttackController.OnAttackExecuted`へ`BeatType`を追加、`PlayerController.OnMoved`を追加
5. `ObjectiveSequenceInitializationModule`で、ロックオン変化イベント・`EnemyAIController.OnAttackReserved`・`CharacterEntity.OnDamageAvoided`・`PlayerController.OnMoved`を`MissionEventController`へ配線
6. チュートリアル専用の0ダメージ敵Wave定義データを作成し、`BattleStage_Tutorial.asset`から参照させる
7. `MissionDefinition_Tutorial.asset`を12ステップ構成へ、Unity Editor上で`SerializedObject`を使って再構築
8. `MissionHudPresenter`の現在ステップ反映(3.7)
9. Play Modeでの通し確認

## 6. 検証観点

- 12ステップが仕様順に進み、各ステップの案内テキストがポーズ中に表示されること
- 攻撃練習ステップで対象の敵が既に出現していること(ロックオン確認ステップ開始時に解放)
- 敵の攻撃を受けてもプレイヤーのHPが減らないこと(0ダメージデータの確認)
- 3拍子・6拍子ステップが現行BGMのリズム定義で実際に到達可能かどうか(到達不可能なら、この2ステップの扱いを別途相談する)
- 「キルコード確認」ステップで、条件を持たないにもかかわらず案内が正しく一時停止・表示されること(ManualAcknowledgeの動作確認)
- 撃破ステップ達成でチュートリアル完了処理(`TutorialData.IsTutorialCompleted`)が今まで通り行われること
- 通常ステージ(01〜03等)の`ObjectiveSequenceClearCondition`を使わないミッションが今まで通り動作すること
