# 仕様検索の設定と索引更新

/spec は、通常回答に利用できる資料を選別してから、日本語bigram/英数字のBM25検索とコサイン類似度検索を実行する。各方式の上位候補をRRFで統合し、資料と節の重みで順位を調整する。同一ページからの採用数を制限し、同じ本文の重複を除く。

## env設定

設定の正本は SinfoniaOperator/sinfonia-operator.env.json の SPEC_SEARCH オブジェクトである。従来の SPEC_SEARCH_PRIORITY_PATH と spec-search-priority.json はBotから読み込まない。秘密設定ファイルや起動引数のJSONに同じキーがあると、既存の設定ローダーの規則によりオブジェクト全体が上書きされる。環境変数にJSONを指定する場合もキー名は SPEC_SEARCH である。

設定は起動時に読む。設定がない場合や不正な場合は、重みなし検索に切り替えずエラーを返す。

| 項目 | 意味 |
| --- | --- |
| SourceRules | 資料の分類と重み。1件以上必要 |
| SectionRules | 見出しのパンくずに対する節の重み。空配列なら全節が同じ重み |
| CandidateCount | 各検索方式から融合する候補数。既定40、1〜1000 |
| MaxChunksPerPage | 同一ページから返す最大チャンク数。既定2 |
| MinimumSimilarity | 意味検索候補にするコサイン類似度の下限。既定0.7 |
| MinimumLexicalCoverage | キーワード候補に必要なクエリ語の一致率。既定0.5 |
| SemanticWeight / LexicalWeight | RRFで使う各検索方式の重み。既定は両方1 |
| RrfConstant | RRFの順位平滑化定数。既定60 |

最終表示件数は既存の SPEC_SEARCH_TOP_K（既定3、最大10）で指定し、CandidateCount以下にする。関連する根拠が少ないときは、件数を埋めるために低信頼資料を追加しない。

RRFの値は「SemanticWeight / (RrfConstant + 意味検索順位) + LexicalWeight / (RrfConstant + BM25順位)」。これに資料のWeightと節のWeightを掛ける。順位は1始まりで、その方式の候補にない場合の項は0とする。重みは類似度の足切りを覆さず、BM25経路は語の一致率で別に判定する。閾値は確率・正答率ではない。実際の質問と正本ページの対応を使って調整する。

### SourceRules

1ルールには、次の識別条件のうち1つだけを指定する。

- PageId: NotionのページID。改名・移動後も同じ資料に適用する
- DocumentKind: DBプロパティ「文書用途」の完全一致
- PathContains: キャッシュファイルのパスの部分一致。移行前の分類に使う

優先順位は PageId → DocumentKind → 長いPathContains。同一条件の重複は設定エラーとする。各ルールに Weight（有限の非負数）と IsPrimary を指定する。

- IsPrimary=true: 通常の仕様質問の根拠候補にできる
- IsPrimary=false: history=trueの場合だけ候補にできる
- Weight=0: 履歴検索でも候補にしない
- どのルールにも一致しない: 未分類として両方の検索から除外する。件数を起動ログへ出す

通常検索で除外する採用状態は、検討中・草案・未承認・要確認・反映待ち・保留・却下・廃止・アーカイブである。「未実装」は実装状態なので除外理由にしない。古い文書をページの更新日時だけで現行仕様へ昇格させない。

### SectionRules

HeadingContains に一致する節とその子孫へ Weight を適用する。履歴検索では HistoryWeight を使う。複数ルールに一致した場合は最小の重みを採用し、親の除外を子の設定で解除しない。

初期設定では、仕様意図・背景・経緯・変更履歴・却下・保留・旧仕様・アーカイブ・補足を通常検索から除外する。history=trueで、これらを参照できる。見出し名はパス・IDと異なり本文の役割の識別に用いる。コードブロック内の見出し記法は節として扱わない。

## Notionキャッシュとの接続

index コマンドは NOTION_EXPORT_OUTPUT のディレクトリを読む。未設定なら Library/NotionSpecifications を優先し、存在しなければ旧 Docs/NotionSpecifications を読む。リポジトリ全体・Git履歴・移行原稿を検索対象にしない。DB索引（先頭が _ のファイル）と assets は本文候補に含めない。

従来Exporterの「Notionで開く」リンク・最終更新行・プロパティ表を読み取る。移行案のHTMLコメントヘッダ（source / page_id / last_edited）にも対応する。プロパティ表から次の名前を読む。

| プロパティ | 検索での扱い |
| --- | --- |
| 文書用途 | SourceRules.DocumentKindに照合 |
| 仕様状態 | 採用済み・廃止など。実装状態と区別 |
| 実装状態 | 未実装を含めて回答生成へ伝える |
| 適用範囲 | 製品版・体験版などを回答生成へ伝える |
| 状態 | 旧構成との互換。アーカイブ等は仕様状態、未実装等は実装状態へ振り分ける |

DBプロパティが未整備でも、PageId / PathContainsの設定で資料を分類できる。プロパティを読み取れないページを、本文の雰囲気だけで正式仕様に分類しない。

見出しとトグルの境界でチャンクを分離する。通常本文と末尾の経緯が同じチャンクへ混ざらないよう、重複部分も節の境界を跨がせない。引用元はpage IDで識別し、同じページのキャッシュが複数あっても採用上限を共有する。

移行計画のT-2（取得と差分更新）とは別の責務である。この変更はNotionを自動取得せず、親仕様リレーションの追跡やDB一覧の同期も行わない。索引はキャッシュのスナップショットであり、最新版を保証しない。既知の反映待ちは仕様状態またはページ個別のIsPrimaryで明示する。適用範囲が混在する表の自動分解は行わず、回答時に範囲を区別させる。

## 更新手順

1. envにSPEC_SEARCHを設定し、対象キャッシュを用意する
2. Botの新しい実行ファイルで index コマンドを実行して索引を再生成する
3. 更新済み索引と同じ版の実行ファイルで serve する

索引形式はversion 2である。古いversion 1はページ属性とトグル境界を保持していないため読み込みを拒否し、再生成を案内する。資料重みだけの変更では索引の再生成は不要だが、Botは設定を起動時に読むため再起動が必要。本文・プロパティを変えた場合は、キャッシュを更新して索引を再生成する。

### デプロイworkflow

Deploy Sinfonia Operatorは公開envからSPEC_SEARCHだけをパッケージへ抽出する。VM上の既存キャッシュ（Library/NotionSpecifications優先、旧Docsへフォールバック）と既設モデルから、新リリースのディレクトリへ索引を再生成する。Notionの取得は行わないため、必要なキャッシュ更新は配備前に別途行う。

serveは実行ファイルと同じ場所のspec-search.release.jsonが存在する場合、その検索設定・索引パス・モデルパスを最後に読み込む。この3項目はVM既存設定よりリリースの組を優先し、トークンやその他の設定はVM側の既存値を使う。公開envの変更もデプロイを起動する。

索引生成が失敗した場合は稼働中のBotを切り替えない。切替後は/specと/branchesの登録を確認し、失敗した場合は旧バイナリ・設定・索引の組へ戻す。初回移行時の旧索引も上書きしない。VMにはpython3と、既存手順のモデル配置（models/multilingual-e5-small）が必要。

## 回答と引用

/spec query:質問 は通常の仕様を検索する。/spec query:質問 history:true は記録と過去の経緯も含める。理由や過去の判断を調べる場合は履歴を含める。

Geminiには資料番号、見出し、分類・状態・適用範囲、本文を渡す。JSON回答のsourcesと本文中の[1]等の引用番号が一致し、すべて渡した候補内にあることを検証する。根拠を挙げられなかった場合は根拠不足と返し、候補全部を引用一覧へ載せない。生成・引用検証に失敗した場合は、回答として断定せず検索候補の抜粋を表示する。

引用番号の検証は、引用内容が回答のすべての主張を意味的に裏付けることまで保証しない。根拠不足時の抑制や関連度閾値の調整は、別途実際の質問で評価する必要がある。

## 検証観点

- env内のオブジェクト配列が欠落せず、後から読み込んだ設定が優先される
- 正式仕様とタスクに同じ用語があっても、通常検索はタスクを除外する
- 正本ページ内の経緯・却下案・トグルが通常の回答へ混入しない
- 履歴検索だけが履歴候補を許し、Weight=0と未分類は常に除外する
- 未実装の採用済み仕様は検索でき、廃止仕様は通常検索から除外する
- PageId指定が改名・移動後も効き、同一ページの重複が件数を占有しない
- コードブロック内の見出しで節が誤分割されない
- 根拠不足、範囲外引用、引用番号不一致、旧索引を正常回答として扱わない

テスト・外部APIによる実回答評価は、実行が許可された段階で行う。
